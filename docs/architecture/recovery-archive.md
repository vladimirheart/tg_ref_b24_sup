# Исторические recovery-артефакты

Задача 01-330 вывела из рабочего дерева 52 исторических файла (955 146 509 байт)
из `spring-panel/recovery-*`, `spring-panel/db-backup-*`, отдельную повреждённую
копию `panel_runtime.db.corrupt-*` и содержимое `temp-recovery`, кроме README.
Это старые снимки и инструменты восстановления, исключённые из текущей поставки.
Рабочие файлы с именами БД, текущие конфигурации, миграции и production не менялись.

Перед удалением каждый файл скопирован во внешний архив и проверен по SHA-256.
Манифест `recovery-archive-330.json` хранит размер, SHA-256 и исходный Git blob
каждого файла. Раскладка архива повторяет исходные пути от корня репозитория.
Точное расположение локальной копии сохраняется в ignored evidence
`spring-panel/target/architecture-330/archive.json` и итоговом apply report.

История Git сохранена. Старые blobs остаются доступны из commit
`90f2a54f21f93a0fddbbfc9b6f57d987cc97119a`; эта чистка уменьшает текущую поставку,
но не переписывает историю и не обещает уменьшить размер полного клона.

## Проверить архив

```powershell
node .\tools\recovery-archive.cjs --archive 'ПОЛНЫЙ_ПУТЬ_К_АРХИВУ'
```

Команда читает файлы, сверяет размеры и SHA-256. SQL и архивные EXE не запускаются.

## Восстановить в отдельный каталог

```powershell
node .\tools\recovery-archive.cjs --archive 'ПОЛНЫЙ_ПУТЬ_К_АРХИВУ' --restore-to 'D:\recovery-review'
```

Для одного файла добавьте `--only 'исходный/путь/из/манифеста'`.
Существующие файлы с другим содержимым не перезаписываются. Восстановление
внутрь текущего checkout запрещено: сначала изучите восстановленные файлы,
затем отдельно решите, что требуется вернуть. Это не runtime fixtures и не
источник текущей схемы или настроек панели.

Значения `historical_snapshot_paths` в диагностике настроек — исходные пути
архивных снимков, а не запрос прочитать эти файлы во время работы панели.
