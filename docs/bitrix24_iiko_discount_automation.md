# Автоматизация Bitrix24 + iiko

Документ описывает runtime-контур панели для сценария отключения корпоративных
скидок сотрудников.

## Что уже умеет контур

- запускаться из панели по кнопке;
- выполнять `dry-run` без боевых изменений;
- использовать личные доступы текущего пользователя панели для Bitrix24 и iiko;
- хранить несколько iiko URL-профилей на пользователя и переключать активный профиль;
- загружать организации iiko для выбранного URL;
- загружать активные категории гостей и кошельки/программы корпоративного питания для выбранного URL;
- сохранять выбор категорий и кошельков внутри активного URL-профиля;
- подключаться к Bitrix24 по webhook;
- находить группы и задачи;
- фильтровать только незакрытые задачи, в которых checklist-пункт еще не
  отмечен;
- извлекать телефон сотрудника из тела задачи;
- по боевому запуску искать гостя по телефону и удалять выбранные категории и
  выбранные программы корпоративного питания;
- вести историю запусков и результатов по каждой задаче в БД панели.

## Где находится UI

- страница `AI Ops`;
- блок `Bitrix24 + iiko automation`.

## Где теперь хранятся секреты

Секреты больше не привязаны к local-machine файлам.

Личные доступы Bitrix24/iiko сохраняются в панели отдельно для каждого
пользователя через `settings_parameters` с ключом
`employee_discount_automation_credentials.v1`.

В UI секретные поля не возвращаются обратно в браузер:

- `webhook_url`;
- `api_secret`.

Если оставить эти поля пустыми при сохранении, панель сохраняет уже существующее
секретное значение.

## Что хранится в общих versioned settings

В `config/shared/settings.json` сохраняются только общие non-secret настройки
автоматизации:

- `bitrix_group_id`;
- `task_title_markers`;
- `checklist_labels`;
- `phone_regex`;
- `dry_run_by_default`.

## Что хранится в личном конфиге пользователя панели

Личный конфиг пользователя может содержать:

- `bitrix24.portal_url`;
- `bitrix24.webhook_url`;
- `active_iiko_profile_url`;
- набор `iiko_profiles` по `base_url`;
- для каждого URL-профиля:
  - `base_url`;
  - `api_login`;
  - `api_secret`;
  - `organization_id`;
  - `selected_discount_category_ids`;
  - `selected_wallet_ids`.

## Рабочая механика в панели

- шаг 0: пользователь сохраняет URL и креды для нужного iiko-контура;
- шаг 1: по активному URL загружаются организации, категории и кошельки;
- шаг 2: пользователь отмечает нужные категории и кошельки и сохраняет профиль;
- шаг 3: панель анализирует задачи Bitrix24 и для найденных сотрудников удаляет
  выбранные категории и кошельки/программы.

## Ограничения текущего этапа

- под “кошельками” сейчас используется documented-механика программ
  корпоративного питания через `remove_from_nutrition_organization`;
- перед production-использованием нужен живой прогон на реальных учетных
  данных и подтверждение, что бизнес-смысл “кошелька” у вас действительно
  соответствует этой iikoCard-модели;
- checklist в Bitrix24 отмечается только после успеха по задаче;
- персональные секреты уже user-scoped, но пока хранятся в БД панели без
  отдельного слоя шифрования.

## Что нужно для завершения боевого режима

- ручная проверка на ваших реальных URL и организациях;
- подтверждение, что выбранные “кошельки” действительно надо отключать через
  программы корпоративного питания;
- при необходимости тонкая корректировка обработчика под фактические тексты
  ошибок вашего iiko-контура.
## AI closeout v40

Перед live acceptance дополнительно зафиксированы runtime-инварианты:

- run history читается только в scope текущего authenticated пользователя панели;
- ошибка извлечения телефона сохраняется как `error`, а не как `skipped`;
- Bitrix24 checklist вызывается только после `MutationResult.success=true` от iiko;
- при iiko failure checklist не отмечается, а run/item history сохраняет ошибку;
- dry-run остаётся полностью non-mutating.

### Финальный ручной smoke

1. Сохранить Bitrix24 webhook и активный iiko URL-профиль текущего пользователя.
2. Выбрать Bitrix24 group и выполнить Preview/Dry-run.
3. Проверить телефон и целевой незакрытый checklist-пункт на тестовой задаче.
4. Выполнить execute на безопасной тестовой записи iiko.
5. Убедиться, что выбранные категории/программы отключены и только после этого checklist Bitrix24 стал complete.
6. Открыть run details и проверить per-task status/message.
7. Под другим пользователем панели убедиться, что этот run не появляется в history и прямой `/runs/{id}` возвращает 404.

После этого `01-033` можно вручную перевести из `🟣` в `🟢`.

## Runtime-аудит v42 — 2026-08-24

Повторная проверка `01-033` выявила несколько скрытых runtime-дефектов, которые не были покрыты v40:

- `tasks.task.list` читался только одной страницей, поэтому задачи Bitrix24 после первых 50 могли не попадать в автоматизацию;
- `task.checklistitem.complete` вызывался именованными параметрами и без проверки `result=true`; теперь используется позиционный контракт `0=TASKID`, `1=ITEMID`, а `result=false` считается ошибкой;
- повторный execute после сценария «iiko уже изменён, а Bitrix checklist не подтвердился» мог повторно вызвать `remove_category`; теперь явный пустой snapshot категорий и ignorable removal errors трактуются идемпотентно;
- ошибки HTTP iiko теперь сохраняют API reason, когда он присутствует в JSON, вместо потери тела ошибки;
- credential storage использует PostgreSQL/SQLite-portable `BOOLEAN` SQL (`FALSE`) и больше не проглатывает DB/JSON failures: успешный ответ save означает, что user-scoped запись действительно сохранена;
- пустой список выбранных iiko categories/wallet programs теперь действительно очищает selection, а не восстанавливает старый fallback;
- Bitrix статус `6` (deferred/postponed) больше не считается закрытым: отложенная незакрытая задача остаётся кандидатом;
- явный пустой `task_title_markers` теперь снимает старый title-фильтр; UI после failed run перечитывает durable history, чтобы error-run сразу был виден оператору;
- `run()` больше не держит одну БД-транзакцию вокруг внешних HTTP-вызовов; run сохраняется до Bitrix discovery, discovery failure попадает в durable history, а execute-item записывается как `running` до внешнего mutation.

После v42 остаётся обязательный live acceptance: реальный webhook Bitrix24, активный iiko URL-профиль, dry-run и безопасный execute на тестовой записи. Отдельно нужно подтвердить бизнес-смысл «кошельков» как corporate nutrition programs в конкретном iiko-контуре.
