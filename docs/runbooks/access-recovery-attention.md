# Восстановление доступа и ожидающие действия

Миграцию `V104__access_recovery_attention.sql` выполняет штатный владелец миграций (`all` / `db-migrate`) перед запуском обновлённых web-реплик. Старые заявки и решения сохраняются. Повторные ожидающие заявки одной УЗ или одного неизвестного логина объединяются с сохранением исходных строк в статусе `MERGED`.

## Права

В существующих каталогах ролей и персональных разрешений добавлены действия:

| Название | Ключ поля роли | Authority |
| --- | --- | --- |
| Разблокировать клиента | `client.unblock` | `EDIT_CLIENT_UNBLOCK` |
| Восстановить доступ | `access.recover` | `EDIT_ACCESS_RECOVER` |

Административные роли наследуют действия по действующим правилам. Персональный `DENY_…` учитывается. Системная УЗ `admin` сохраняет доступ. Делегирование восстановления не даёт права восстанавливать административные УЗ: это делает администратор. Право просмотра страницы «Клиенты» само по себе больше не разрешает разблокировку.

Все действующие пользователи видят счётчик запросов клиентов. Детали клиентов доступны с `PAGE_CLIENTS` или правом разблокировки, а принятие решения — с правом разблокировки. Восстановление доступно по `/access-recovery-requests` даже сотруднику без страницы настроек, если у него есть соответствующее действие.

## Обработка

Форма «Восстановить доступ» доступна без входа, включая заблокированные УЗ. Она собирает введённый логин, ФИО, контакт, причину и комментарий. Публичный ответ одинаков для известного, неизвестного и заблокированного аккаунта. Неизвестный или неоднозначный логин сохраняется как `NEEDS_REVIEW`.

Ответственный проверяет личность через известный корпоративный контакт или руководителя. Введённый заявителем контакт и технические признаки не служат доказательством владения УЗ. Для привязки существующей УЗ и одобрения обязательны отметка проверки и основание решения. Неизвестная УЗ не создаётся автоматически.

Сброс пароля и снятие блокировки выбираются отдельно. Сброс не включает `enabled` и не снимает `is_blocked`. Выбранные действия и решение фиксируются атомарно, с блокировкой на время обработки. После восстановления повышается `session_version`, поэтому старые сеансы и remember-me теряют доступ. Другие ожидающие заявки той же УЗ получают `SUPERSEDED`.

Временный пароль возвращается только сотруднику в ответе одобрения, с `Cache-Control: no-store`, и остаётся в текущем документе до явного скрытия/ухода. Он не сохраняется в журнале, localStorage или истории заявки. Передача пользователю остаётся ручной.

Отметки просмотра персональны и привязаны к неизменяемому ID сотрудника. Они не уменьшают счётчик ожидающих действий. Оповещения обновляются через SSE и резервный опрос каждые 15 секунд.

## Настройки защиты

| Переменная | По умолчанию |
| --- | --- |
| `APP_ACCESS_RECOVERY_MINIMUM_RESPONSE_TIME` | `350ms` |
| `APP_ACCESS_RECOVERY_RATE_WINDOW` | `15m` |
| `APP_ACCESS_RECOVERY_REQUESTS_PER_IP` | `20` |
| `APP_ACCESS_RECOVERY_REQUESTS_PER_LOGIN` | `5` |
| `APP_ACCESS_RECOVERY_LOGIN_ATTEMPTS_PER_IP` | `100` |
| `APP_ACCESS_RECOVERY_LOGIN_ATTEMPTS_PER_LOGIN` | `20` |
| `APP_ACCESS_RECOVERY_METADATA_RETENTION_DAYS` | `90` |
| `APP_ACCESS_RECOVERY_TRUSTED_PROXIES` | пусто |

Лимиты хранятся в PostgreSQL и действуют для всех web-реплик. Учитываются также неизвестные логины. Превышение лимита отправки восстановления сохраняет общий публичный ответ. Допущенные повторные отправки увеличивают счётчик, но не заменяют первоначальные контакт, комментарий, привязку и решение. Публичные endpoint остаются под защитой CSRF.

По умолчанию IP берётся из соединения. За reverse proxy задайте только реальные доверенные CIDR/адреса через `APP_ACCESS_RECOVERY_TRUSTED_PROXIES` (список через запятую). Цепочка `X-Forwarded-For` проверяется справа налево до первого недоверенного узла. При используемой в production стратегии Spring `framework` проверка IP обращается к исходному запросу до forwarded-обёрток. Не переключайте обработку адреса на native valve без отдельной проверки доверенных прокси. Вход к приложению должен идти только через предусмотренные ingress. Все перечисленные переменные проброшены в общий environment production compose.

Из диагностических записей исключаются пароли, токены и cookies. Сохраняются время, IP соединения/источника, ограниченный User-Agent, ID запроса, результат поиска УЗ и действия сотрудника. Браузер/ОС определяются приблизительно из User-Agent. Диагностика видна только обладателям права восстановления.

Ежечасная очистка удаляет устаревшие IP/User-Agent/ID корреляции, события неудачного входа и старые счётчики лимитов. После срока хранения у завершённых заявок очищаются контакт, ФИО и комментарии; у событий — пояснения. Основные решения, исполнители и даты сохраняются. Незавершённые заявки и их персональные отметки просмотра не удаляются.

Для входа выполняется сопоставимая проверка пароля, включая legacy-пароли и заблокированные УЗ. Неизвестный логин использует защиту dummy-hash в DaoAuthenticationProvider. Нижняя граница времени дополняет одинаковые пути обработки и публичные ответы. Она не гарантирует точного совпадения миллисекунд при любой нагрузке: перед выпуском нужно сравнить распределения времени по сериям запросов через реальный ingress и подобрать границу под фактическую стоимость хеширования/БД. Дополнительно нужны инфраструктурные ограничения нагрузки на публичные маршруты.

cd spring-panel
.\mvnw.cmd '-Dtest=AccessRecoverySecurityTest,AccessRecoveryPostgresqlTest,AccessRecoveryWebMvcTest,PanelAccessPolicyTest,SessionAuthorityWebMvcTest,AuthManagementIdentityWebMvcTest,UnblockRequestsControllerWebMvcTest,AuthCredentialInputWebMvcTest,AuthLegacyLoginCollisionTest' test
