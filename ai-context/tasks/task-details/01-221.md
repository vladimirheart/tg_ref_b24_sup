# Задача [01-221] Провести предметный аудит client avatars и dialog media после recovery storage-контура и закрыть остаточные legacy-ожидания

Статус: 🟣 Ожидает ручной проверки

## Краткое описание

После recovery 2026-08-31 dialog attachment storage снова зелёный, но по операторскому восприятию остаются вопросы: «куда пропали аватары клиентов и всё медиа из диалогов» и не потерялось ли что-то во время разрезания сервисов. Нужно зафиксировать фактические источники данных, понять, где реальная потеря, а где неверное ожидание legacy-path, и закрыть этот хвост отдельным аудитом.

## Почему это важно

- Storage gates подтверждают, что canonical dialog objects и panel avatar objects доступны, но это ещё не объясняет UX-восприятие операторов.
- Текущий live audit показывает `client_avatar_history_users_checked=0`, то есть клиентские аватары сейчас не подтверждаются через тот же путь, что panel avatars.
- Без явного аудита легко перепутать реальные data gaps, пустые исторические таблицы, внешние URL и остаточную привязку UI к legacy-путям.

## Что нужно сделать

1. Разобрать, из каких именно источников UI берёт:
   - media вложения диалогов;
   - client avatars;
   - panel user avatars.
2. Сверить live БД, MinIO/S3 и реальные UI/API endpoints для каждого класса media.
3. Отделить три сценария:
   - данные реально есть и UI их должен показывать;
   - данные исторически отсутствуют и это не regression;
   - данные есть, но UI или API всё ещё смотрит в legacy/неправильный source.
4. Если найдётся реальный residual legacy path, создать или выполнить точечный fix без возврата общего local fallback.
5. Обновить task-detail доказательствами: SQL counters, object checks, runtime endpoints и конкретным verdict по каждому виду media.

## Критерии готовности

- Есть явная таблица соответствия `source of truth -> runtime endpoint -> storage/backend`.
- По client avatars, panel avatars и dialog media дан отдельный verdict: `ok`, `historically absent` или `needs fix`.
- Если нужен fix, он локализован и не требует повторного включения `APP_STORAGE_OBJECT_LEGACY_LOCAL_FALLBACK_ENABLED=true`.
- Операторы получают понятное объяснение, что именно было recovery, а что остаётся предметом отдельной миграции/UI-правки.

## Findings on 2026-08-31

### Source-of-truth map

- Dialog media:
  `chat_attachment_metadata.storage_key` + `availability_status` -> `DialogConversationReadService.toAttachmentUrl(...)` -> `/api/attachments/tickets/by-storage-key?key=...` -> `AttachmentService.downloadTicketAttachmentByStorageKey(...)` -> `AttachmentObjectStorageService.openDialogAttachmentByStorageKey(...)` -> canonical S3 object `iguana/attachments/<storage_key>` under prefix `iguana`.
- Panel user avatars:
  `users.photo` / `PanelUserPhotoService.resolveUserAvatarUrl(...)` -> `/api/attachments/avatars/<storedName>` -> `AttachmentService.downloadAvatar(...)` -> `AttachmentObjectStorageService.openAvatar(...)` -> canonical S3 object `iguana/avatars/<storedName>`.
- Client avatars in dialogs/workspace:
  `dialogs-shell-runtime.js` always builds `/avatar/<userId>` -> `AvatarController` -> `AvatarService.loadAvatar(...)` -> checks `PanelUserPhotoService.avatarFileName(userId, full)` with legacy client-style names `<userId>.jpg` / `<userId>_full.jpg` via `AttachmentObjectStorageService.avatarExists(...)`.

### Audit gap found and closed

До правки `scripts/docker-production-client-avatar-cutover-audit.ps1` смотрел только на `client_avatar_history`, поэтому мог ошибочно показывать GREEN при пустой истории и живом legacy avatar tail в `attachments/avatars`.

Скрипт был расширен так, чтобы проверять union двух источников кандидатов:

- `client_avatar_history`
- локальные `attachments/avatars` с паттерном клиентских файлов `<userId>.jpg` / `<userId>_full.jpg` и родственными image-расширениями

Новый live audit на 2026-08-31 подтвердил:

### Current verdict

  canonical path после recovery — `chat_attachment_metadata.storage_key -> /api/attachments/tickets/by-storage-key`; authoritative storage gate остаётся GREEN, неожиданных пропаж нет.
- Panel avatars: `ok`
  panel avatar reference и canonical S3 object подтверждены, `missing_s3_panel_avatars=0`.
