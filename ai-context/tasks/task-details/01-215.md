# Задача [01-215]

## Короткое описание

Исправить `Production readiness` для local PostgreSQL bootstrap, чтобы Redis/MinIO не помечались как незапущенные production-gate при явно отключённых `required-for-postgresql`, а RabbitMQ/лог-шум отражались понятнее.

## Цель

Привести readiness-контур в соответствие с фактическим runtime-контрактом `spring-panel\run-windows.bat`:

- local bootstrap на `APP_DB_MODE=postgresql` может осознанно работать без Redis coordination и без S3/MinIO;
- readiness не должен считать такой контур «поломанным prod», если launcher явно выставил compatibility-флаги;
- UI должен объяснять, что компонент отключён для локального bootstrap-контура, а не просто показывать непонятный статус;
- реальные проблемы RabbitMQ (например, сообщения в DLQ) должны оставаться видимыми и понятными.

## Контекст

- Launcher для локального PostgreSQL bootstrap уже подставляет:
  - `APP_COORDINATION_MODE=direct`
  - `APP_COORDINATION_REQUIRED_FOR_POSTGRESQL=false`
  - `APP_STORAGE_OBJECT_REQUIRED_FOR_POSTGRESQL=false`
- `ProductionReadinessService` сейчас определяет canonical/prod-контур только по `app.datasource.mode=postgresql`.
- Из-за этого:
  - Redis probe идёт как обязательный gate и даёт `unavailable`, хотя для local bootstrap он отключён намеренно;
  - MinIO/S3 probe идёт как обязательный gate и даёт `unavailable`, хотя local filesystem storage разрешён;
  - overall/readiness health/observability получают искажённую картину.
- По текущему `.env` RabbitMQ transport действительно активен (`APP_INTEGRATION_TRANSPORT_MODE=rabbitmq`), поэтому этот probe должен остаться боевым и честно показывать DLQ-сигналы.
- В логах есть шум двух типов:
  - transient ошибки JDBC/Hikari после административного рестарта PostgreSQL;
  - фоновые WARN интеграций/мониторов, которые не связаны напрямую с readiness modal.

## Что сделать

- Пересчитать readiness-классификацию по реальному production contour, а не только по `datasource_mode`.
- Учитывать `app.coordination.required-for-postgresql` и `app.storage.object.required-for-postgresql` при определении required/compatibility для Redis и object storage.
- Скорректировать `overall` readiness, чтобы local bootstrap c compatibility-компонентами не выглядел как full production ready.
- Сделать summaries/status labels в UI понятными для оператора: compatibility должен читаться как локально допустимый/необязательный контур, а не как «не запущено».
- Добавить/обновить unit tests для readiness service и связанных UI/health контрактов.
- Зафиксировать в задаче разбор фактических spring-ошибок, чтобы отделить реальный defect readiness от внешнего лог-шумa.

## Критерии готовности

- На local PostgreSQL bootstrap Redis coordination и MinIO/S3 больше не показываются как обязательные сломанные компоненты, если `required-for-postgresql=false`.
- `Production readiness` в UI различает:
  - production gate;
  - compatibility/локально допустимый компонент;
  - реальную деградацию, например DLQ в RabbitMQ.
- `overall` readiness для такого контура не маскируется под full `ready`.
- Targeted tests проходят.
- После AI implementation статус задачи только `🟣`; перевод в `🟢` делает пользователь после ручной проверки.

## Update 2026-08-27 09:48:55 +03:00 — readiness local bootstrap отделён от full production contour

Что изменено:

- `ProductionReadinessService` больше не считает любой `APP_DB_MODE=postgresql` автоматически full production contour.
- Для Redis и object storage теперь учитываются:
  - `APP_COORDINATION_REQUIRED_FOR_POSTGRESQL`
  - `APP_STORAGE_OBJECT_REQUIRED_FOR_POSTGRESQL`
- Если эти флаги выключены, Redis coordination и MinIO / S3 получают `compatibility`, помечаются как необязательные для текущего bootstrap-контура и не тянут `overall` в ложную деградацию.
- В snapshot добавлен верхнеуровневый `contour`, чтобы UI явно различал `production` и `compatibility`.
- RabbitMQ probe сохранён боевым: transport по-прежнему считается обязательным для PostgreSQL contour и честно показывает деградацию при ненулевых DLQ.
- `settings-production-readiness.js` переведён на понятные operator-facing подписи:
  - русские названия статусов;
  - human-readable labels для деталей вместо сырых `snake_case` ключей;
  - отдельное пояснение про local bootstrap contour.

Что показал разбор spring-логов:

- Проблема readiness была реальной логической ошибкой классификации bootstrap-контура, а не отсутствием запуска RabbitMQ/Redis/MinIO как такового.
- Шум в `spring-panel.log` сейчас складывается из отдельных внешних/транзиентных событий:
  - `FATAL: terminating connection due to administrator command` и Hikari WARN после административного рестарта PostgreSQL контейнера;
  - `SSL monitor check failed` для внешней цели;
  - `Scheduled Notion knowledge sync failed: Не задан integration token Notion`;
  - предупреждения про legacy Telegram proxy route.
- Эти WARN/ERROR не являются прямым следствием readiness modal и требуют отдельного решения только если хотим чистить integration/monitoring noise.
