# Задача [01-206]

## Короткое описание

Подключить alerting и SLO burn-rate по sustained provider delivery failures / rate-limit pressure из provider delivery ledger.

## Цель

Сделать `provider delivery ledger` не только retrospective журналом outbound delivery, но и proactive monitoring signal:

- автоматически выявлять не разовые ошибки, а устойчивую деградацию reply-path;
- отличать общий sustained failure pressure от отдельного rate-limit pressure;
- поднимать и резолвить signal incidents через уже существующий incident contour;
- дать оператору на analytics page быстрый срез burn-rate и историю таких alert-решений по каждому provider channel.

## Контекст

- В `01-203` уже появился persisted `provider_delivery_ledger` с нормализованной классификацией ошибок для outbound reply-path `Telegram` / `VK` / `MAX`.
- Текущий экран `provider-delivery` показывает overview и recent attempts, но пока не умеет:
  - вычислять sustained pressure по time-window, а не только по последней попытке;
  - различать error-budget burn для общих delivery failures и `429` / rate-limit pressure;
  - автоматически создавать signal incidents и закрывать их после восстановления.
- В проекте уже есть рабочий паттерн такого lifecycle:
  - `IncidentService.openOrRefreshSignalIncident(...)`;
  - `IncidentService.resolveSignalIncident(...)`;
  - lease-guarded scheduler через `RuntimeCoordinationService`;
  - operator-facing timeline через `monitoring_check_history`.
- Для `01-206` правильнее встроиться в existing incident/monitoring contract, а не делать новый параллельный alerting pipeline.

## Что сделать

- Добавить evaluator sustained provider delivery pressure поверх `provider_delivery_ledger`.
- Считать как минимум два независимых сигнала по каждому monitored channel:
  - общий delivery failure burn-rate;
  - rate-limit burn-rate на основе `classification = rate_limited` / `HTTP 429`.
- Использовать multi-window оценку, чтобы отличать кратковременный всплеск от sustained pressure.
- Сохранять snapshots burn-rate в `monitoring_check_history` с отдельным `monitor_kind/check_kind`.
- Поднять scheduler с lease, который регулярно пересчитывает alert state и синхронизирует incidents.
- Автоматически `open/refresh` incident при sustained `warning/critical` деградации и `resolve` после восстановления.
- Расширить API и analytics page `provider-delivery`:
  - alert overview;
  - channel-level burn-rate summary;
  - active incident context;
  - history modal по alert snapshots.
- Покрыть изменения целевыми тестами на burn-rate calculation, incident lifecycle и analytics/API surface.

## Ограничения и допущения

- Источником истины по outbound attempts остаётся `provider_delivery_ledger`; новые persisted business tables не нужны.
- Burn-rate считается только по фактически записанным outbound attempts и не должен придумывать synthetic traffic.
- Если по каналу мало данных, evaluator должен деградировать в `ok/idle`, а не плодить ложные incidents.
- Новые signal incidents должны дедуплицироваться по `signal_type/signal_key`, а не дублироваться на каждый scheduler tick.

## Критерии готовности

- У `provider-delivery` появляется отдельный alerting/burn-rate слой поверх уже существующего ledger.
- Sustained failure pressure и rate-limit pressure автоматически поднимают signal incidents и резолвятся после восстановления.
- На analytics page видно channel-level burn-rate summary, alert severity и связанный incident context.
- Есть timeline/history по alert snapshots, а не только по delivery attempts.
- Изменения покрыты целевыми тестами.
