# Задача [01-274]

## Краткое описание

Пересобрать контур задач в полноценный work-management workspace: проекты, независимое включение задач в проекты, Kanban по проекту и пользователю, структурированные теги/события и аналитика по произвольным task-триггерам.

## Цель

Сохранить существующую задачу как самостоятельную сущность и поверх неё построить расширяемый слой:

- задача может существовать без проекта;
- задача может быть добавлена в один или несколько проектов и исключена из любого проекта без удаления самой задачи;
- проекты создаются и редактируются независимо от задач;
- нормализованные теги становятся полноценным измерением, а не одним текстовым полем;
- structured task events становятся источником для будущей аналитики;
- Kanban и аналитические views используют тот же canonical task/project query layer, а не отдельные копии данных;
- UI должен развиваться в стилистике Iguana: компактные surfaces, muted borders, текущие theme tokens и минимум декоративного шума.

## Декомпозиция

### Phase A — domain foundation

- `projects`;
- `task_project_memberships`;
- `tags` + `task_tags`;
- `task_events`;
- backfill существующего `tasks.tag` в normalized tag domain;
- Project API;
- backward-compatible Task API integration;
- structured events для create/update/tag/project/comment;
- PostgreSQL readiness probes;
- SQLite/MySQL migration counterparts только как compatibility source chain, без возврата к multi-SQLite production topology.

### Phase B — Tasks / Projects workspace UI

- `/projects` catalog и project workspace;
- единый `/tasks` workspace с `Список | Доска | Аналитика`;
- scope `Все задачи | Мои задачи | Проект`;
- project selector и multi-tag editor;
- task side-sheet вместо тяжёлой административной modal-xl;
- компактный list layout и column preferences.

### Phase C — Kanban

- project board;
- personal board по задачам authenticated user;
- editable columns/order;
- drag/drop placement;
- разделение canonical task status и board placement;
- per-user board preferences;
- позднее расширение WIP limits / alternate grouping без смены базовой task model.

### Phase D — Analytics

- query/filter layer по project/tag/status/assignee/dates/source/events;
- task-event metrics: lead time, cycle time, time-in-status, throughput, overdue, reopen и workload;
- сохранённые analytical views;
- экспорт результатов.

## Foundation R1 contract

Первый implementation slice сознательно не меняет UI и не исполняет DB migration в runtime.

Он добавляет schema/source contract для Phase A:

- `projects` с code/name/status/lead/archive metadata;
- many-to-many `task_project_memberships`;
- normalized `tags` + `task_tags`, сохраняя `tasks.tag` как временное compatibility-поле;
- structured `task_events`;
- Project REST API;
- Task API принимает optional `tags` и `project_ids`, при этом старый `tag` остаётся совместимым;
- existing Task details получают `tags`, `projects`, `events`;
- `PanelTaskService` создаёт structured event/tag data и для backend-generated tasks;
- bot-side JDBC compatibility schema не расширяется ownership-логикой новой модели;
- PostgreSQL readiness verifier проверяет новый canonical planning schema.

## Критерии готовности Phase A

- existing task без project остаётся валидной;
- project создаётся через backend API и получает стабильный `PRJ_<id>` key при отсутствии явного code;
- одна task может иметь несколько project memberships;
- удаление membership не удаляет task;
- old single `tasks.tag` не ломает текущий UI и backfill-ится в normalized tag relation;
- новая/обновлённая task пишет structured events;
- comment create пишет `COMMENT_ADDED` event;
- production readiness fail-fast проверяет `projects`, `task_project_memberships`, `tags`, `task_tags`, `task_events`;
- no runtime DB mutation выполняется apply/validation runner-ом;
- targeted compile/tests проходят в isolated workspace.

## UI direction для следующих фаз

Референсные паттерны: Linear, ClickUp, Plane, YouTrack. Не копировать их визуально; использовать только interaction patterns:

- compact switchable views;
- quick property editing;
- saved filters/views;
- configurable Kanban;
- project/personal scopes;
- task side-sheet.

Визуальный контракт остаётся Iguana: существующая типографика, theme tokens, surfaces, muted borders, плотный информационный layout, theme-aware states.
