# Задача [01-204]

## Короткое описание

Подключить alerting и escalation policy для critical состояний credential rotation registry.

## Цель

Сделать critical-состояния в registry ротации секретов не только видимыми на analytics page, но и операционно значимыми:

- автоматически поднимать incident по каждой проблемной credential записи;
- доставлять alert через уже существующий incident routing contour;
- эскалировать такие incident-ы по общему incident ops lifecycle;
- показывать операторам связь между записью registry и активным incident-ом.

## Контекст

- В `01-202` уже появился persisted credential rotation registry со scheduler-ом, history и статусами `warning` / `critical`.
- Сейчас registry пересчитывает состояние, но не создаёт proactive alert signal: оператор увидит проблему только если откроет страницу аналитики.
- В проекте уже есть готовый incident lifecycle:
  - `IncidentService.openOrRefreshSignalIncident(...)`;
  - `IncidentService.resolveSignalIncident(...)`;
  - durable route delivery через incident outbox;
  - автоматическая эскалация в `IncidentOpsEscalationService`.
- Для `01-204` правильнее встроиться в existing signal-incident contour, чем делать отдельный параллельный alerting pipeline.
- Critical registry состояния уже определены в `CredentialRotationRegistryService`: `missing_secret`, `source_removed`, `expired`, `rotation_overdue`, а также near-expiry / near-rotation окна на критическом горизонте.

## Что сделать

- Привязать credential rotation registry к signal incidents с `signal_type = credential_rotation`.
- Во время scheduler/manual refresh:
  - автоматически `open/refresh` incident для каждой записи registry со статусом уровня `critical`;
  - автоматически `resolve` incident, если запись перестала быть critical.
- Передавать в incident payload нормализованные детали причины:
  - `entry_key`, `display_name`, `integration_kind`, `credential_kind`;
  - `status_level`, `last_status`, `status_reason`;
  - даты `expires_at`, `rotated_at`, `next_rotation_due_at`;
  - owner/source metadata без раскрытия секретов.
- Расширить API и analytics page registry данными о связанных incident-ах и alerting summary.
- Явно зафиксировать в task detail и коде, что escalation path для этих alert-ов идёт через общий incident critical policy и incident ops controls.

## Ограничения и допущения

- Raw secret values по-прежнему нельзя хранить или включать в incident payload.
- Не нужно создавать отдельную, изолированную систему alerting вне `IncidentService`.
- Если active incident по `signal_type/signal_key` уже есть, нужно refresh-ить его, а не плодить дубликаты.
- Если запись опускается с `critical` до `warning` или `ok`, связанный signal incident должен автоматически переходить в `resolved`.

## Критерии готовности

- После scheduler/manual refresh critical credential rotation entry автоматически получает active signal incident.
- При снятии critical состояния incident автоматически резолвится.
- Incident routing/outbox получает события открытия, обновления и резолва без раскрытия секретов.
- На analytics page registry видны связанные incident-ы и operator-facing alert context.
- Изменения покрыты целевыми тестами на incident lifecycle и API payload.
