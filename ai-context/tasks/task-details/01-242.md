# Задача [01-242] Устранить дубли входящих событий, диалогов и системных сообщений Telegram/MAX

## Цель

Исключить повторную обработку одного входящего события и повторную отправку системных сообщений во всех dynamic bot runtime.

## Контекст

- В production одновременно работали `bot-runner` и вручную запущенный legacy Compose service `bot-telegram`; лишний контейнер остановлен как немедленная мера.
- Telegram повторяет запрос выбора бизнеса и вопрос о прошлых значениях, а затем отправляет ложный timeout после положительного ответа.
- MAX создаёт два диалога на одно обращение и отображает media как два сообщения.

## Что сделать

- Найти все входные пути Telegram и MAX, определить ключи исходного provider event и места создания dialog/message.
- Сделать обработку входного события атомарно идемпотентной на уровне PostgreSQL: один provider event создаёт не более одного dialog, message и transition сценария.
- Устранить повторную отправку prompt, timeout и feedback/system reply при уже подтверждённом состоянии.
- Убрать возможность запуска legacy static bot services совместно с `bot-runner` из production-compose и документации запуска.

## Критерии готовности

- На каждый активный канал есть один runtime owner.
- Один входящий Telegram/MAX update создаёт один dialog и одно media/message в истории.
- Вопросы сценария и timeout не отправляются повторно после подтверждённого ответа.
- Регрессионные тесты покрывают duplicate provider update и повторный system transition.
