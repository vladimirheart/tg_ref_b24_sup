# Задача [01-228] Завершить контролируемый перенос legacy SQLite данных в PostgreSQL и закрыть runtime-доступ к исходным БД

## Короткое описание

Довести фактический перенос исторических SQLite данных до проверяемого результата: мигратор должен получать только read-only staging-копии, фиксировать evidence в PostgreSQL, а production runtime не должен видеть исходные SQLite-файлы.

## Цель

Закрыть реальный migration gap: текущий `db-migrate` не видит корневой `panel_runtime.db`, поэтому critical recovery пропускает сообщения, историю диалогов, уведомления, web-form sessions и metadata вложений. После выполнения PostgreSQL становится единственным runtime source of truth, а SQLite остаётся только архивным import source.

## Контекст

- Логи `db-migrate` от 2026-09-01 подтверждают: `Critical legacy recovery skipped: panel_runtime.db was not found`.
- В корне репозитория есть `panel_runtime.db` и secondary SQLite-файлы; в `bot_databases` есть изменившиеся после предыдущей консолидации `bot-1.db` и `bot-3.db`.
- `panel-web` и `ops-worker` не должны получать mount legacy DB.
- Автоматический re-import изменившихся shard-файлов запрещён до отдельной сверки, чтобы не получить дубли.

## Что сделать

- Добавить отдельный read-only staging mount только для `db-migrate`.
- Добавить PowerShell/Bash helper для подготовки staging-копий SQLite с SHA-256 manifest и запретом перезаписи работающего source.
- Добавить verification helper, который сверяет source table counts с canonical PostgreSQL, import/recovery ledgers и выявляет изменившиеся bot shards.
- Документировать безопасную последовательность: stage, migrate, verify, выключение auto-import, архивирование source.
- Не менять `.env` пользователя автоматически и не удалять SQLite-файлы.

## Критерии готовности

- `db-migrate` получает `panel_runtime.db` и secondary sources только из read-only staging-каталога.
- Post-migration verification даёт машиночитаемый отчёт и non-zero при незакрытых critical table mismatch.
- `panel-web` и `ops-worker` не имеют `legacy-sqlite` mount.
- В документации есть безопасный cutover и rollback до удаления источников.

## Фактический результат 2026-09-01

- SQLite-источники скопированы в `.tmp/legacy-sqlite-import` с SHA-256 manifest; исходные файлы не изменялись.
- Одноразовый `db-migrate` завершился с кодом `0`: generic import перенёс 7 545 строк, critical recovery добавил 650 строк и записал шесть recovery ledger entries.
- Проверка подтвердила покрытие PostgreSQL: `messages` 33/21, `chat_history` 462/250, `notifications` 689/689, `web_form_sessions` 1/1 и `chat_attachment_metadata` 73/17 (PostgreSQL/SQLite).
- `panel-web` и `ops-worker` не получают mount с legacy SQLite; live runtime healthy.
- В пользовательском `.env` auto-import сохранён без изменений по ограничению задачи. После ручной приёмки пользователь должен установить `IGUANA_LEGACY_SQLITE_AUTO_IMPORT=false` и перезапустить контур по runbook.

## Обязательные дополнительные условия

- Не выполнять destructive operations над SQLite-источниками или PostgreSQL данными.
- После завершения показать alert через `./ai-context/baseline/scripts/show-completion-alert.sh`.
- В финальном ответе подготовить `Резюме для коммита`.
- После file changes создать отдельный changelog в `ai-context/changelog` с пользовательским промптом.
