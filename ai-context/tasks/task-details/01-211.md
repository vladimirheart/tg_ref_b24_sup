# Задача [01-211]

## Короткое описание

Разделить `spring-panel` на scale-ready deployment roles `panel-web` и `ops-worker` из одного codebase/image, сохранив единый backend-owned business boundary. Не распиливать проект на сетевые микросервисы без эксплуатационной причины, но подготовить устойчивые seams для будущих `media`, `notifications`, identity/IdP и integration services.

## Цель

Перевести production Docker contour от модели, где один `spring-panel` одновременно обслуживает HTTP/UI и выполняет весь background workload, к явным ролям:

- `panel-web` — UI, REST/API, auth/session и operator-facing workload;
- `ops-worker` — backend-owned schedulers, monitoring, sync, housekeeping, inbox/outbox и delivery jobs;
- `db-migrate` или эквивалентный single-owner migration path — единственный владелец startup migrations в multi-instance deployment.

Целевой эффект: web role можно масштабировать независимо от background workload, worker можно перезапускать независимо от UI, а дальнейшее выделение сервисов не потребует пересмотра ownership business data.

## Контекст

- `01-183` закрепила PostgreSQL/RabbitMQ/Redis/object-storage production contour и требование multi-backend/multi-worker readiness.
- `01-208` добавила Docker contour с `spring-panel`, PostgreSQL, RabbitMQ, Redis, MinIO, отдельными `bot-*` и optional nginx edge.
- В `spring-panel` остаётся много фоновых задач: monitoring, credential rotation, NetBox/iiko sync, housekeeping, provider checks, SSL/SMTP checks, knowledge sync и другие.
- Масштабирование текущего единого `spring-panel` масштабирует HTTP и schedulers одновременно, что повышает риск duplicate jobs, лишней конкуренции и влияния долгих integrations на latency UI.
- `ops-worker` остаётся deployment role canonical backend и может использовать backend PostgreSQL repositories. Запрет прямого business DB ownership относится к transport/integration workers (`bot-*`, внешние adapters).

## Архитектурный target

```text
Internet
   |
   v
nginx / edge
   |
   v
panel-web x N
   |
   +------ PostgreSQL
   +------ Redis
   +------ RabbitMQ
   +------ MinIO/S3
             ^
             |
        ops-worker x M

bot-telegram / bot-vk / bot-max
             |
             +------ RabbitMQ / internal API

db-migrate (one-shot / single owner)
```

## Архитектурные инварианты

1. `panel-web` не выполняет operational schedulers/background loops.
2. `ops-worker` не принимает публичный пользовательский traffic.
3. Web и worker пока используют один codebase/image: role split — deployment boundary, не преждевременный microservice split.
4. Business schema/data остаются backend-owned.
5. `bot-*` и будущие adapters не получают прямой JDBC ownership business PostgreSQL.
6. `ops-worker x N` разрешён только для workload с доказанным lease/claim/idempotency contract.
7. Unsafe job работает single-worker до hardening.
8. Startup migrations имеют одного явного владельца.
9. Runtime role задаётся env/property contract, а не hostname/process-name эвристикой.
10. Local/dev compatibility может использовать `all`; production compose обязан использовать явные roles.
11. Будущие сервисы отделяются через API/queue/storage boundaries, а не через shared database ownership.

## Что сделать

### Phase A — runtime-role foundation и inventory

- Ввести явный contract `APP_RUNTIME_ROLE=all|web|worker` и migration-owner contract.
- Добавить startup diagnostics: выбранная role, instance id, включённые workload groups.
- Провести inventory всех `@Scheduled`, long-running watchers, startup runners, inbox/outbox consumers, monitoring/sync/housekeeping/delivery jobs.
- Для каждого workload зафиксировать owner role, concurrency model, lease/claim/idempotency protection, допустимый replica count и retry/failure semantics.
- Добавить guard/test, чтобы новый scheduler нельзя было тихо добавить без role classification.

### Phase B — `panel-web`

- Оставить MVC/UI, REST/API, Spring Security/auth/session и synchronous operator-facing domain operations.
- Отключить operational background execution.
- Проверить `panel-web x 2+` без дублирования background side effects.
- Удерживать web максимально stateless: PostgreSQL/Redis/RabbitMQ/S3 — shared state boundaries.

### Phase C — `ops-worker`

- Запускать из того же image/codebase.
- Перенести execution ownership backend background workloads в worker role.
- Не публиковать worker наружу; management endpoint — только internal при необходимости.
- Разделить workloads на `multi-replica-safe` и `single-replica-until-hardened`.
- Для unsafe jobs сделать явный fail-fast/replica guard, а не только документационное ограничение.

### Phase D — migration ownership

- Убрать зависимость migration/bootstrap от того, какой web/worker container стартовал первым.
- Предпочтительный target: one-shot `db-migrate` из того же application artifact/image.
- Если отдельный migrate role технически неоправдан, реализовать другой проверяемый single-owner guard и документировать выбор.
- Дополнительные web/worker replicas не должны конкурировать за schema bootstrap.

### Phase E — Docker scale-ready topology

- Перевести `docker-compose.production-contour.yml` с единого `spring-panel` responsibility на `panel-web` + `ops-worker`.
- Направить nginx/public traffic только на web role.
- Перевести bot internal API target на стабильный backend/web service alias.
- Не публиковать worker ports наружу.
- Проверить `container_name`: убрать hardcoded names там, где они мешают `docker compose --scale`.
- Не использовать host bind ports для service discovery внутри compose network.
- Обновить production up/down helper scripts и env docs.
- Не ломать local/dev Windows startup.

### Phase F — observability contract

Полный Prometheus/Grafana/Loki rollout оформить отдельной задачей, но 01-211 должна подготовить:

- role/instance labels;
- readiness/liveness;
- metrics separation `panel-web` / `ops-worker`;
- production readiness для обязательного worker;
- runbook по replica count, lease-safe jobs и диагностике duplicate/stuck work.

### Phase G — задел на будущие сервисы

#### Media

Не создавать `FileService` как HTTP-прокси перед MinIO. Будущий `media-service` оправдан, когда появятся самостоятельные обязанности: upload authorization, presigned URLs, MIME/size validation, antivirus, thumbnails/transcoding, retention, quotas, dedup/content hash, media metadata.

#### Notifications

Выделять notification worker/service после стабилизации event contract, retry/dead-letter semantics и появления реальной потребности независимого масштабирования.

#### Identity

Не писать собственный `AuthService` в этой задаче. При SSO/MFA/multiple frontends/public API/federation рассматривать внешний OIDC IdP (`Keycloak`, `Authentik` или корпоративный provider), сохраняя в Iguana business RBAC/permissions/operator profile.

#### Integrations

Любой будущий adapter/service не владеет business PostgreSQL, работает через queue/API и получает отдельный lifecycle только при реальной scale/failure/security boundary.

## Scale smoke / проверки

1. `APP_RUNTIME_ROLE=web`: UI/API работают, schedulers не активируются.
2. `APP_RUNTIME_ROLE=worker`: background jobs активируются, public UI role отсутствует.
3. `APP_RUNTIME_ROLE=all`: local/dev compatibility сохраняется.
4. Два `panel-web`: оба healthy, фоновые jobs не дублируются.
5. Restart worker не делает operator UI недоступным.
6. Restart одного web replica не останавливает background processing.
7. `worker x N` разрешён только для lease/claim-safe workloads без duplicate side effects.
8. Fresh PostgreSQL bootstrap имеет одного migration owner.
9. `bot-*` продолжают использовать RabbitMQ/internal API и не получают business DB credentials.
10. nginx направляет public traffic только на web role.
11. Existing local Windows/dev startup не ломается.

## Критерии готовности

- Production compose содержит отдельные `panel-web` и `ops-worker` roles.
- Оба role используют один image/codebase либо отдельно обоснованное эквивалентное решение.
- `panel-web` не выполняет operational schedulers.
- Все background workloads классифицированы по owner role и replica policy.
- Multi-replica workload имеет lease/claim/idempotency protection.
- Startup migrations имеют одного владельца.
- Минимум два web replicas работают без duplicate background side effects.
- Worker и web можно перезапускать независимо.
- `bot-*` не получают business DB ownership.
- nginx не маршрутизирует public traffic на worker.
- Role отражается в logs/health/metrics.
- Compose/helper scripts/runbooks/env docs обновлены.
- Есть targeted tests на role activation и scheduler isolation.
- Выполнен реальный Docker smoke `panel-web + ops-worker + postgres + redis + rabbitmq + minio`.
- После AI implementation статус только `🟣`; `🟢` — после ручной проверки пользователем.

## Не входит в первый implementation scope

- Multi-region.

## Риски

- Background loops могут существовать без `@Scheduled`; нужен inventory runners/watchers.
- Некоторые jobs могут иметь только instance-local protection.
- Flyway/bootstrap может запускаться в каждом role.
- `container_name` может блокировать `docker compose --scale`.
- Internal bot API сейчас может быть связан с service name `spring-panel`.
- Worker workload может зависеть от servlet/web beans.
- Нельзя ломать local/dev Windows path ради production Docker contour.

## Update 2026-08-26 09:05:00 — Phase A implementation started

Первый implementation slice 01-211 переведён из архитектурной постановки в runtime foundation:

- добавляется явный `APP_RUNTIME_ROLE=all|web|worker` с alias `panel-web` / `ops-worker`;
- вводится source-level `@RuntimeWorkload` classification для `@Scheduled` и panel-side `@RabbitListener` entry points;
- каждый workload получает replica policy: `PROCESS_LOCAL`, `LEASED`, `BROKER_COMPETING_CONSUMER` или консервативный `SINGLETON`;
- SSE heartbeat отделяется от shared `UiEventStreamService`, чтобы сам event service мог оставаться dependency backend worker-логики без запуска heartbeat в worker role;
- startup diagnostics и `/actuator/info` показывают runtime role, instance id и enabled workloads;
- common metrics получают `runtime_role` и `instance_id` tags;
- source-contract test запрещает добавлять новый `@Scheduled` / panel `@RabbitListener` без явной role/replica classification;
- создан runtime inventory/runbook с blocking items перед реальным compose split.

Осознанно не переключаем production compose в этом slice. Найден архитектурный blocker: `UiEventStreamService` хранит SSE emitters в памяти процесса, поэтому worker-owned events перед split требуют distributed fanout к web replicas. Также отдельным следующим slice остаются startup runners/Flyway migration ownership и hardening `SINGLETON` workloads.

Статус задачи остаётся `🟡`: это foundation, а не завершение 01-211.

## Update 2026-08-26 10:22:00 — Phase B distributed UI fanout + startup/migration ownership

Phase B закрывает два blocker перед реальным compose split:

- UI realtime больше не должен зависеть от process-local SSE publisher:
  - backend publishers формируют versioned-ish event envelope и публикуют через Redis pub/sub;
  - каждый `panel-web` подписывается на общий Redis channel и доставляет событие только своим локальным SSE emitters;
  - targeted user events публикуются в тот же fanout и фильтруются локально по identity;
  - `all` сохраняет AUTO/local fallback для dev compatibility;
  - `web`/`worker` fail-fast требуют `APP_UI_EVENT_FANOUT_MODE=redis`, чтобы split deployment не мог тихо потерять worker -> web realtime.
- runtime contract расширен ролью `migrate/db-migrate`.
- Flyway migration strategy выполняет schema normalization/migrate только в `all` или `migrator`; `web` и `worker` больше не являются владельцами schema migration.
- startup `ApplicationRunner`-мутации классифицированы:
  - legacy import/recovery/seed/repair -> `MIGRATOR`;
  - SQLite compatibility bootstrap -> compatibility-only (`roles = {}`);
  - normal scheduled runner, уже worker-classified, сохраняет worker ownership.
- `SecurityBootstrap` становится migrator-owned, а legacy local process health check остаётся compatibility-only.
- добавлен optional `APP_RUNTIME_EXIT_AFTER_MIGRATION=true` для будущего one-shot `db-migrate` container.
- создан source-contract test для startup ownership и отдельный YAML parse test.
- исправлен найденный Phase A дефект: `management.metrics.tags.instance_id` больше не склеен с `distribution:`.

Статус остаётся 🟡. Перед compose split ещё требуется:
- audit/hardening side-effecting `@PostConstruct` startup hooks;
- решить оставшиеся `SINGLETON` worker workloads;
- затем переключить production compose на `db-migrate -> panel-web + ops-worker`.
