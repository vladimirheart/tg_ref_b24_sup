# Задача [01-275]

## Краткое описание

Закрыть три небольших эксплуатационных хвоста после 01-274: уплотнить верх и account bubble sidebar, восстановить автоматическую загрузку аватаров клиентов MAX и дать настройку проекта для задач, создаваемых при автозакрытии диалогов по неактивности.

## Scope

### S1 — Sidebar density

- уменьшить верхний внутренний отступ header bubble рядом с логотипом;
- сделать account/footer bubble компактнее без изменения поведения account menu;
- сохранить текущие theme tokens и responsive/collapsed режимы.

### S2 — MAX client avatars

- получать профиль клиента MAX по dialog `chat_id` через официальный MAX API;
- сохранять `avatar_url` / `full_avatar_url` в canonical `avatars/` object-storage domain;
- не блокировать critical inbound-message path сетевым avatar refresh;
- ограничить частоту refresh и сохранять provider evidence в `client_avatar_history`;
- не менять работающий Telegram avatar path.

### S3 — Auto-close follow-up project routing

- существующий follow-up task при inactivity auto-close сохраняет текущего ответственного диалога как assignee;
- приглашённые участники диалога остаются co-executors;
- добавить nullable настройку `auto_close_config.follow_up_project_id`;
- выбранный активный project добавляется как canonical `task_project_membership`;
- отсутствие настройки сохраняет прежнее поведение без project;
- если ранее выбранный project удалён/архивирован, auto-close и создание задачи не должны ломаться: задача создаётся без project, а runtime пишет warning.

## S1 implementation — 2026-09-25

- Sidebar header/account surfaces уплотняются только SCSS-источником.
- `/settings` → Channels → Automation получает selector проекта для inactivity follow-up tasks.
- Settings controller публикует только неархивированные проекты.
- `AutoCloseConfigNormalizer` канонизирует `follow_up_project_id` как positive Long или удаляет invalid значение.
- `DialogAutoCloseSchedulerService` передаёт тот же settings snapshot, которым был выбран auto-close template, в follow-up task service.
- `PanelTaskService` получает optional `projectIds` и пишет membership через существующий `TaskDomainFoundationService.recordSaved`, без нового DB schema.
- S2 MAX avatars остаётся следующим независимым slice.

## S2 implementation - 2026-09-25

<!-- 01-275_S2_MAX_CLIENT_AVATARS_R4_2026-09-25 -->

- MAX message.sender remains a plain User and is not treated as an avatar source.
- For accepted inbound messages the MAX runtime schedules a non-blocking profile refresh by recipient chat_id.
- The profile is loaded from GET /chats/{chatId} and only dialog_with_user.avatar_url/full_avatar_url are accepted.
- Avatar downloads reuse the existing trusted MAX CDN perimeter and have a dedicated 8 MiB bound.
- Canonical runtime names are <userId>.<ext> and <userId>_full.<ext> in the avatars object-storage domain; stale extension variants are removed only after a successful replacement write.
- client_avatar_history stores provider evidence and a content fingerprint; no raw signed CDN URL is persisted.
- Refresh runs on a bounded daemon executor with a one-hour success TTL and five-minute retry backoff, so inbound message processing does not wait on profile/image network calls.
- No DB migration is required. Telegram avatar behavior is unchanged.
