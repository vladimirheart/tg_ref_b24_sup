# Задача [01-238] Устранить стартовые timeout внутреннего channel API для MAX и включить фактические retry

## Цель

Сделать обращение runtime-ботов к internal panel channel API устойчивым к краткой задержке панели после restart, не допуская ERROR в фоновых MAX-задачах.

## Контекст

- После controlled rollout `bot-runner` успешно запустил MAX, но первый scheduled вызов `POST /internal/api/bot/channels/resolve` превысил текущий timeout `5s`.
- Сеть и readiness панели доступны из `bot-runner`; проблема относится к кратковременной задержке internal API.
- В `IntegrationPanelApiProperties` есть `retry-attempts` и `retry-backoff`, но `PanelChannelClient` пока не использует их при `HttpClient.send`.

## Что сделать

- Реализовать bounded retry для временных transport timeout и 5xx в `PanelChannelClient` с существующими параметрами retry/backoff.
- Сделать MAX cleanup scheduler безопасным при исчерпании retry: предупреждение без ERROR и без остановки следующих циклов.
- Добавить unit tests retry-политики и ошибки scheduler.
- Пересобрать bot JAR и выполнить restart только `bot-runner`; проверить отсутствие новых MAX ERROR.

## Критерии готовности

- Кратковременная задержка `panel-web` не ломает MAX scheduled cleanup.
- В логах MAX после restart отсутствует `Unexpected error occurred in scheduled task` для channel resolve.
- Retry ограничен конфигурацией, не бесконечен и не публикует секреты.

## Выполнение

- `PanelChannelClient` использует `retry-attempts` и `retry-backoff` для `IOException` и HTTP `5xx`; повторные write-запросы сохраняют один idempotency key.
- MAX silent-session cleanup перехватывает временную недоступность channel resolution, записывает `WARN` и пропускает только текущий цикл.
- Локально пройдено `mvnw.cmd -pl bot-max -am -Dtest=ChannelServiceTest -Dsurefire.failIfNoSpecifiedTests=false test`: 5 tests, 0 failures.
- Docker rebuild `iguana-panel:local` запущен в фоне, но BuildKit/Maven пока не завершил stage bot-builder; работающий `bot-runner` не перезапускался.
- Сборка завершена успешно; `bot-runner` пересоздан и healthy.
- Новый runner последовательно запустил Telegram channels `1` и `3`, MAX channel `2`; в Redis восстановлены три ingress lease.
- В свежем MAX process log после первого scheduled интервала нет `Unexpected error occurred in scheduled task`, ошибок channel resolve или SQLite JDBC.
