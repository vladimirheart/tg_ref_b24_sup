# Задача [01-216] — ВНЕДРИТЬ БЕЗОПАСНЫЙ FIRST-RUN BOOTSTRAP PRODUCTION-СЕКРЕТОВ И МИГРАЦИЮ СУЩЕСТВУЮЩИХ PERSISTENT VOLUMES

## Короткое описание

Сделать единый безопасный bootstrap production-секретов перед первым `docker compose up` и отдельный migration-path для уже существующих persistent volumes.

## Почему задача нужна

Во время E2E задачи `01-213` production launcher обнаружил отсутствие `.env`.

Текущий `-AllowInsecureDefaults` нужен только для локального compatibility/E2E запуска и после `01-213` materialize-ит документированные небезопасные defaults только в process environment. Он намеренно:
- не создаёт `.env`;
- не генерирует production secrets;
- не ротирует persisted credentials;
- не является production bootstrap.

Production first-run сейчас требует ручного заполнения большого набора переменных и не различает fresh install и существующий стенд.

## Цель

Получить один управляемый first-run/migration workflow, который безопасно создаёт или переносит production secrets, не запекает их в image/Git и не ломает существующие persistent volumes.

## Что сделать

### Fresh install

- До первого `compose up` определить, что production volumes ещё не инициализированы.
- Создать ignored `.env` атомарно.
- Сгенерировать криптографически случайные значения как минимум для:
  - `IGUANA_POSTGRES_PASSWORD`;
  - `IGUANA_RABBITMQ_PASSWORD`;
  - `IGUANA_REDIS_PASSWORD`;
  - `APP_STORAGE_OBJECT_ACCESS_KEY`;
  - `APP_STORAGE_OBJECT_SECRET_KEY`;
  - `APP_INTERNAL_BOT_API_TOKEN`;
  - `APP_SECURITY_REMEMBER_ME_KEY`;
  - `MONITORING_CREDENTIALS_MASTER_KEY`;
  - `IGUANA_GRAFANA_ADMIN_PASSWORD`.
- Не печатать секретные значения в stdout/log/changelog.
- Не передавать secrets через Docker build args и не сохранять их в image history.

### Existing install / migration

- До изменения `.env` определить существующие PostgreSQL/RabbitMQ/MinIO/Grafana volumes.
- Никогда не генерировать новые credentials поверх существующего volume без явной migration procedure.
- PostgreSQL: сначала безопасно изменить persisted role password, проверить новое подключение, затем атомарно обновить `.env`.
- RabbitMQ: синхронизировать persisted user credentials без потери definitions/queues.
- Redis: учесть, что пароль задаётся runtime-конфигурацией, и обеспечить согласованное переключение клиентов.
- MinIO: проверить semantics существующих root credentials и не потерять доступ к данным.
- Grafana: учесть persisted Grafana DB и корректный admin-password reset/migration.
- `MONITORING_CREDENTIALS_MASTER_KEY`: сохранить совместимость с `config/shared/monitoring-credentials.key` через существующий `base64:` bridge, чтобы старые `enc:v1:` credentials продолжили расшифровываться.
- Предусмотреть rollback при частично неуспешной ротации.

### UX / lifecycle

- Один явный bootstrap/helper для Windows и Bash parity.
- Dry-run/status режим: fresh / existing / migration-required / ready.
- Повторный запуск должен быть идемпотентным.
- `docker-production-up.*` должен вызывать bootstrap только в безопасно определённом состоянии.
- Пользователь не должен получать цепочку ошибок «не хватает следующего пароля».

## Критерии готовности

- Fresh checkout без `.env` проходит secure first-run и получает production-ready ignored secrets.
- Ни один секрет не попадает в Git, Dockerfile/image history или changelog.
- Existing volumes мигрируются без потери данных и без рассинхронизации `.env`/persisted credential.
- Legacy monitoring credentials после migration успешно расшифровываются.
- Есть automated fresh-install smoke и existing-volume migration smoke.
- Есть recovery/rollback runbook.
- После AI implementation статус максимум `🟣`; `🟢` — только после ручной проверки пользователя.
