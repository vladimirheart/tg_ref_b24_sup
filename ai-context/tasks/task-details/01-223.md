# Задача [01-223] Реализовать component-specific apply/rotation workflow для persisted credentials поверх existing volumes

## Краткое описание

`01-222` уже дал безопасный status/dry-run слой и классификацию existing contour, но
сам apply-path ротации по компонентам ещё не реализован. Нужен отдельный workflow,
который будет менять persisted credentials управляемо и с rollback.

## Почему это важно

- status helper уже умеет показать `migration_required`, но сам по себе не лечит
  drift;
- blind `.env` rewrite по-прежнему опасен для PostgreSQL, RabbitMQ, Redis,
  MinIO и Grafana;
- production contour требует repeatable apply-path, а не ручной ad-hoc набор команд.

## Что нужно сделать

1. Добавить component-specific apply steps для:
   - PostgreSQL role password rotation;
   - RabbitMQ user password sync;
   - Redis coordinated password switch;
   - MinIO runtime credential reconciliation;
   - Grafana admin reset/rotation.
2. Для каждого шага предусмотреть:
   - preflight status check;
   - backup/rollback checkpoint;
   - live verification после изменения;
   - атомарное обновление `.env` только после успешной верификации.
3. Подготовить smoke и runbook на случай частичного неуспеха.

## Критерии готовности

- Каждый компонент имеет repeatable apply path.
- `.env` обновляется только после успешной live verification.
- Есть rollback instructions и post-change smoke.
- В production contour credential drift можно закрыть без ручного угадывания.

## Связанные задачи

- `01-222` — status/dry-run helper и классификация existing contour
- `01-216` — secure bootstrap / persistent volume migration envelope
- `01-224` — coordinated Redis/MinIO persisted credential migration and restart choreography

## Update 2026-08-31 - Windows-first apply slice for PostgreSQL and RabbitMQ

- Добавлен `scripts/docker-production-credential-migration-apply.ps1`.
- Текущий automation scope намеренно ограничен компонентами:
  - `postgresql`;
  - `rabbitmq`.
- Script по умолчанию работает как dry-run и делает реальные изменения только с
  явным `-Apply`.
- Для обоих компонентов реализованы:
  - live discovery текущего рабочего credential-кандидата через safe auth probe;
  - генерация нового секрета без вывода в stdout;
  - rollback checkpoint `.env.credential-migration-<component>-<timestamp>.bak`;
  - live credential update;
  - повторная auth verification;
  - обновление `.env` только после успешной live verification;
  - recreate зависимых сервисов и readiness wait;
  - best-effort rollback live credential и `.env` при сбое.
- Документирован отдельный runbook `docs/runbooks/persisted-credential-rotation-apply.md`.
