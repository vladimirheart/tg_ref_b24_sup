# Задача [01-153]

## Короткое описание

Добавить для каждого бота настройку очереди обращений с назначением на операторов или отделы оргструктуры.

## Цель

Сделать на уровне конкретного бота управляемую маршрутизацию новых обращений: кто получает очередь, кому можно сразу назначать ответственного и как это масштабируется от одного оператора до пула и отдела без ручных правок в коде.

## Контекст

- В проекте уже есть per-channel `questions_cfg`, через который сохраняются операторские настройки канала, уведомления панели и прочие runtime-параметры.
- Новые обращения и входящие клиентские сообщения сейчас проходят через `DialogRealtimeEventService` и `AlertQueueService`, но ответственный по диалогу назначается в основном вручную или при первом ответе оператора.
- В проекте уже существует живая модель операторов:
  - `DialogParticipantService` умеет отдавать список доступных операторов с `department` и `role`;
  - `users.department` уже используется для группировок и маршрутизации;
  - `SharedConfigService.loadOrgStructure()` читает оргструктуру из `config/shared/org_structure.json`.
- Есть готовые паттерны маршрутизации по отделу и списку сотрудников в channel-level notification settings, а также готовые стратегии распределения нагрузки в SLA auto-assign (`round_robin`, `least_loaded`, `hash_by_ticket`).
- Пользовательский запрос требует не просто уведомлений, а именно настройки очереди обращений “со всеми вытекающими действиями”, то есть с заделом на:
  - маршрутизацию новых обращений;
  - выбор ответственного по правилам;
  - переиспользование того же конфига для будущих workflow.

## Что сделать

- Расширить per-channel contract новым блоком `assignmentRouting` в `questions_cfg` с нормализацией и безопасными значениями по умолчанию.
- Поддержать как минимум режимы:
  - `disabled`;
  - `single_operator`;
  - `operator_pool`;
  - `department_queue`.
- Для пулов и отделов поддержать стратегию выбора ответственного без архитектурного тупика:
  - `round_robin`;
  - `least_loaded`;
  - `hash_by_ticket`.
- Реализовать backend-сервис, который:
  - разрешает получателей очереди для нового обращения;
  - при необходимости выбирает оператора для авто-назначения;
  - не ломает текущий fallback на `all_operators`, если конфиг пустой или некорректный.
- Встроить новый routing в lifecycle нового обращения так, чтобы на создании диалога можно было:
  - уведомить нужную очередь;
  - сразу назначить ответственного, если режим это предполагает.
- Обновить settings UI карточки канала:
  - добавить отдельный блок настройки очереди обращений;
  - давать выбирать отдел из доступного списка, а не вводить руками;
  - давать выбирать операторов из живого каталога операторов;
  - скрывать/показывать поля по выбранному режиму без визуального шума.
- Прокинуть в `channels` page-data всё, что нужно UI для выбора:
  - список операторов;
  - список отделов / оргструктуры.
- Добавить/обновить unit-тесты на нормализацию и разрешение маршрута.

## Критерии готовности

- В настройках каждого бота есть явный блок очереди обращений, где можно выбрать режим назначения и целевой отдел/операторов без ручного ввода критичных значений.
- Новый блок безопасно сохраняется и читается через `questions_cfg` и не ломает существующие настройки канала.
- При создании нового обращения система умеет использовать bot-level routing:
  - уведомлять нужную очередь;
  - назначать ответственного по выбранному правилу там, где это включено.
- При пустом или выключенном routing поведение остаётся обратно совместимым.
- Есть автоматические проверки минимум на backend-логику выбора маршрута и нормализацию payload.

## Ограничения и риски

- Нельзя жёстко завязываться только на свободный текст отдела: UI должен опираться на живой список и backend должен нормализовать конфиг.
- Нельзя смешивать queue-routing для бота с глобальным notification-routing проекта: bot-level contract должен жить рядом с каналом.
- Не стоит вводить новую БД-сущность, если текущий `questions_cfg` уже подходит как per-channel configuration boundary.
- Нельзя завязывать аналитический/операторский runtime на display label оператора или отдела без нормализованного значения.
