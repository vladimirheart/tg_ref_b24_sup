# Задача 01-313

## Промт пользователя

> http://127.0.0.1:8080/unblock-requests висит один запрос, но:
> а) при попытке одобрить или отклонить, возвращает "Внутренняя ошибка сервера"
> б) в карточке клиента активна кнопка "Заблокировать", т.е. система не видит блокировки.
> значит либо заявка старая и багнутая либо панель некорректно обработала статус.

## Факты диагностики

- Baseline/HEAD/origin_main: `711c0436c0803e39578b3e38e1f45b0ea93ff7d7`.
  Checkout чистый до начала работы. Runtime image —
  `iguana-panel:access-recovery-711c0436c080-20261125-114559`,
  digest `sha256:ccf44e03ab9c3e44914106c52a026fb2e4fcc198f1c99fd29e6bb948c5d1df58`.
- Рабочая схема V104. Заявка №1 от 28.10.2026 остаётся pending;
  blacklist.is_blacklisted=false и unblock_requested=false. Карточка клиента верна.
- Ошибки decision endpoint: integer передаётся в boolean is_blacklisted и
  unblock_requested. Оба решения падают на SQL и откатываются.
- Старый AccessRecoveryPostgresqlTest использовал INTEGER fixture для этих
  полей, поэтому не воспроизводил каноническую PostgreSQL-схему.

## Решение

- Использовать boolean параметры/литералы в UnblockRequestService.
- Перед решением блокировать blacklist, затем повторно читать/блокировать заявку:
  тот же порядок, что при создании /unblock и ручных blacklist actions.
- Если блокировки уже нет, закрывать заявку как expired с понятным комментарием,
  без фиктивного unblocked history event и без сообщения клиенту.
- V105 сохраняет исторические строки и переводит только obsolete pending
  заявки незаблокированных клиентов в expired; активные блокировки не меняются.
- Счётчики внимания и списка используют прежний pending predicate: завершённая
  заявка исключается из ожидающих действий, оставаясь доступной в истории.

## Проверки и готовность

- Изолированные PostgreSQL-тесты: approve/reject на BOOLEAN, stale/no-blacklist,
  rollback, repeated/concurrent decisions, идемпотентность V105 и сохранение
  blocked/processed заявок.
- Регрессии access recovery, permissions, WebMvc, bot runtime blacklist и
  полная Flyway-цепочка до V105.
- После rollout: migrator exit=0, панель healthy, заявка №1 expired,
  pending count=0, клиент остаётся незаблокированным.
- Сохранить rollback image и compose chain; не отправлять тестовые сообщения
  реальному клиенту. Staging/commit/push остаются действиями пользователя.
