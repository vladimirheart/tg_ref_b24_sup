# Задача [01-202]

## Короткое описание

Добавить registry истечения токенов и rotation watch по внешним интеграциям.

## Цель

Собрать в одном monitoring-контуре все ключевые внешние секреты и токены, которые влияют на работу Iguana, чтобы владелец системы и support/ops команда видели:

- какие секреты реально присутствуют в runtime или конфигурации;
- по каким секретам уже заведена metadata ротации;
- какие токены скоро истекают или уже просрочены;
- где metadata ротации ещё не заполнена и остаётся blind spot;
- какие именно интеграции требуют ближайшего действия без раскрытия значений секретов.

## Контекст

- В roadmap мониторинга support-систем уже зафиксирован отдельный контур `secret/token expiry registry` с горизонтами предупреждений `30 / 14 / 7 / expired`.
- Секреты в проекте живут не в одном месте:
  - `shared config` (`bot_credentials.json`, `settings.json`);
  - `channels.platformConfig`;
  - `settings_parameters.extra_json` для per-user automation credentials;
  - `env` / runtime properties.
- Для большинства интеграций фактическая дата expiry сейчас не хранится автоматически, поэтому нужен смешанный подход:
  - автообнаружение источника секрета и факта его наличия;
  - отдельная persisted metadata по rotation/expiry без хранения или показа самого секрета.
- Уже существует monitoring contour с отдельной monitoring DB, custom JDBC repositories, scheduler-ами и analytics pages; новый реестр должен лечь в этот же архитектурный паттерн.

## Что сделать

- Добавить в monitoring DB отдельный registry для credential/token rotation metadata.
- Реализовать discovery по основным источникам секретов:
  - bot credentials `telegram` / `vk` / `max`;
  - webhook/confirmation secrets в provider channel config;
  - NetBox token;
  - Notion token;
  - dialog external auth tokens;
  - internal panel/bot API token и remember-me key;
  - per-user Bitrix24 webhook и iiko API secrets;
  - iikoServer source secrets для sync-контура.
- Для каждой найденной записи хранить и показывать только metadata:
  - integration kind;
  - credential kind;
  - display name / source reference;
  - факт наличия секрета;
  - `expires_at`, `rotated_at`, `rotation_interval_days`, owner/note;
  - вычисленный статус и причину.
- Добавить scheduler, который регулярно пересчитывает registry и пишет snapshots в `monitoring_check_history`.
- Добавить analytics page и API для:
  - overview по статусам;
  - списка записей;
  - ручного refresh;
  - ручного обновления metadata rotation/expiry;
  - просмотра history.

## Ограничения и допущения

- Реестр не должен хранить и тем более возвращать raw secret values.
- Если для секрета нельзя автоматически определить expiry, запись всё равно должна попадать в registry со статусом, который показывает отсутствие metadata ротации.
- В этом срезе допустим manual metadata update через UI/API; автоматическая интеграция с внешними secret manager-ами не требуется.
- Там, где источник секрета plural/per-user, registry может содержать несколько записей одного integration kind с разными source keys.

## Критерии готовности

- В monitoring DB есть отдельная таблица registry истечения/ротации секретов.
- После refresh registry автоматически находит основные секреты из runtime/configuration contour без раскрытия значений.
- Страница аналитики показывает overview, список записей, горизонты риска и blind spots по metadata.
- Есть manual update metadata и history по записи.
- Есть scheduler и целевые тесты на status calculation/discovery edge cases.
