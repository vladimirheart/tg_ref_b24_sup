# Задача [01-235] Восстановить core production services и выполнить rollout bot runtime

## Цель

Поднять остановленные PostgreSQL и RabbitMQ, применить собранные изменения `01-231`, `01-232` и `01-234`, затем доказать стабильную работу каждого Telegram token без SQLite JDBC и `409 Conflict`.

## Исходное состояние

- `postgres` и `rabbitmq` в `docker-compose.production-contour.yml` находятся в статусе `Exited (0)`.
- `panel-web` и `ops-worker` запущены, но unhealthy из-за недоступности core dependencies.
- На Windows-хосте нет активных `java.exe` bot runtime и PID-файлов, поэтому исторический конкурент polling уже не подлежит безопасной остановке.

## Шаги

- Проверить причину остановки PostgreSQL/RabbitMQ и поднять только нужные core services в production compose.
- Пересобрать и развернуть актуальные Telegram runtime artifacts и panel image.
- Запустить по одному экземпляру каждого бота штатным lifecycle-путём; не использовать Maven runtime параллельно с Docker profile.
- Проверить bot logs: PostgreSQL datasource, Redis coordination, отсутствие `409 Conflict` и SQLite JDBC.
- Выполнить тестовые text/sticker обращения и проверить читаемый fallback для отсутствующего диалога.

## Критерии готовности

- `postgres`, `rabbitmq`, `panel-web`, `ops-worker` healthy.
- На каждый Telegram token ровно один ingress owner.
- В свежих process logs нет `409 Conflict` и SQLite JDBC.
- Text и sticker проходят end-to-end.
