# Задача [01-201]

## Короткое описание

Ввести unified provider health для `Telegram` / `VK` / `MAX`, чтобы в аналитике было видно единое состояние провайдеров по ingress и outbound delivery без ручного обхода отдельных экранов и runtime-логов.

## Цель

Дать оператору и владельцу системы один экран, где по каждому каналу видно:

- жив ли runtime соответствующего бота;
- проходит ли provider-level auth/connectivity probe;
- есть ли свежий inbound/outbound трафик;
- когда были последние успешные входящие и исходящие сообщения;
- как выглядит краткая timeline-история проверок.

## Контекст

- Production contour уже получил отдельные monitoring-срезы по backup freshness, public ingress и SMTP / incident notification delivery.
- В проекте authoritative source of truth по provider-каналам уже живёт в `channels`; плодить отдельный CRUD-реестр провайдеров не нужно.
- Для прямого операторского reply-path в `spring-panel` сейчас нет полноценного delivery ledger с persisted классификацией `4xx/5xx/429/retry`; поэтому нельзя честно дорисовать такие метрики из уже существующих данных.
- В текущем срезе нужно собрать честный unified health на базе:
  - `Channel`;
  - `BotProcessService`;
  - provider auth / connectivity probes;
  - фактической активности из `chat_history`;
  - `monitoring_check_history` как общего timeline.

## Что сделать

- Добавить backend-сервис unified provider health для активных каналов `telegram` / `vk` / `max`.
- Использовать `channels` как source of truth и не вводить отдельную persisted сущность monitor-а.
- Для каждого канала собрать и отдать в UI:
  - `runtime status`;
  - `provider/auth probe status`;
  - `last inbound at`, `last outbound at`;
  - `inbound_24h`, `outbound_24h`;
  - агрегированный `overall status` и человекочитаемый summary.
- Поддержать manual refresh одного канала и массовый refresh.
- Сохранять snapshots проверок в `monitoring_check_history` с отдельным `monitor_kind`.
- Добавить analytics-page с overview-метриками, таблицей каналов и просмотром history.
- Добавить scheduler для периодического refresh под lease через `RuntimeCoordinationService`.

## Ограничения и допущения

- В этом implementation-срезе `outbound health` должен опираться на:
  - provider auth / connectivity probe;
  - runtime status;
  - фактическую свежесть/наличие исходящих сообщений в `chat_history`.
- Полноценная persisted классификация delivery failures прямого operator reply-path (`provider 4xx/5xx`, retry pressure, terminal/permanent error kinds) выносится в отдельный follow-up task `01-203`, потому что такого ledger сейчас нет в canonical panel runtime.

## Критерии готовности

- На странице аналитики есть отдельный экран unified provider health.
- По каждому активному каналу `telegram` / `vk` / `max` видны runtime, provider probe и activity-сигналы в одном списке.
- Есть manual refresh all / per-channel refresh.
- Есть history timeline на базе `monitoring_check_history`.
- Есть scheduler, который регулярно обновляет snapshots без гонок.
- Изменения покрыты целевыми тестами.
