## Причина

В присланном скриншоте общей карточки BUSINESS категории видны в шапке,
но кнопка закрытия открывает выбор и сообщает, что категории отсутствуют.
`DialogLookupReadService` уже читает `tickets.business_categories`, а
`DialogDetailsReadService` отдельно формировал массив `categories` через
legacy `ticket_categories`. JS отображал fallback из summary, но проверял
пустой массив выбранных значений. Воспроизведено regression test на исходном
DialogDetailsReadService: после реального сохранения в PostgreSQL массив пуст.

Следующий вызов `/api/dialog-ticket/resolve` также направлялся в legacy lifecycle,
который запрещает BUSINESS mutation при strict scope. Поэтому исправление
включает переход закрытия в существующий BusinessTicketWorkService.

## Исправления

- Details читает canonical BUSINESS массив по полному owner tuple
  (user/raw/public/business, non-GENERAL) с однозначностью raw ID в том же SQL.
  Имена с запятыми не разбиваются; порядок JSON массива сохранён. Для остальных
  обращений прежнее чтение сохраняется. При отсутствии доказанного owner — пусто,
  без подмены legacy данными или текстом шапки.
- Common close получает текущий BUSINESS work state, использует authentication
  исходного запроса, проверяет OPERATE/account/flags и выполняет существующий
  transactional CAS/change. Ошибка CAS возвращается409, legacy fallback нет.
  Пустые категории остаются ошибкой; повторное закрытие — already_closed.
- Добавлены PostgreSQL, MVC и UI regressions на сохранение → повторное открытие
  → закрытие, очистку, owner mismatch, отозванные права и конкурентную revision.

Sandbox: `.tmp/01-295-dialog-close-source`. Native PostgreSQL с новым nonce,
отдельным каталогом и случайным loopback port; рабочая БД не используется.
В тестах используются существующие V81/V97, новых миграций задача не добавляет.
Runtime на сервере пользователя не изменяется; source сессия не получает
разрешения на deploy из исторических записей других сессий.
