# Задача [01-217] Мигрировать legacy media и avatars в MinIO/S3, убрать runtime-зависимость от local attachments и подготовить безопасный финальный purge

## Краткое описание

Перевести исторические вложения диалогов, клиентские/операторские аватары и прочие файловые артефакты из legacy local filesystem (`attachments/**`) в production object storage (`MinIO/S3`) так, чтобы UI и background runtime больше не зависели от локального каталога как от primary storage.

## Почему это важно

- После split-контура `panel-web` / `ops-worker` runtime перешёл в `APP_STORAGE_OBJECT_MODE=s3`.
- Исторические вложения и аватары уже лежали на диске, но не были полностью backfill-нуты в MinIO.
- Из-за этого UI переставал показывать media и аватары, а `chat_attachment_metadata.availability_status` массово уходил в `missing`, хотя файлы физически не были потеряны.
- Нужен не временный fallback, а повторяемая migration-path процедура для нового production-контура.

## Цель

Сделать перенос legacy media в object storage управляемым, идемпотентным и проверяемым:

- runtime умеет безопасно читать legacy-файлы как fallback на переходном периоде;
- существует штатный скрипт backfill-а в MinIO/S3;
- attachment metadata в PostgreSQL синхронизируется с фактической доступностью файлов;
- после ручной валидации можно отдельно выполнить финальный purge legacy local файлов без риска потери данных.

## Что сделать

### 1. Runtime safety net

- Сохранить в `AttachmentObjectStorageService` безопасный fallback: если S3-объект отсутствует, runtime может прочитать файл из legacy local storage.
- При таком fallback выполнять best-effort backfill в object storage, не ломая успешную выдачу файла пользователю.
- Исключить ложные повторные upload-операции, если объект уже есть в MinIO/S3.

### 2. Attachment metadata reconcile

- Нормализовать reconcile `chat_attachment_metadata` по строкам таблицы, а не по общему `chat_history_id`.
- Перед выставлением `availability_status` пытаться backfill-нуть объект по `storage_key`.
- После backfill-а выставлять `available` только для реально восстанавливаемых вложений.

### 3. Ops migration path

- Добавить повторяемый PowerShell-скрипт для production-контура, который:
  - зеркалирует legacy media из `attachments/**` в bucket MinIO/S3;
  - отдельно переносит `avatars`, `knowledge_base`, `passport_photos`;
  - синхронизирует `chat_attachment_metadata.availability_status` в PostgreSQL;
  - при необходимости перезапускает `panel-web` и `ops-worker`, чтобы они переподняли соединения и health.
- Скрипт не должен удалять legacy local файлы.

### 4. Финальный отказ от legacy

- После ручной проверки UI, выборочных media/avatars и production readiness подготовить отдельный purge-runbook.
- Purge local attachments допустим только после подтверждения, что:
  - MinIO/S3 содержит полный рабочий набор объектов;
  - `availability_status` больше не откатывается в `missing`;
  - новые вложения и аватары создаются сразу в object storage;
  - rollback strategy задокументирована.

## Уже сделано

- Добавлен runtime fallback и best-effort backfill в `AttachmentObjectStorageService`.
- Исправлен reconcile attachment metadata на обновление по `id`.
- Добавлен production backfill script `scripts/docker-production-storage-backfill.ps1`.
- На живом контуре выполнен backfill legacy media в MinIO и обновлены 22 строки `chat_attachment_metadata` в `available`.

## Критерии готовности

- `/login` и рабочие страницы панели открываются без деградации из-за отсутствующих PostgreSQL/RabbitMQ.
- Исторические вложения из диалогов снова открываются в UI.
- Клиентские и операторские аватары доступны через текущие URL панели.
- `chat_attachment_metadata` не содержит ложных `missing` для реально существующих legacy-файлов.
- Есть повторяемый скрипт backfill-а для существующего production-контура.
- Финальное удаление local legacy storage выделено в отдельный ручной шаг, а не смешано с миграцией.

## Риски

- В legacy storage могут лежать orphan-файлы без нормальных metadata-ссылок; их удаление нельзя автоматизировать без отдельной инвентаризации.
- UI recovery и логический перенос в новый контур не равны физическому удалению local source.
- При больших объёмах media backfill нужно выполнять под наблюдением по времени, I/O и размеру bucket.

## Update 2026-08-28 - canonical object mappings before cutover

После проверки фактического runtime contract выяснено, что один bulk mirror недостаточен для безопасного отключения local fallback: Java строит ключи как `<APP_STORAGE_OBJECT_KEY_PREFIX>/<domain>/<logical-key>`, а соответствие вложений уже хранится в `chat_attachment_metadata.storage_key`.

Migration path усилен следующим образом:
- bulk mirror сохранён как быстрый перенос существующих файлов, но destination теперь включает runtime key prefix;
- для каждой строки `chat_attachment_metadata` строится точный canonical object key `prefix/attachments/storage_key`;
- наличие local source больше не считается достаточным: перед переводом metadata в `available` объект обязательно подтверждается через `mc stat` по canonical S3 key;
- `legacy_attachment_ref` используется как дополнительная подсказка для выбора historical root, включая `java-bot/attachments`;
- `APP_STORAGE_OBJECT_KEY_PREFIX` явно проброшен в production panel/bot containers и документирован в `.env.example`;
- MinIO client запускается через Compose service `minio-init`, без угадывания `${project}_default` network;
- credentials передаются через process/container environment, а не встраиваются строковой заменой в shell command;
- добавлен безопасный `-ValidateOnly`, который не меняет БД, MinIO или контейнеры;
- добавлены read-only audits для attachment metadata, `users.photo` operator avatars и client avatars, где runtime ожидает `<userId>.jpg` / `<userId>_full.jpg`;
- source-contract tests фиксируют exact Java S3 keys и запрещают destructive cleanup в migration/audit scripts.

При дополнительной сверке с MinIO CLI contract до runtime запуска исправлена команда точечного copy: `mc cp --overwrite` заменён на поддерживаемый `mc cp`; `--overwrite` остаётся только у `mc mirror`.

Local source на этом этапе не удаляется. `APP_STORAGE_OBJECT_LEGACY_LOCAL_FALLBACK_ENABLED=true` остаётся обязательным до GREEN обоих live cutover audits и ручной проверки UI/media/avatars.

- Вынести физический purge local legacy storage в отдельный завершающий task/runbook.
