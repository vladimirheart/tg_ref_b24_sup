# Задача [01-217] Мигрировать legacy media и avatars в MinIO/S3, убрать runtime-зависимость от local attachments и подготовить безопасный финальный purge

## Краткое описание

Перевести исторические вложения и аватары из legacy local filesystem в production object storage и завершить переход так, чтобы локальные каталоги больше не являлись runtime dependency. Физический cleanup выполняется отдельно, только через доказанный manifest-driven quarantine и с сохранённым rollback window.

## Цель

- canonical runtime storage — MinIO/S3;
- attachment metadata соответствует реальной доступности canonical objects;
- local fallback после успешного cutover выключен;
- известные невосстановимые исторические вложения явно зафиксированы и не маскируются placeholder-объектами;
- оставшиеся локальные файлы инвентаризируются и сопоставляются без destructive операций;
- quarantine и физическое удаление отделены друг от друга и требуют отдельных решений оператора.

The old manual evidence is intentionally tied to `5d284c...`; after pulling the tooling commit it must be regenerated on the new HEAD before any quarantine can be considered.

## Safety contract

- Do not use `docker compose ps` as authoritative production state; use Docker Compose labels plus `docker inspect`.
- Do not broad-delete or broad-move `attachments/**` or `java-bot/attachments/**`.
- Do not touch canonical or legacy MinIO objects during local purge preparation.
- Do not delete or rewrite PostgreSQL attachment rows during purge preparation.
- Do not include `knowledge_base`, `passport_photos`, `forms`, avatar scope, or orphans without dedicated audits.
- Exactly 20 reviewed known-unrecoverable dialog attachments remain allowed to be absent from canonical MinIO.
- Quarantine manifest entries are integrity-bound by `candidate_set_sha256`.
- Real quarantine requires explicit `quarantine_authorized=true`, explicit quarantine path, same-volume move semantics and fresh GREEN gates.
- `physical_delete_authorized` remains false; physical deletion is a later independent operator decision.

## Что остаётся

1. Pull the tooling commit to the production host with a clean fast-forward.
2. Run all new PowerShell scripts with `-ValidateOnly` under real Windows PowerShell 5.1.
3. Generate a **fresh** inventory on the new production HEAD.
4. Run the exact mapping audit and confirm the candidate/orphan/blocker counters remain acceptable.
5. Manually review the new integrity-hashed candidate manifest; do not authorize quarantine by default.
6. If the operator chooses to proceed, create a reviewed manifest copy changing only `quarantine_authorized=true` and run full dry-run / `-Apply -WhatIf` with an explicit quarantine path.
7. Execute real quarantine only after a separate explicit operator decision.
8. After quarantine, rerun both storage gates, health checks, logs and manual UI/media smoke; restore exact paths if any regression appears.
9. Keep quarantine and cutover rollback backup through the observation window.
10. Consider physical deletion only after a later explicit rollback-window closure. Orphans and unaudited domains stay outside that decision.

## Критерии готовности задачи

- production remains stable with local fallback disabled;
- all canonical storage gates stay GREEN;
- fresh inventory and exact mapping evidence are reproducible;
- every quarantined path is tied to an exact reviewed manifest entry and unchanged SHA-256;
- orphans/unaudited domains are excluded;
- quarantine passes observation and manual UI/media verification;
- rollback evidence is retained;
- physical deletion, if ever performed, is a separately approved operation after rollback-window closure.
