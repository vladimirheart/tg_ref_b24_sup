# Задача [01-210]

## Короткое описание

Сделать `incidents` workbench понятным для `credential_rotation` сигналов и объяснить severity policy.

## Цель

Убрать внутренний технический жаргон из карточек `credential_rotation` incidents, показать оператору и владельцу проекта нормальное объяснение причины/действия, а также явно отразить, почему incident имеет именно такой severity.

## Контекст

- Сейчас `CredentialRotationRegistryService` формирует incident summary/description слишком внутренними формулировками (`critical secret hygiene condition`, `registry history`, `lifecycle risk`).
- Для `credential_rotation` contour severity policy бинарная: warning-состояния остаются на analytics странице registry, а incident в workbench создаётся только когда состояние уже `critical`.
- В текущем incident detail API нет нормализованного signal context; UI в workbench показывает только `summary` и `description`, поэтому пользователь не понимает, что реально сломано и почему это critical.

## Что сделать

- Переписать incident title/summary/description для `credential_rotation` в понятные русские формулировки.
- Передавать в incident detail структурированный signal context и severity explanation из последнего signal event payload.
- В `incidents-workbench.js` показать в карточке отдельный блок с:
  - диагностикой причины;
  - политикой severity для текущего signal type;
  - рекомендуемым следующим действием.
- Зафиксировать в UI/данных, что `credential_rotation` incidents создаются только для `critical`, а warning остаётся на analytics registry page.
- Покрыть изменения целевыми тестами.

## Критерии готовности

- Карточка incident для `credential_rotation` больше не показывает абстрактный англоязычный текст без смысла.
- Пользователь видит, почему severity выставлен именно так.
- Для `credential_rotation` явно отражено, что warning не эскалируется в incident workbench, а critical — эскалируется.
- Изменения подтверждены тестами.
