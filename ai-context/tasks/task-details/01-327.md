- Связать состав задачи с её READ, сохранив независимый module grant/PAGE_TASKS,
  ограничения заблокированных аккаунтов и отдельные EDITOR/OWNER permissions.
- Привязывать участника к users.id, не выдавать права по совпадению имени при
  каждом чтении, не назначать владельца по legacy creator/lead, не наследовать
  задачи из проектного участия. Явные назначения и производное чтение различаются.

## Проверки

## Реализовано

- Уточнённый scope — карточка проекта на /projects. Общая страница настроек
  панели не меняется. В карточке два раздела: «Сведения» и «Участники». Они
  находятся внутри scrollable modal body; header/footer остаются доступны.
- В каталоге проектов есть отдельная кнопка «Участники». После создания проект
  остаётся открытым на составе. Добавление находится перед roster и видно сразу
  при длинном списке. Код, архивирование, передача владения и аудит свёрнуты.
  Руководитель явно отделён от допуска к проекту. Поиск и назначения используют
  прежний current scoped people API, string IDs и проверки OWNER/system admin.
- Несохранённые сведения сохраняются при смене вкладок и изменении состава.
  Состав сохраняется сразу, сведения — отдельной кнопкой. Повторный SAVE блокируется.
  Подтверждённый ответ создания открывает его ID до обновления списка: ошибка
  последующего GET не превращает созданный проект в повторяемый create draft.
- READ-only блокирует изменение сведений и состава; передача владельца требует
  прежнего подтверждения. Отзыв закрывает карточку также во время анимации открытия.
- Причина невидимых задач: task_people и shared_task_members не были связаны.
  Ответственный/co/watcher теперь получает производный READ через numeric user_id,
  а не через сравнение текущего логина с историческим текстом. Shared OWNER/EDITOR/
  VIEWER независимы; участие не выдаёт WRITE/OWNER и не обходит module/account gates.
- Current account, PAGE_TASKS/shared can_read, enabled/blocked, role snapshot и
  owned-root boundary сохранены. Проектное участие не открывает задачи. Старому
  объекту без владельца администратора по-прежнему требуется явно назначить OWNER.
- List/count/pagination, прямое чтение, вложения, получатели уведомлений и late READ
  используют обновлённое ядро. «Мои задачи» включает assignee/co/watcher по ID.
  Отзыв участия удаляет производный READ, сохраняя отдельные явные grants.
- V109: nullable account FK в task_people с ON DELETE SET NULL; exact, однозначная
  привязка existing roster и восстановление недостающего assignee из tasks.assignee.
  Неизвестные/неоднозначные/удалённые записи сохраняют подпись с NULL; trim/case
  folding и владение не выводятся. System follow-up writer теперь сохраняет
  assignee в roster сразу, чтобы не потерять такие задачи в «Моих».
- Повторное использование логина не перепривязывает неизменённое участие к новой
  УЗ. Unchanged NULL binding сохраняется при записи. READ держит participant share
  lock до commit; roster replacement ждёт завершения чтения/доставки.
- Roster доступа отличает taskParticipant от явного назначения и не предлагает
  бесполезный DELETE grant, когда READ задан составом задачи. Общие previews и
  server-provided options сохранены; новых глобальных grants/fallback нет.
