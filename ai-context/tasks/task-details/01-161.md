# Задача [01-161]

## Краткое описание

Нормализовать attachment metadata и восстановить broken attachment references как первый implementation-шаг storage strategy Iguana.

## Цель

Перевести Iguana от хранения вложений как неустойчивых path-строк в runtime-таблицах к metadata-first модели с предсказуемым storage contract, а также убрать уже выявленные broken attachment references и path drift, чтобы historical dialog/media данные перестали зависеть от случайного layout каталога на диске.

## Контекст

- Задача `01-160` завершила design-часть: зафиксированы lifecycle-правила, storage tiers, retention и phased rollout.
- В рамках follow-up implementation уже добавлены:
  - `scripts/report-iguana-storage.py`;
  - запуск storage inventory из админки `Настройки -> Storage inventory Iguana`.
- Inventory уже подтвердил фактическую проблему в текущем runtime:
  - missing attachment references в `panel_runtime.db`;
  - missing attachment references в `java-bot/panel_runtime.db`;
  - missing attachment references в `spring-panel/panel_runtime.db`;
  - исторические абсолютные пути вида `.../java-bot/attachments/...` и filename-only записи в `chat_history.attachment`.
- Сейчас вложения и file references живут неоднородно:
  - bot runtime пишет файловые пути;
  - panel-side download/relay сценарии завязаны на path resolution;
  - metadata как канонический business-факт в отдельной модели ещё не оформлена.

## Что сделать

- Спроектировать и внедрить canonical attachment metadata model для Iguana:
  - `storage_key`;
  - `storage_provider`;
  - `storage_class`;
  - `original_name`;
  - `mime_type`;
  - `size`;
  - `hash`/dedup key при необходимости;
  - timestamps и archive/delete markers.
- Выбрать и зафиксировать первичный storage contract для runtime:
  - что именно хранится в `chat_history` и соседних business-таблицах;
  - какие legacy path-поля остаются только как migration/read-compat слой;
  - где проходит граница между metadata и physical location.
- Реализовать первый migration/remediation шаг для уже существующих broken references:
  - разобрать абсолютные legacy paths;
  - разобрать ticket-scoped filename-only ссылки;
  - определить recoverable и unrecoverable записи;
  - подготовить безопасную нормализацию/repair strategy.
- Обновить panel/bot-side attachment access path так, чтобы новый canonical contract не зависел от того, запускался runtime из root или из `java-bot/`.
- Сохранить и расширить inventory/diagnostics контур:
  - чтобы после миграции можно было повторно измерить remaining missing references;
  - чтобы storage drift был виден как явный операционный сигнал.
- Если задача окажется слишком большой для одного implementation-pass, зафиксировать внутри detail-файла явную декомпозицию на следующие bounded follow-up tasks, а не размывать scope неявно.

## Критерии готовности

- В проекте есть canonical attachment metadata contract, на который можно опираться в panel и bot runtime.
- Есть реализованный migration/remediation путь для уже выявленных broken attachment references или чётко зафиксированная автоматизируемая стратегия их восстановления.
- Attachment download/lookup сценарии больше не зависят от исторического различия `attachments/` vs `java-bot/attachments/` как неявного runtime assumption.
- Storage inventory после изменений позволяет явно увидеть уменьшение или полное закрытие текущего класса missing references.
