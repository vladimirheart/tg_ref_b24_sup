# Задача [01-222] Собрать controlled migration workflow для persisted infra credentials после secure bootstrap

## Краткое описание

Fresh first-run bootstrap теперь умеет создавать безопасные секреты, но уже существующие PostgreSQL/RabbitMQ/Redis/MinIO/Grafana volumes нельзя переводить на новые credentials простой перезаписью `.env`. Нужен отдельный управляемый migration workflow.

## Почему это важно

- `01-216` закрыл secure fresh-install slice, но намеренно не ротирует volume-backed credentials автоматически.
- Простая замена `IGUANA_POSTGRES_PASSWORD`, `IGUANA_RABBITMQ_PASSWORD`, `IGUANA_REDIS_PASSWORD`, `APP_STORAGE_OBJECT_SECRET_KEY` или `IGUANA_GRAFANA_ADMIN_PASSWORD` в уже работающем стенде может рассинхронизировать `.env` и persisted state.
- Для production-переезда нужен repeatable путь с rollback, чтобы не потерять доступ к данным и не сорвать запуск split roles.

## Что нужно сделать

1. Определить fresh/existing/migration-required состояния для PostgreSQL, RabbitMQ, Redis, MinIO и Grafana volumes.
2. Для каждого компонента описать и по возможности автоматизировать безопасную credential migration:
   - PostgreSQL role password rotation + проверка нового подключения;
   - RabbitMQ user password sync без потери queues/definitions;
   - Redis coordinated password switch для всех клиентов;
   - MinIO root credential migration без потери доступа к bucket/object set;
   - Grafana admin reset с учётом persisted DB.
3. Сделать единый status/dry-run helper, который не меняет `.env`, пока не подтверждена успешная миграция persisted credentials.
4. Подготовить rollback/runbook и smoke-проверки post-migration.

## Критерии готовности

- Existing install классифицируется явно, без guesswork.
- Есть dry-run verdict и отдельный apply path.
- Ни один volume-backed credential не ротируется до успешной проверки persisted state.
- После migration все backend roles, integrations и observability контур стартуют на новых secret values.
- Есть rollback-инструкция и post-migration smoke.
