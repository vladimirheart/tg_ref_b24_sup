# Задача [01-162]

## Краткое описание

Разобрать и закрыть оставшиеся orphan attachment rows после metadata migration Iguana.

## Цель

Довести attachment remediation после `01-161` от уровня «ссылки нормализованы и диагностируются» до уровня «остаточные orphan/media gaps либо реально восстановлены, либо явно санированы по согласованной политике», чтобы в canonical runtime не оставалось неясных missing attachment кейсов.

## Контекст

- По состоянию на `2026-07-31` в рамках `01-161`:
  - `chat_history.attachment` был нормализован в `chat_attachment_metadata`;
  - в `spring-panel/panel_runtime.db` больше нет legacy attachment rows без metadata;
  - в `spring-panel/panel_runtime.db` осталось `40` metadata rows с `storage_key`, которые указывают на отсутствующие binaries в `attachments/`;
  - в `spring-panel/panel_runtime.db` осталась `1` unresolved metadata row с внешним URL `https://i.oneme.ru/...`, который не может быть канонизирован в local `storage_key`;
  - аналогичный хвост есть и в соседних repo-копиях `panel_runtime.db` / `java-bot/panel_runtime.db`.
- Storage inventory теперь умеет показывать canonical metadata layer и отделять:
  - normalized references;
  - unresolved rows;
  - remaining missing files.
- Проблема уже не в формате ссылок, а в отсутствии physical payload или в special-case external URL.

## Что сделать

- Разделить оставшийся хвост на классы:
  - recoverable из локального/внешнего backup;
  - external URL references, которые требуют отдельного policy decision;
  - irrecoverable missing binaries.
- Для recoverable rows:
  - определить источник восстановления;
  - вернуть binaries в canonical attachment root;
  - подтвердить, что `storage_key` после восстановления начинает резолвиться inventory-скриптом.
- Для irrecoverable rows:
  - зафиксировать policy: archival marker, explicit tombstone, operator-facing fallback или cleanup;
  - внедрить безопасную санацию, чтобы UI не выглядел как «битое вложение без объяснения».
- Для external URL кейсов:
  - решить, остаются ли они отдельным `storage_provider`, либо требуют локального ingest/mirror;
  - оформить canonical handling без маскировки под local file.
- Повторно снять inventory после remediation и подтвердить фактическое сокращение remaining missing references.

## Критерии готовности

- Для canonical runtime (`spring-panel/panel_runtime.db`) не остаётся неразобранных orphan attachment rows.
- Все remaining attachment cases имеют явный статус:
  - восстановлено;
  - сохранено как external reference по каноническому правилу;
  - санировано как irrecoverable.
- Storage inventory после изменений показывает понятный и ожидаемый остаток без «немых» broken references.
