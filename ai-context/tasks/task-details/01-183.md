# Задача [01-183]

## Краткое описание

Довести Iguana до full production contour: `PostgreSQL-only` runtime, `backend-owned transport` и `incident module`.

## Цель

После завершения `01-181` и `01-182` перевести проект из состояния `PostgreSQL-first readiness` в полноценный production-ready контур, который выдерживает целевые объёмы и архитектурные ограничения:

- `30 000+` диалогов в месяц;
- `50+` одновременно работающих операторов;
- `100+` зарегистрированных интеграционных каналов;
- `40+` одновременно активных каналов;
- несколько экземпляров backend;
- несколько worker одного типа;
- отсутствие прямого доступа integration workers к business database;
- PostgreSQL как единственный canonical runtime/business storage для живой системы;
- полноценный incident module, связанный с dialogs, tasks и objects.

## Контекст

- `01-181` закрыла fast-path readiness для fresh `PostgreSQL-first` запуска и backend-owned основных runtime-path.
- `01-182` изолировала remaining bot-side task/follow-up fallback в `java-bot` как `jdbc`-only compatibility perimeter.
- На текущем состоянии репозитория всё ещё остаются отдельные SQLite/transitional контуры:
  - `panel_identity.db`;
  - `monitoring.db`;
  - `bot_runtime.db`;
  - `clients.db`;
  - `knowledge_base.db`;
  - `objects.db`;
  - `settings.db`;
  - bootstrap/dev wiring вокруг `APP_DB_MODE=sqlite`.
- В `spring-panel` и документации всё ещё существует явная multi-SQLite topology, которая уже не соответствует финальной production-цели.
- Для production storage boundaries в проекте уже зафиксировано правило: backend владеет business data, а transport/integration workers не должны напрямую владеть business schema.
- Новая задача должна опираться на фактическое состояние репозитория на `2026-08-17`, а не на исторические ожидания из ранних этапов `01-181`.

## Что сделать

- Убрать из живого runtime проекта зависимость от отдельных SQLite business/secondary контуров и свести canonical storage к PostgreSQL.
- Перевести в PostgreSQL оставшиеся operational/identity/monitoring/object/task/knowledge/runtime данные, которые ещё живут в отдельных SQLite-файлах или secondary datasource-контурах.
- Убрать из `spring-panel` runtime wiring, которое поддерживает SQLite как отдельные production-like data source для:
  - identity;
  - monitoring;
  - bot-runtime;
  - clients;
  - knowledge;
  - objects;
  - settings-registry.
- Зафиксировать и реализовать final backend-owned transport model:
  - integration workers не ходят напрямую в business DB;
  - live message/task/incident flows проходят через queue/API boundary;
  - bot-side local state остаётся только как runtime/per-channel technical state, если он вообще нужен.
- Довести production contour:
  - PostgreSQL как canonical source of truth;
  - Redis для session/runtime coordination и live delivery coordination;
  - RabbitMQ как transport/event backbone;
  - MinIO/S3 abstraction для attachment binaries;
  - stateless backend/worker scaling model.
- Реализовать incident module на canonical backend storage, а не как отдельный временный слой:
  - incident lifecycle;
  - signal -> incident model;
  - dialog/task/object links;
  - incident events/history/watchers/routes;
  - operator-facing UI и alert delivery.
- Обновить task/docs/changelog так, чтобы после завершения было явно видно:
  - `01-181` и `01-182` были подготовительными слоями;
  - `01-183` закрывает уже full production contour, а не только readiness.

## Декомпозиция

### Phase A. PostgreSQL canonical schema consolidation

- Свести оставшиеся business/secondary SQLite-контуры в canonical PostgreSQL schema(s).
- Определить финальную logical topology для:
  - runtime/business;
  - identity;
  - monitoring;
  - objects;
  - integration/inbox/outbox;
  - incident domain.
- Перенести ownership всех live runtime таблиц под Flyway/PostgreSQL.

### Phase B. Spring-panel runtime rewiring

- Выпилить production-like SQLite datasource graph из `spring-panel`.
- Оставить SQLite только там, где это действительно допустимо как test/import/dev compatibility, если такие места останутся после пересмотра.
- Перевести сервисы и repositories на PostgreSQL-owned контур без split по отдельным SQLite файлам.

### Phase C. Transport/backend ownership completion

- Довести все active worker flows до queue/API boundary.
- Убедиться, что `java-bot` больше не воспринимается как владелец business state.
- Изолировать или удалить remaining compatibility/JDBC paths, которые не нужны для production contour.

### Phase D. Infra contour

- Поднять и зафиксировать production role для `Redis`, `RabbitMQ`, `MinIO/S3`.
- Обеспечить stateless backend и multi-worker coordination model.
- Закрыть single-point-of-failure сценарии в live message processing.

### Phase E. Incident module

- Реализовать canonical incident domain внутри backend.
- Связать incidents с dialogs/tasks/objects.
- Добавить lifecycle, alerts, history, watchers и operator workflows.

## Критерии готовности

- Живой runtime проекта больше не зависит от отдельных SQLite business/secondary файлов как от production-like data sources.
- PostgreSQL является единственным canonical storage для актуальных business/runtime/identity/monitoring данных системы.
- Integration workers не имеют прямого доступа к business PostgreSQL schema.
- `spring-panel` и `java-bot` поддерживают production contour через backend-owned PostgreSQL + transport boundary.
- Redis/RabbitMQ/MinIO входят в целевой production runtime contour и не висят как “потом подключим”.
- Incident module реализован на canonical backend storage и связан с dialogs/tasks/objects.
- Архитектура допускает несколько backend instance и несколько worker одного типа без фундаментальной переделки.
- Релевантные tests, verification-path и runbooks обновлены.
