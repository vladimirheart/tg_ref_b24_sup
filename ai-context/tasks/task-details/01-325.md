## Механизм

NotificationService использует JPA @Transactional, а application.yml явно
оставляет open-in-view=true. На тех же версиях библиотек vendor adapter выбирает
DELAYED_ACQUISITION_AND_HOLD: request-bound EntityManager может удерживать
физическое соединение после прикладной транзакции до завершения HTTP request.

При записи ответа Spring Session сохраняет сессию через отдельную REQUIRES_NEW
JDBC-транзакцию. Её manager отдельный, но DataSource и Hikari-пул те же.
Если шесть одновременно завершающихся запросов уже удерживают все шесть
соединений, session save просит дополнительные соединения из исчерпанного пула.
Ответы ждут, а удерживаемые соединения освобождаются при завершении/ошибке request.
Таймауты и попытки записать ошибку/сессию растягивают эпизод примерно до минуты.
Обычные запросы обновлённой страницы и проверки состояния попадают в ту же очередь.

Это подтверждённый изолированным воспроизведением механизм, согласующийся с
производственными стеками и метриками; thread dump непосредственно во время
эпизода не снимался, точные входные параметры запросов не журналируются.

## Изолированное воспроизведение

- Внешний PoolSessionRepro.java использует библиотеки из реально установленного
  R324 JAR: Spring ORM/JDBC, Hibernate, Hikari. Отдельная PostgreSQL 16, tmpfs,
  собственная БД diag, шесть потоков, только SELECT 1, pool max=6.
- Request-bound EntityManager + JpaTransactionManager, затем REQUIRES_NEW
  DataSourceTransactionManager на том же DataSource. В тесте acquisition timeout
  сокращён до одной секунды, не изменяет production 30 секунд.
- Результат до освобождения EM: active=6, success=0, timeouts=6.
- При закрытии EM перед session transaction: success=6, timeouts=0.
  После обоих сценариев active=0. Production-сессии/данные тест не использует.

## Рекомендации в порядке приоритета

1. Устранить удержание JPA connection до HTTP/session commit. Предпочтительный
   ограниченный scope — JDBC/DTO read path списка оповещений с короткой JDBC
   transaction и освобождением до сериализации. Сохранить текущие account/owner/
   business/shared-work predicates и блокировки. Отдельно проверить release mode
   AFTER_TRANSACTION либо отказ от OSIV для JSON API. Не выключать глобально OSIV
   без регрессии lazy rendering; не удалять session transaction manager как обход.
2. Проверить таким же конкурентным сценарием другие JPA JSON endpoints и SSE:
   шесть и более одновременных authenticated requests с настоящим session save.
   Критерии: нет pool starvation, pending возвращается к нулю, нет 500/504,
   permissions/revocation/session persistence сохраняются.
3. Для списка оповещений убрать невыгодный JIT адресно и проверить план/индексы,
   row estimates и batch нормализации номеров. Не отключать диагностику и не
   упрощать SQL ценой пропуска проверок доступа. EXPLAIN подтверждает отдельную
   проблему latency, но сам по себе не объясняет удержание connection 60 секунд.
4. Сделать single-flight/coalescing и backoff для самого /api/notifications:
   loadNotificationsSafe не проверяет notificationPageLoading на входе,
   reload timer сбрасывается до await. Это допускает перекрытие manual/SSE reload.
   Ранее сериализован unread_count, что не защищает загрузку списка.
   Abort в браузере один не гарантирует освобождения backend connection.
5. Усилить диагностику: Nginx request_time/upstream_response_time/request ID,
   корреляция HTTP/JDBC/session и автоматический thread dump при длительном
   pending. Текущий access log не содержит request durations и client IP за
   Docker NAT недостаточен для точного сопоставления машины.

Увеличение max_connections=550, child minimumIdle/maxPoolSize или HTTP timeout
не устраняет этот цикл. Больший web pool может временно разнести пик, но те же
условия воспроизводятся при насыщении нового размера; это не основное исправление.
Отдельный ограниченный session pool возможен как дополнительная изоляция после
оценки общего connection budget, а не замена освобождению прикладных соединений.
