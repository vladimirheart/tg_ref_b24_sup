# Задача [01-272]

## Короткое описание

Провести системный UI/UX-проход с упором на единые переиспользуемые паттерны и убрать текстовый helper/disclosure «Подробнее» там, где статическое пояснение можно открыть компактной `i`-иконкой.

## Контекст

- Пользователь зафиксировал глобальное правило: одинаковая пользовательская функция должна иметь одинаковый UI/interaction pattern; локальные одноразовые решения не должны раздувать runtime-файлы.
- Статический help/why/how-it-works текст предпочтительно скрывать за компактным `i`, но operational status, ошибки и предупреждения должны оставаться видимыми.
- Первый read-only audit нашёл runtime-текст «Подробнее» в `content-disclosure.js`, `passport-detail-equipment-runtime.js` и `settings-partner-contacts-runtime.js`.
- R1 частично изменил эти три JS и остановился на CRLF-sensitive SCSS marker; R2 заблокировался до apply, потому что его known-state fingerprint не распознал фактический R1 partial state.
- R3.3 продолжает работу только вперёд из подтверждённого exact partial state без `reset`, `clean` или broad `checkout`; R3 и R3.1 остановились до первой записи на Maven preflight, R3.2 — до первой записи на неоднозначном JS marker после полностью GREEN Maven preflight.

## Первый implementation slice

- generic `content-disclosure` становится `i`-only: preview-копия убирается, полный helper body находится в общем info panel;
- page-header и generic disclosure используют одну JS-функцию open/close interaction;
- DOM mount order сначала закрепляет wrapper в исходном parent, затем переносит helper body в panel, исключая `HierarchyRequestError`;
- helper body явно остаётся видимым внутри открытого panel (`element.hidden = false`);
- карточка оборудования использует компактный `bi-info-circle` в native `<details>`;
- карточка контакта партнёра сохраняет whole-card action и заменяет текстовый affordance на `bi-info-circle`;
- obsolete textual disclosure SCSS удаляется, equipment summary получает минимальный native-details reset;
- source contract запрещает повторное появление «Подробнее» в application runtime JS/templates, не затрагивая changelog/history/test/vendor.

## Ограничения

- backend/API semantics не меняются;
- runtime/deploy/container/DB/queue mutations не входят в этот slice;
- generated CSS должен контролироваться после Maven: unrelated Sass output возвращается к HEAD, сохраняется только минимальный counterpart текущего UI change;
- task остаётся `🟡` до ручной UI-приёмки пользователя;
- AI не переводит задачу в `🟢` самостоятельно.

## Критерии текущего slice

- exact pre-state: HEAD/origin main `000c6bc804e947a12028a1e6530b47e1276234ca`, dirty scope ровно из трёх подтверждённых R1 JS;
- `node --check` GREEN для изменённых application JS;
- `UiInfoDisclosureSourceContractTest` GREEN;
- `git diff --check` GREEN;
- отсутствует runtime UI string «Подробнее» в application JS/templates;
- no stage/commit/push;
- после apply требуется ручная UI-проверка перед дальнейшим batching/commit.

🟡 В работе. Первый info-disclosure slice подготовлен как continuation R3.3; дальнейшие UI-комментарии пользователя продолжают собираться в эту же задачу, если не образуют отдельный функциональный scope.

- После принятого S5 compact overview следующий Knowledge Base slice переводит статью с raw-Markdown-only редактирования на inline visual editing поверх уже отрендеренного содержимого.

- Основные formatting controls (undo/redo, bold/italic/strike, H2/H3, списки, quote/code, link/unlink) находятся в sticky toolbar вместе с `Сохранить`, поэтому при длинной статье не требуется возвращаться к началу страницы.
- Если пользователь меняет только metadata, исходный Markdown не пересериализуется; Markdown обновляется только после фактического изменения article content.
- Serializer сохраняет project-specific rendered knowledge blocks как source constructs: table of contents, empty block и callout.

### S6 manual preview follow-up — Notion-style editing R2

- Ручная preview-проверка S6 R1 приняла compact article header и вход в edit mode, но выявила два UX-дефекта: toolbar не удерживался при прокрутке, а текущее форматирование блока/выделения было неочевидно.
- Причина sticky regression: общий `.ops-section-card` задаёт `overflow: hidden`, из-за чего descendant `position: sticky` не мог работать относительно viewport; article editor получает узкий `overflow: visible` override только для `kb-editor-main`.
- Editing interaction приближается к знакомому Notion-паттерну без копирования его data model: block-type selector показывает текущий тип блока, inline formatting buttons отражают active state, выделение текста открывает compact floating formatting bar, а `/` в начале блока открывает menu для text/headings/lists/quote/code/divider.
- Existing Markdown persistence contract сохраняется: визуальная поверхность по-прежнему сериализуется в прежнее поле `content`; backend/API/DB/schema не меняются.
- Block drag/reorder и collaborative semantics Notion намеренно не добавляются в этот corrective slice, чтобы не менять persisted document model до отдельного contract review.
- Task остаётся `🟡` до ручной проверки sticky toolbar, active formatting context, slash menu и фактического save round-trip.

### S6 save regression follow-up — R3

- Ручная проверка R2 выявила два независимых save-path дефекта: штатный submit ошибочно попадал под unsaved-changes `beforeunload`, а существующая статья не сохранялась в PostgreSQL.
- Read-only runtime log подтвердил корень backend-ошибки до notification/redirect: `KnowledgeArticle` использовал `LenientOffsetDateTimeConverter<OffsetDateTime,String>` для `createdAt`/`updatedAt`/`externalUpdatedAt`, из-за чего Hibernate отправлял varchar в PostgreSQL `TIMESTAMP WITH TIME ZONE` и транзакция откатывалась.
- R3 оставляет lenient converter для других legacy/read-path сущностей нетронутым, но переводит temporal-поля `KnowledgeArticle` на native Hibernate/JDBC `OffsetDateTime` binding, соответствующий production PostgreSQL schema.
- Visual editor получает явное `submitting` state: при штатном submit source сериализуется, после чего `beforeunload` больше не показывает ложное предупреждение; fallback `form.submit()` использует тот же preparation path.
- DB migration/schema mutation не требуется: исправляется только Java mapping существующих temporal columns.
- После targeted Maven и panel-web-only preview обязательна повторная ручная проверка сохранения существующей статьи; commit/push выполняются только после неё.
