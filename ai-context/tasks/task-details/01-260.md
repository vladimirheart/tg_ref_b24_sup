# Задача [01-260] Декомпозировать крупные source-файлы по ответственности и закрепить clean-code layout

## Контекст

Проект вырос до состояния, где ряд исходников объединяет несколько независимых причин изменения. Это повышает риск регрессий, усложняет review и заставляет затрагивать большие файлы ради локальных изменений.

Разделение выполняется не по правилу «один use-case = один файл», а по устойчивой ответственности компонента. Маленькие связные классы и модули не дробятся только ради размера.

## Цель

- оставить entrypoint/facade-файлы маленькими и предсказуемыми;
- группировать реализацию по feature/responsibility;
- не допускать новых god-files;
- проводить миграцию поэтапно, без big-bang rename/move;
- сохранять публичные runtime-контракты и поведение на каждом структурном шаге.

## Найденные зоны риска на baseline d26ee650

### Frontend source
- settings/index.html: около 400 KB;
- passports/new.html: около 186 KB;
- dialogs/index.html: около 93 KB;
- app/_passports.scss: около 70 KB;
- app/_dialogs.scss: около 85 KB;
- app/_dashboard.scss: около 47 KB;
- settings/_calm.scss: около 28 KB;
- sidebar/_sections.scss: около 19 KB;
- несколько browser runtime JS-файлов находятся в диапазоне 60–180 KB.

### Backend
Spring Panel в основном организован layer-first (`controller/`, `service/`, `repository/`). В `service/` есть крупные orchestration-классы, для которых нужен постепенный переход к feature-first пакетам и разделение orchestration/query/mutation/integration responsibilities.

### Operational scripts
В `scripts/` есть крупные production PowerShell/Bash workflows. Их нельзя механически дробить вместе с UI: сначала должны быть выделены стабильные safety/helper contracts и сохранены dry-run/guard semantics.

## Целевая структура

### SCSS
Entrypoint-файлы (`app.scss`, `settings.scss`, `sidebar.scss`, `style.scss`) только подключают feature-модули. Крупные partials становятся compatibility aggregators и подключают подмодули в исходном cascade order.

### Browser JS
Текущие публичные имена script-файлов временно сохраняются как facades. Реализация постепенно переносится в `core/` и feature-каталоги (`dialogs/`, `settings/`, `analytics/`, `sidebar/`), без массового изменения тлобальных window-контрактов одним коммитом.

### Templates
Page-файл отвечает за shell и composition. Самостоятельно меняющиеся modal/form/table/workspace-секции выносятся в Thymeleaf fragments внутри каталога feature.

### Java
Переход выполняется вертикальными feature-срезами:
`<feature>/api`, `<feature>/application`, `<feature>/domain`, `<feature>/infrastructure`.
Общие технические компоненты остаются в `shared/`. Никакого массового package move.

### Scripts
Целевая группировка: `build/`, `deploy/`, `db/`, `monitoring/`, `security/`, `recovery/`, `lib/`. Production scripts мигрируют последними и только после тестов safety contracts.

## Size-review policy

Размер — сигнал к review, а не автоматическая причина дробления:
- SCSS partial: целевой диапазон до 15 KB, обязательный review отвественности после 20 KB;
- browser JS module: целевой диапазон до 25 KB, обязательный review после 40 KB;
- Thymeleaf page/fragment: review после 30 KB или примерно 500 строк;
- Java class: review после примерно 500 строк, особенно при нескольких типах I/O/оркестрации;
- operational script: review после 20 KB, но безопасность важнее формального лимита.

Generated CSS, vendor assets, migrations, fixtures и исторические документы не дробятся по этим лимитам автоматически.

## План

1. P1 — зафиксировать source-layout policy и механически разрезать `app/_passports.scss` с битово эквивалентным generated CSS.
2. P2 — SCSS: sidebar, dialogs, dashboard, settings.
3. P3 — templates: settings, passports, dialogs; page files оставить composition shells.
4. P4 — browser JS: compatibility facade -> feature modules, начиная с наиболее изолированных runtime.
5. P5 — Spring Panel Java: feature-first migration крупных orchestration-классов по одному домену.
6. P6 — java-bot и operational scripts; отдельно решить tracked runtime artifacts.
