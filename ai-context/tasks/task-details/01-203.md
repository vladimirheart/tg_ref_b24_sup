# Задача [01-203]

## Короткое описание

Ввести persisted provider delivery ledger и нормализованную error classification для outbound reply-path в `Telegram` / `VK` / `MAX`.

## Цель

Дать support/ops-команде и владельцу Iguana отдельный monitoring-срез, в котором видно:

- какие исходящие ответы реально пыталась отправить панель;
- в какой provider/channel ушла попытка;
- чем закончилась доставка: `success`, `4xx`, `5xx`, `429`, timeout, network/proxy failure, validation failure;
- является ошибка временной (`transient`) или постоянной (`terminal`);
- какой именно reply-path деградирует и по какому ticket/channel это происходит чаще всего.

## Контекст

- В `01-201` уже появился unified provider health, но outbound сигнал там пока косвенный: он строится по `chat_history` и probe-ам провайдера.
- Canonical direct reply-path живёт в `spring-panel`: `DialogReplyService` -> `DialogReplyTransportService`.
- В текущем коде panel умеет вернуть оператору текст ошибки, но не сохраняет provider-level outcome как отдельный persisted ledger.
- В `java-bot` есть свои transport/integration таблицы, но это другой контур; для operator reply они не являются source of truth.
- Для продолжения roadmap по observability и alerting нужен именно panel-owned ledger с history и API для аналитики.

## Что сделать

- Добавить в monitoring DB отдельный ledger outbound delivery attempts.
- Хранить по каждой попытке как минимум:
  - `provider/channel/platform`;
  - `ticket_id`, `user_id`, `sender`, `message_kind`;
  - итоговый delivery status;
  - classification (`success`, `client_error`, `rate_limited`, `provider_error`, `timeout`, `network_error`, `validation_error`, `unknown_error`);
  - severity / retryability (`ok`, `warning`, `critical`, `transient`, `terminal`);
  - `http_status`, provider error code/message, краткий response excerpt;
  - timestamps и длительность попытки.
- Встроить запись ledger в `DialogReplyService` / `DialogReplyTransportService` для text и media reply-path.
- Для `Telegram` / `VK` / `MAX` собрать provider-specific разбор ошибок и нормализовать его в общий classification contract.
- Добавить analytics page и API с overview, списком последних delivery attempts и history по каналу.
- Сохранять snapshots/summary в `monitoring_check_history`, чтобы был общий monitoring timeline.

## Ограничения и допущения

- Ledger не должен хранить полный текст сообщений и тем более секреты; допустимы только безопасные excerpts и provider metadata.
- В этом срезе приоритет у outbound `send` операций; edit/delete reply-path можно не включать, если это заметно раздувает контур.
- Источник истины по channel metadata остаётся `channels`; отдельный CRUD провайдеров не нужен.
- Если provider response нельзя полноценно распарсить, попытка всё равно должна попадать в ledger со статусом `unknown_error`.

## Критерии готовности

- В monitoring contour есть persisted ledger outbound delivery attempts.
- После operator/AI reply в `Telegram` / `VK` / `MAX` создаётся запись с нормализованной classification.
- В analytics есть отдельная страница просмотра overview и последних delivery attempts.
- Есть API/manual refresh/history для use-case расследования инцидента.
- Изменения покрыты целевыми тестами.
