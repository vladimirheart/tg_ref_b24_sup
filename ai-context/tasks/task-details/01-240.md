# Задача [01-240] Восстановить realtime inbox, feedback и media после исчерпания PostgreSQL connections и duplicate bot runtime

## Цель

Устранить задержку realtime-сообщений и media, дубли Telegram/feedback-ответов и массовые ошибки production contour.

## Контекст

- `panel-web`, `ops-worker` и `bot-runner` возвращают readiness `503`; PostgreSQL отвечает `FATAL: sorry, too many clients already`.
- Внутри `panel-web` обнаружен вручную запущенный `bot-telegram`, хотя active channels уже обслуживает `bot-runner`.
- В логах тестового Telegram подтверждён `409 Conflict: terminated by other getUpdates request`.
- `UiEventOutboxWatcher` останавливается на `feedback_created`: сохранение `Notification.created_at` передаёт строку вместо PostgreSQL `timestamptz`. Checkpoint не движется и блокирует все следующие client/message/media realtime events.
- Feedback параллельно обрабатывается legacy `OperatorNotificationWatcher`, создавая дублирующие operator notifications.

## Что сделать

- Запретить web/worker роли запускать или останавливать child bot process.
- Убрать duplicate feedback watcher, оставить owner за `UiEventOutboxWatcher`.
- Сделать обработку одного outbox event fault-isolated.
- Исправить PostgreSQL mapping `notifications.created_at`.
- Ограничить connection pool и выполнить controlled Java-role rollout.

## Критерии готовности

- В `panel-web` нет child bot JVM; Telegram не выдаёт `409 Conflict`.
- PostgreSQL принимает новые подключения, readiness Java-ролей `UP`.
- Ошибка `created_at ... character varying` исчезает.
- Клиентское текстовое сообщение и media видны в UI без последующего сообщения оператора.

## Выполнение

- Подтверждён источник `409`: вручную запущенный child `bot-telegram` внутри `panel-web` конкурирует с `bot-runner` за token.
- Подтверждено исчерпание PostgreSQL connections и повторяющаяся ошибка записи `notifications.created_at` как `character varying`.
- Внесены кодовые ограничения lifecycle API, исправление PostgreSQL mapping, fault isolation outbox и pool limits для Compose.
- PostgreSQL server-side capacity вынесена в `APP_POSTGRES_MAX_CONNECTIONS`; для текущего contour задано `150` вместо image default `100`.
- Исправлено имя переменной pool-limit: custom datasource использует `APP_DB_MAX_POOL_SIZE`, который Compose получает из `APP_POSTGRES_POOL_MAX_SIZE=6`.
- Обнаружено, что `java-bot` строит отдельные child Hikari pools; лимит добавлен и для bot datasource перед следующей targeted пересборкой `bot-runner`.
- `spring-panel` успешно проходит compile-gate. Production image собирается; rollout и пользовательская проверка realtime/media ещё не выполнены.
- `java-bot` применяет `APP_DB_MAX_POOL_SIZE=6` и к дочерним PostgreSQL Hikari pool. После controlled rollout `bot-runner` запустил три канала; у каждого child JVM подтверждена переменная окружения с лимитом `6`.
- PostgreSQL после rollout: `max_connections=150`, 36 idle JDBC connections. Все runtime services имеют статус `healthy`; в контрольных логах отсутствуют `too many clients`, Telegram `409 Conflict`, ошибки `notifications.created_at` и ошибки outbox.
- Обнаружена и исправлена смежная ошибка feedback scheduler: `DialogAutoCloseSchedulerService` передавал `pending_feedback_requests.created_at/expires_at` строками. JDBC-параметры заменены на `OffsetDateTime`; профильные тесты `DialogAutoCloseSchedulerServiceTest` и `DialogTicketLifecycleServiceTest` прошли успешно (7 tests, 0 failures), новый `ops-worker` healthy и контрольный цикл прошёл без `expires_at ... character varying`.
- Требуется ручная приёмка: одно входящее текстовое сообщение после ответа оператора, одно media-сообщение и один ответ на оценку в Telegram и MAX. Ожидается немедленное появление в UI и ровно один автоматический ответ.
