# Задача [01-185]

## Короткое описание

Починить live-path нового обращения в PostgreSQL-first/RabbitMQ contour после обнаруженного smoke-дефекта: событие `ticket.created.initial_contact` должно гарантированно попадать в canonical panel DB, а клиент должен видеть только подтверждённый человекочитаемый номер обращения.

## Фактический дефект

Smoke 2026-08-24 показал:

1. java-bot завершил question-flow, сформировал технический ticket UUID и опубликовал `ticket.created.initial_contact` в RabbitMQ;
2. spring-panel listener упал в `IntegrationInboundEventInboxService.beginProcessing` с PostgreSQL ошибкой `event_id uuid` vs `varchar`;
3. recovery-query выполнялся в уже aborted PostgreSQL transaction;
4. canonical `tickets/messages/chat_history` не создавались, поэтому новое обращение не появилось в UI, notification watcher не дал bell и AI runtime не был вызван;
5. bot сразу после enqueue пытался получить request number через panel read API. Из-за asynchronous ingestion возникал race, и fallback показывал клиенту технический UUID.

## Реализация v45

- PostgreSQL V33 переводит `integration_inbound_event_inbox.event_id` в TEXT, в соответствии с Java String/SQLite TEXT transport contract;
- `beginProcessing` использует `INSERT ... ON CONFLICT(event_id) DO NOTHING`, поэтому duplicate delivery не переводит PostgreSQL transaction в aborted state;
- failed/stale inbox event по-прежнему может быть reclaimed через существующую retry semantics;
- bot-core ждёт canonical request number от panel bounded polling до 6 секунд;
- technical ticket UUID никогда не используется как client-facing request number в RabbitMQ mode;
- если canonical number ещё не готов, Telegram/MAX/VK отправляют нейтральное подтверждение без ложного номера;
- Telegram/MAX/VK используют единый confirmation contract;
- добавлены regression tests для duplicate inbox claim, opaque event ids, delayed canonical number и UUID suppression.

## Что проверить вручную

1. Перезапустить spring-panel на PostgreSQL и убедиться, что Flyway применил V33 без ошибок.
2. Создать НОВОЕ тестовое обращение через Telegram question-flow.
3. В логе bot увидеть enqueue/publish `ticket.created.initial_contact`.
4. В panel не должно быть SQLSTATE 25P02 или `event_id uuid ... varchar`.
5. Новое обращение должно появиться в списке, а клиентский номер иметь формат `yyyyMMdd-NNN`, не UUID.
6. Должно появиться операторское notification/bell по canonical chat_history.
7. После этого проверить AI decision для текста проблемы; 01-184 остаётся отдельной ручной приёмкой.

Статус: 🟣 AI-часть исправления готова, требуется live smoke на реальном PostgreSQL + RabbitMQ.
