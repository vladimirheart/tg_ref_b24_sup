# Задача: Production-архитектура Iguana + модуль управления инцидентами

## 0. Общая цель

Проект Iguana готовится к первому production-запуску.

Нельзя проектировать изменения как временный MVP, который через месяц придётся фундаментально переделывать.

Исходные ориентиры на старте:

- ~3000 диалогов в месяц;
- ~10 одновременно работающих операторов;
- ~10 активных интеграционных ботов.

Архитектуру необходимо сразу заложить с нормальным запасом:

- 30 000+ диалогов в месяц;
- 50+ одновременно работающих операторов;
- 100+ зарегистрированных интеграционных каналов;
- 40+ одновременно активных каналов;
- возможность запуска нескольких экземпляров backend;
- возможность запуска нескольких worker одного типа;
- отсутствие единой точки отказа в логике обработки сообщений;
- отсутствие прямого доступа integration workers к business database.

Кроме инфраструктурного рефакторинга необходимо реализовать полноценный модуль управления инцидентами, тесно связанный с существующими диалогами поддержки.

Работать от актуального состояния репозитория.

Перед изменениями обязательно изучить существующие:

- spring-panel;
- java-bot/bot-core;
- bot-telegram;
- bot-vk;
- bot-max;
- Dialog/ChatHistory/Ticket/Client модели;
- систему каналов;
- систему пользователей/ролей;
- SSE / notifications;
- attachments;
- ObjectPassport;
- monitoring;
- BotProcessService;
- BotRuntimeContractService;
- BotDatabaseRegistry;
- DatabaseBootstrapService;
- существующие Flyway migrations;
- application.yml;
- текущие SQLite wiring и документацию по БД.

Не создавать параллельную новую систему рядом со старой без интеграции.
Рефакторинг должен постепенно заменить старую архитектуру.

---

# 1. Основные архитектурные принципы

## 1.1. Iguana Backend — единственный владелец business data

После миграции НИКАКОЙ transport/integration worker не должен напрямую читать или изменять business database.

Запрещён production-сценарий:

Telegram/VK/MAX worker
    -> JDBC
    -> PostgreSQL

Правильный сценарий:

provider
    -> integration worker
    -> RabbitMQ / internal Iguana API
    -> Iguana Backend
    -> PostgreSQL

Только Iguana Backend имеет credentials к основной PostgreSQL.

---

## 1.2. Не создавать отдельную business DB для каждого бота

Нельзя хранить:

- dialogs;
- tickets;
- clients;
- chat_history;
- incidents;
- tasks;

в bot-1.db, bot-2.db и т.д.

Бизнес-данные должны иметь один source of truth.

При 100 ботах поиск всех непрочитанных диалогов не должен означать запрос к 100 БД.

---

## 1.3. Per-bot/per-channel storage допускается только для runtime state

Оставить архитектурную возможность локального runtime storage конкретной интеграции, например:

bot-17-runtime.db

Допустимые данные:

- provider offset;
- временный local spool;
- retry state;
- temporary delivery state;
- last successful polling marker.

Запрещённые данные:

- клиенты;
- диалоги;
- обращения;
- сообщения как business history;
- задачи;
- инциденты.

Local runtime DB не является source of truth.

При потере local runtime DB бизнес-история Iguana не должна пострадать.

# 3. PostgreSQL

## 3.1. Уйти от SQLite как основной business database

Production business storage перевести на PostgreSQL.

SQLite после миграции разрешается использовать только:

- migration utility для чтения старых DB;
- локальный adapter spool/runtime state при реальной необходимости;
- изолированные тесты, если это оправдано.

spring-panel и java-bot не должны поддерживать две полноценные параллельные business-schema SQLite/PostgreSQL после завершения миграции.

PostgreSQL должен стать canonical production storage.

---

# 4. Одна PostgreSQL database, несколько schemas

Использовать одну физическую PostgreSQL database:

iguana

Внутри создать логические schemas:

core
incidents
integrations
identity
monitoring
objects
knowledge
audit

Не создавать отдельную physical DB на каждый bounded context.

Причины:

- нужны транзакции между доменами;
- нужны нормальные FK;
- incidents тесно связаны с dialogs;
- tasks связаны с incidents и objects;
- clients связаны со всеми support-сущностями;
- проще backup;
- проще migrations;
- нет distributed transactions.

# 6. Flyway

Flyway должен быть единственным владельцем структуры PostgreSQL.

Создать PostgreSQL migrations отдельно от legacy SQLite.

Например:

db/migration/postgresql/

Запрещено:

- schema auto create Hibernate;
- SQL init от integration workers;
- CREATE TABLE IF NOT EXISTS в бизнес-коде;
- параллельное управление одной таблицей Flyway и bot schema.sql.

После миграции:

hibernate.ddl-auto = none

Integration workers не выполняют business migrations.

Удалить production-зависимость от:

SPRING_SQL_INIT_MODE=always

для java-bot.

---

# 7. Время

Все новые PostgreSQL timestamp columns хранить как TIMESTAMPTZ.

Backend работает с Instant / OffsetDateTime.

Не переносить legacy подход с timezone-less строками SQLite в новую schema.

При импорте старых SQLite timestamps использовать конфиг:

APP_LEGACY_TIMEZONE

и явно документировать преобразование.

---

# 8. Redis

Добавить Redis сразу.

Использовать для:

1. Spring Session;
2. короткоживущего cache;
3. live notification fan-out между несколькими backend instance;
4. distributed locks/leases, где это необходимо;
5. worker/channel coordination;
6. rate limiting state при необходимости.

Бизнес-данные в Redis не хранить как единственный source of truth.

Потеря Redis не должна уничтожать:

- диалоги;
- сообщения;
- инциденты;
- задачи;
- историю.

---

# 9. RabbitMQ

Добавить RabbitMQ как transport/event backbone интеграционного слоя.

Минимальные routing concepts:

integration.inbound.telegram
integration.inbound.max
integration.inbound.vk

integration.outbound.telegram
integration.outbound.max
integration.outbound.vk

incident.alert

dead-letter

Имена exchanges/queues выбрать аккуратно и централизованно.

Queues должны быть:

- durable;
- с persistent messages;
- retry policy;
- dead letter handling.

При ошибке после установленного количества retry событие должно попадать в DLQ.

---

# 10. Idempotency

Каждое входящее provider event должно иметь idempotency key.

Например:

platform + channel_id + external_message_id

В БД должен быть UNIQUE constraint.

Пример:

telegram:17:18727281

Повторная доставка provider event не должна создавать:

- второй dialog message;
- второе attachment;
- второй ticket;
- второй incident signal.

Idempotency должна быть обеспечена на уровне database constraint + application logic.

---

# 11. Transactional Outbox

Обязательно реализовать Transactional Outbox.

Пример отправки ответа оператором:

BEGIN

INSERT core.chat_history(...)
INSERT integrations.integration_outbox(...)

COMMIT

Только после COMMIT outbox publisher публикует событие в RabbitMQ.

Нельзя делать:

DB write
Rabbit publish
DB commit

без transactional guarantee.

Outbox должен содержать минимум:

id UUID
event_type
aggregate_type
aggregate_id
channel_id
payload_json
status
attempts
available_at
created_at
processed_at
last_error
correlation_id

Worker должен безопасно обрабатывать несколько outbox сообщений параллельно.

Использовать PostgreSQL mechanisms уровня:

FOR UPDATE SKIP LOCKED

или эквивалентный надёжный подход.

---

# 12. Integration Workers

Текущая модель "один channel = один JVM process" не должна быть обязательной архитектурой.

Новая модель:

Telegram Worker
    -> обслуживает N Telegram channels

MAX Worker
    -> обслуживает N MAX channels

VK Worker
    -> обслуживает N VK channels

Количество logical channels не равно количеству JVM processes.

---

# 13. Масштабирование workers

Архитектура должна поддерживать:

100 зарегистрированных channels
40 одновременно активных

и возможность запуска:

telegram-worker-1
telegram-worker-2
telegram-worker-3

без двойного polling одного channel.

Реализовать channel lease.

Worker должен получить lease перед началом exclusive polling.

Lease:

- имеет TTL;
- периодически renew;
- освобождается при graceful shutdown;
- автоматически истекает при падении worker;
- после expiry другой worker может забрать channel.

Redis подходит для lease coordination.

Worker без lease не имеет права poll соответствующий provider channel.

Для webhook-based integration использовать соответствующий routing без ненужного exclusive polling.

---

# 14. Worker configuration

Worker не должен читать configuration непосредственно из PostgreSQL.

Создать internal Iguana API либо control-plane mechanism.

Worker должен уметь:

- получить список назначенных channels;
- получить provider configuration;
- получить необходимые credentials;
- отправить heartbeat;
- сообщить health;
- сообщить runtime status.

Internal API защищать отдельной service authentication.

Provider tokens:

- никогда не писать в лог;
- никогда не класть в public API;
- никогда не отправлять в frontend;
- передавать worker только по защищённому internal channel.

---

# 15. Integration worker business responsibilities

Worker выполняет только:

- provider protocol;
- polling/webhook;
- download/upload provider media;
- normalization;
- retry transport operations;
- provider rate limiting;
- delivery acknowledgment;
- публикацию normalized event.

Worker НЕ принимает business decisions:

- создавать ticket или нет;
- закрывать dialog или нет;
- связывать incident;
- определять ответственного;
- изменять client status.

Это зона Iguana Backend.

# 18. NGINX

Добавить production reverse proxy configuration.

NGINX должен:

- принимать frontend HTTP/HTTPS;
- проксировать backend;
- поддерживать SSE;
- позволять load balancing нескольких backend instance;
- иметь корректные proxy timeout для SSE;
- не открывать internal worker API наружу без необходимости.

---

# 19. Stateless Iguana Backend

После изменений backend не должен хранить критичное runtime state только в Java RAM.

State распределяется:

business data -> PostgreSQL
sessions       -> Redis
files          -> MinIO
queues         -> RabbitMQ

Это должно позволить поднять backend-2 без изменений business code.

# 23. Новый модуль INCIDENTS

Инцидент является не отдельной системой рядом с support.

Инцидент — агрегированное состояние общей проблемы, обнаруженной в первую очередь через support dialogs, но также:

- monitoring;
- provider notification;
- manual operator observation.

Основной источник инцидента чаще всего — клиентский dialog.

---

# 24. Основные понятия incidents

Разделить:

## Dialog

Конкретная коммуникация с конкретным клиентом.

## Incident Signal

Конкретная информация о проблеме.

Signal может появиться:

- из dialog message;
- вручную;
- из monitoring;
- от provider.

Один dialog может дать несколько signals.

## Incident

Общая проблема, объединяющая один или несколько signals.

Один incident может связывать много dialogs.

# 30. Создание signal из dialog

На странице dialog добавить действие:

"Зафиксировать проблему"

или:

"Инцидент"

Flow:

1. оператор нажимает действие;
2. выбирает одно или несколько сообщений, послуживших источником;
3. выбирает category;
4. dynamic form запрашивает конкретику;
5. часть полей автоматически заполняется из dialog:
   - client;
   - channel;
   - object;
   - timestamp;
   - operator;
6. оператор вводит краткое техническое описание;
7. создаётся Incident Signal.

Signal сам по себе ещё не обязан создавать подтверждённый Incident.

# 31. Поиск похожих incidents

После заполнения signal backend ищет активные incidents.

Учитывать:

- category;
- object;
- location;
- channel;
- scope;
- provider;
- keywords;
- временную близость;
- связанные предыдущие обращения.

Первый алгоритм сделать deterministic + PostgreSQL text search.

Предусмотреть возможность расширения matching engine без изменения модели данных.

UI показывает:

Возможно связано с:

"Недоступна оплата через Сбербанк"

Dialogs: 12
Objects: 7

[Привязать]

[Единичная проблема]

По умолчанию оператор подтверждает связь.

# 32. Создание нового Incident из dialog

Оператор может:

1. создать SUSPECTED incident;
2. сразу создать CONFIRMED incident, если проблема очевидна;
3. прикрепить signal к существующему incident;
4. оставить signal как единичную проблему.

При создании incident:

- dialog связывается с incident;
- signal связывается с incident;
- создаётся incident_event;
- создаётся status history;
- создаются необходимые notifications/outbox events.

Всё должно происходить одной PostgreSQL transaction.

## Текущий статус на 2026-08-11

Задача находится в активной фазе поэтапного переезда на PostgreSQL-first runtime.

Что уже сделано в рамках текущей серии шагов:

- добавлен infrastructure-слой external DB mode для `spring-panel` и `java-bot`;
- `spring-panel` научен работать в external PostgreSQL-режиме без SQLite bootstrap для основных runtime datasource;
- bot launch contract передаёт во внешние bot-процессы PostgreSQL datasource-настройки;
- hot-path вставки переведены с `last_insert_rowid()` на generated keys в активном runtime-коде;
- runtime-проверки схемы пользователей переведены с `PRAGMA` на JDBC metadata;
- для external PostgreSQL добавлены Flyway-мосты для runtime auxiliary tables, monitoring и objects;
- bot-side runtime auxiliary self-bootstrap ограничен SQLite-режимом через `BotDatabaseRuntimeMode`;
- `SecurityBootstrap` больше не создаёт `user_authorities` в external PostgreSQL-режиме и требует, чтобы эту таблицу создавал Flyway.

## Что осталось по задаче в ближайшем practical scope

- добить оставшиеся PostgreSQL/Flyway пробелы для legacy business schema, которая всё ещё описана через `schema.sql`/`schema-postgres.sql` и частично живёт вне Flyway;
- убрать production-зависимость от `spring.sql.init` и `schema.sql` для external bot runtime, оставив её только для локального SQLite/dev-контура;
- провести аудит оставшихся runtime SQL-мест на предмет скрытых SQLite-допущений в активном коде и закрыть их точечно;
