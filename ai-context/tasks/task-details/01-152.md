# Задача [01-152]

## Короткое описание

Спроектировать структурированные select-вопросы в шаблонах бота с универсальным хранением ответов и переиспользуемой аналитикой обращений.

## Цель

Подготовить каноническую продуктовую и техническую постановку для развития шаблонов вопросов бота от свободного текста к структурированным ответам с вариантами выбора, чтобы ответы можно было:

- использовать как системные атрибуты обращения;
- агрегировать в dashboard и analytics;
- переиспользовать в маршрутизации, SLA и будущих сценариях классификации;
- расширять без точечных schema-костылей под каждый новый вопрос.

## Контекст

- В текущей модели `bot_settings.question_templates[*].question_flow` уже есть разделение `preset/custom`, обязательность вопроса и support для `excluded_options`, но полноценного manual select для произвольных списков вариантов пока нет.
- Runtime бота сохраняет ответы в плоский `Map<String, String>`, после чего при создании обращения в `messages` промоутятся только фиксированные поля `business`, `location_type`, `city`, `location_name`, `problem`.
- Текущие `/analytics` и `/dashboard` опираются либо на SQL-агрегации по фиксированным колонкам `messages`, либо на read-side `DialogListItem`, который также собирается из текущих полей обращения.
- Пользовательский запрос требует добавить сценарии вида:
  - «Выберите компанию» -> список вручную заданных вариантов;
  - «Выберите направление обращения» -> структурированное значение для dashboard;
  - дополнительную детализацию по ботам и смежным направлениям;
  - будущую унификацию через явную настройку наподобие «отображать в дашборд».
- Простое добавление UI-контрола `select` без изменения модели хранения приведёт к тому, что ответ будет виден в переписке, но не станет нормальным аналитическим измерением и не даст масштабируемого контракта для новых use case.

## Что сделать

- Зафиксировать каноническую модель одного вопроса шаблона с разделением на:
  - `input_type` (`text`, `single_select`, в перспективе `multi_select`);
  - `option_source` (`manual`, `preset`);
  - `options[]` со стабильными `id`, `label`, `active`;
  - `binding` для системного смысла ответа (`business`, `direction`, `bot_product`, `issue_type` и т.д.);
  - `analytics` как отдельный блок, а не неявный побочный эффект UI.
- Спроектировать универсальный слой хранения ответов обращения:
  - что остаётся в старых колонках `messages`;
  - какие ответы промоутятся в typed-поля для обратной совместимости;
  - какую отдельную сущность или таблицу нужно ввести для `ticket_attributes`.
- Определить минимальный набор системных ключей для первой реализации:
  - `business`;
  - `direction`;
  - `bot_product`;
  - при необходимости `issue_type`.
- Разделить product semantics:
  - `business` как уже существующее системное поле;
  - `direction` как новое измерение для направления обращения;
  - `bot_product` как уточнение внутри `direction=Боты`;
  - не смешивать новую модель с текущим `category`, пока не будет отдельного решения по унификации категории и направления.
- Подготовить staged implementation plan:
  1. MVP с `single_select`, `manual options`, `binding`, `analytics.enabled` и универсальным хранением атрибутов.
  2. Dashboard/analytics-этап с чтением новых измерений, фильтрами и графиками.
  3. Расширение на зависимые списки, маршрутизацию, SLA и `multi_select`, если это действительно понадобится.
- Описать правила эволюции справочников ответов:
  - почему нельзя агрегировать по `label`;
  - как обрабатывать переименование варианта;
  - как архивировать варианты через `active=false`;
  - как поддержать `Другое` без разрушения аналитики.
- Зафиксировать ожидаемый контракт UI/UX для настроек:
  - отдельный тип вопроса «выбор из вариантов»;
  - ручное управление вариантами ответа;
  - явное поле/переключатель вида «использовать в аналитике»;
  - более точная подкапотная настройка, чем просто чекбокс «отображать в дашборд».

## Критерии готовности

- Есть зафиксированная каноническая модель structured-question для bot templates, где явно описаны `input_type`, `options`, `binding` и `analytics`.
- Есть принятое решение по универсальному хранению ответов обращения, совместимое с текущими typed-полями `messages`.
- Определён минимальный scope первой реализации без архитектурного тупика.
- Отдельно описаны правила масштабирования: стабильные option IDs, soft-archive, fallback `Другое`, разделение `business/direction/bot_product`.
- Сформирован follow-up план реализации по слоям:
  - DB/migrations;
  - backend DTO/service/runtime;
  - settings UI;
  - dashboard/analytics read-side;
  - tests.

## Ограничения и риски

- Нельзя ограничиться только изменением frontend-редактора шаблонов: без универсального хранилища ответы не станут надёжной основой для аналитики.
- Нельзя использовать `label` варианта ответа как долговечный аналитический ключ: переименование разрушит исторические агрегаты.
- Нельзя перегружать текущий `category` без отдельного решения по обратной совместимости и семантике dashboard/read-side.
- `multi_select` не должен входить в первую итерацию, если не будет подтверждён реальный use case: это усложняет и хранение, и агрегирование, и UX.

## Предлагаемый первый implementation slice

- В шаблонах бота добавить `single_select` с ручными вариантами ответа.
- Поддержать `binding.key=business` для сценария выбора компании.
- Поддержать `binding.key=direction` для направления обращения.
- Поддержать `binding.key=bot_product` для уточнения по ботам.
- Оставить `problem` как свободный текст.
- Ввести универсальное хранение структурированных ответов обращения и отдельно промоутить системные поля в существующие typed-колонки `messages` для совместимости.
