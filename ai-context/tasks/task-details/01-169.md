# Задача [01-169]

## Краткое описание

Зафиксировать порядок sidebar-оповещений и сделать очередь RMS устойчивой к рестарту панели.

## Цель

Убрать два операционных UX/надёжностных дефекта:

- в dropdown оповещений элементы не должны прыгать вверх после пометки как прочитанных, пока список открыт;
- очередь ручного обновления RMS в `RMS Control` должна переживать рестарт `spring-panel` и автоматически восстанавливаться после запуска.

## Контекст

- Сейчас `spring-panel/src/main/resources/static/js/sidebar.js` рендерит оповещения отдельными секциями `unread/read`, поэтому после auto-read или ручной пометки элемент физически переезжает в другой блок и визуально сдвигает список.
- API `/api/notifications` уже отдаёт элементы в стабильном порядке по `created_at desc`, а backend не требует перестройки для самого факта пометки прочитанным.
- В `spring-panel/src/main/java/com/example/panel/service/RmsLicenseMonitoringService.java` очередь обновления RMS хранится только в памяти (`AtomicBoolean`, `AtomicReference`, `QueueProgressTracker`), поэтому любой рестарт панели очищает pending-состояние.
- `monitoring.db` уже используется как каноническое хранилище для RMS/SSL/iiko мониторинга и подходит для небольшой persistent-очереди с восстановлением на startup.

## Что сделать

- Перестроить клиентский рендер sidebar-оповещений на единый стабильный список без перестановки элементов при смене `read`-состояния.
- Сохранить визуальное различие между прочитанными и непрочитанными уведомлениями, не ломая existing auto-read и `read all`.
- Добавить в monitoring-контур persistent-хранилище очереди RMS refresh с отдельными записями для license/network задач.
- На старте `spring-panel` восстанавливать pending RMS-задачи из `monitoring.db` и заново отправлять их в executor без ручного вмешательства пользователя.
- Обновить backend-модель состояния очереди так, чтобы UI `RMS Control` продолжал показывать `queued/running/completed` корректно и после восстановления.

## Критерии готовности

- При чтении отображённых оповещений в sidebar список не поднимается вверх и не меняет порядок уже показанных элементов.
- Пометка одного уведомления и `Прочитать все` сохраняют read-state, но не пересортировывают текущий dropdown.
- Если пользователь поставил RMS refresh в очередь и перезапустил `spring-panel`, после старта очередь не теряется и задача продолжает/повторно начинает выполнение.
- `RMS Control` после рестарта показывает консистентное состояние очереди и не падает на пустых/восстановленных pending-записях.
- Есть локальная проверка изменённых контуров.
