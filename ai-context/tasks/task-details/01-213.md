# Задача [01-213]

## Короткое описание

Подключить Alertmanager к утвержденному Iguana incident/notification delivery boundary и доказать end-to-end доставку firing/resolved alerts.

## Цель

Закрыть оставшийся operational gap после `01-194`: Alertmanager уже агрегирует и хранит состояние alerts, но внешний receiver намеренно локальный. Production alert должен доходить до существующего надежного notification/incident контура Iguana без ad-hoc provider secrets в infrastructure YAML.

## Контекст

- `01-194` добавляет Prometheus/Grafana/Alertmanager/Loki/Alloy и versioned alert rules.
- Текущий `observability/alertmanager/alertmanager.yml` сознательно не содержит SMTP/webhook/provider credentials.
- В Iguana уже есть incident delivery/outbox, SMTP monitoring и provider delivery ledger (`01-200`, `01-203`).
- Новый transport не должен обходить существующие retry/idempotency/audit boundaries.

## Что сделать

- Выбрать внутренний Alertmanager ingestion contract для Iguana.
- Принимать firing/resolved events только из internal Docker/network boundary с явной authentication/signature policy.
- Нормализовать alert labels/annotations в incident/notification event.
- Проводить delivery через существующий durable outbox/provider boundary, а не напрямую из Alertmanager в Telegram/VK/MAX/SMTP credentials.
- Обеспечить idempotency по alert fingerprint/status transitions.
- Добавить delivery/audit observability и failed-delivery signal.
- Добавить end-to-end smoke: synthetic Prometheus alert -> Alertmanager -> Iguana delivery boundary -> recorded delivery/result.
- Документировать secret rotation и failure modes.

## Критерии готовности

- Critical/high alert реально покидает Alertmanager и попадает в approved Iguana delivery pipeline.
- firing/resolved не создают неконтролируемые дубли.
- Provider credentials не хранятся в Alertmanager YAML/Git.
- Failed delivery виден через существующий incident/provider monitoring.
- Есть automated E2E smoke и runbook.
- После AI implementation статус только `🟣`; `🟢` — после ручной проверки пользователя.

## Обязательные дополнительные условия

- Не создавать новый публичный endpoint без необходимости; ingestion должен быть internal-only.
- Не добавлять Docker socket/host-control privileges.

## Update 2026-08-27 - Alertmanager internal ingestion implementation

Chosen boundary:
- generic Alertmanager webhook -> internal `panel-web` endpoint;
- random Bearer token from an ignored dedicated host secret file (`config/secrets` by default);
- public nginx contours return 404 for `/internal/observability/**`;
- no provider credentials or ad-hoc Telegram/VK/MAX/SMTP sender in Alertmanager.

Event mapping:
- only high/critical are routed externally from Alertmanager;
- `signal_type=alertmanager`;
- `signal_key=Alertmanager fingerprint`;
- firing opens a signal incident with an approved incident route;
- resolved resolves the active signal incident;
- repeats are deduplicated by fingerprint/status transition;
- shared per-fingerprint Redis lease prevents concurrent processing across panel-web replicas.

Delivery:
- initial alert route is created before the first `incident_signal_updated` enqueue;
- all delivery continues through `incident_route_delivery_outbox`;
- existing delivery retry/diagnostics/failed-delivery Prometheus signals remain authoritative;
- local `severity=medium` rule `IguanaAlertmanagerDeliveryFailed` covers Alertmanager webhook failures that happen before an Iguana outbox row exists without recursively using the failed webhook.

Automated source/unit verification is part of the apply. A real Docker E2E smoke is provided but cannot be executed while the operator's project is stopped.

Status stays YELLOW until the production observability contour is started and the firing/resolved E2E smoke is GREEN. Only after that may AI move the task to PURPLE; GREEN still requires explicit operator verification.

### 01-213 resume after PowerShell 5.1 smoke parser gate

The initial v1.1 apply reached the verification phase after writing the complete 01-213 implementation, then stopped on the PowerShell parser for `scripts/docker-alertmanager-delivery-smoke.ps1`.

Root cause: a double-quoted error string contained `$LASTEXITCODE:`. In Windows PowerShell 5.1 a colon immediately after an unbraced variable name is parsed as part of a scoped variable reference. The correct form is `${LASTEXITCODE}:`.

The resume:
- accepts only the exact generated bad smoke SHA or the exact corrected SHA;
- rewrites only the smoke script when required;
- repeats PowerShell parser checks;
- validates Bash syntax when available;
- validates the base + observability Compose model without starting containers;
- runs Maven `test-compile` and targeted 01-213 plus backup source-contract tests;
- runs `git diff --check`.

No project process or Docker service is started by the resume. Task 01-213 stays YELLOW until the real firing/resolved Docker E2E smoke is GREEN.

### Update 2026-08-27 - local AllowInsecureDefaults preflight compatibility

During the real `01-213` E2E startup, the production launcher failed even with `-AllowInsecureDefaults` when `.env` was absent because the insecure branch still called `Assert-RequiredSetting` for values that already have documented Compose defaults.

The compatibility fix changes only local/insecure semantics:
- when `-AllowInsecureDefaults` / `--allow-insecure-defaults` is explicit, missing values are materialized only in the launcher process environment;
- explicit process environment and `.env` values always win;
- PostgreSQL/RabbitMQ/Redis/MinIO/Grafana values match the existing documented Compose/.env.example defaults;
- `MONITORING_CREDENTIALS_MASTER_KEY` prefers the existing ignored `config/shared/monitoring-credentials.key` through the `base64:` compatibility bridge when that file exists;
- no `.env` file is created or modified;
- secure production mode continues to reject missing/default secrets.

A complete secure first-run + existing-volume migration flow is intentionally deferred to separate task `01-216`.
