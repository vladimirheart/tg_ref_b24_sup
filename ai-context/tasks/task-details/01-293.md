# Задача [01-293]

## Короткое описание

Сделать выбор бизнеса каноническим и единым для вопросника и оператора, а
действия с бизнес-обращениями направить в scoped-контур без legacy fallback.

## Цель

Выбранный клиентом в вопроснике или оператором бизнес сохраняется в
`tickets.business_id`, корректно отображается в общем списке и открывает
безопасную карточку бизнес-обращения. Оператор выбирает бизнес только для
неразрешённого обращения, где вопросник его не определил.

## Контекст

- `messages.business` — исторический текст сообщения, не источник правды для
  business scope.
- `tickets.business_id`, `ticket_public_id` и `is_general` образуют
  канонический scope обращения.
- Явный GENERAL не переклассифицируется в BUSINESS; для него выбор бизнеса не
  предлагается.
- Доступность выбора определяется разрешением оператора на работу с целевым
  бизнесом. Угадывание бизнеса по тексту, каналу или локации запрещено.

## Что сделать

- Передавать канонические scope и название бизнеса в общий список обращений.
- Добавить транзакционный endpoint оператора для однократного выбора бизнеса
  только у UNRESOLVED-обращения, с аудитом и UI outbox event.
- Перенаправить открытие и действия BUSINESS-обращения в существующую
  business-карточку; старые raw-ticket команды должны вернуть понятный
  conflict, а не ложный 404.
- Убрать изменение бизнеса через legacy свободное текстовое поле UI/API.
- Покрыть критические сценарии тестами и проверить миграции PostgreSQL.

## Критерии готовности

- Бизнес из вопросника отображается по `tickets.business_id`, даже когда в
  сообщении нет текстового значения бизнеса.
- Оператор с правом OPERATE может выбрать только доступный бизнес для
  UNRESOLVED-обращения; повторное изменение и изменение GENERAL/BUSINESS
  отклоняются.
- Назначение категории, закрытие и другие действия с BUSINESS-обращением не
  попадают в legacy API.
