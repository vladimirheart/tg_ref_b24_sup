# Задача [01-292]

## Короткое описание

Диагностировать, почему новое обращение остаётся без бизнеса и почему
операторские действия отвечают «диалог не найден».

## Цель

Подтвердить источник обоих симптомов по данным, логам и коду, оценить их общую
причину и подготовить безопасный scope исправления без изменения production
данных во время диагностики.

## Контекст

- Текущий production-like Docker contour работает локально; `panel-web`,
  `ops-worker` и `bot-runner` healthy.
- Бизнесовые обращения используют защищённый scoped API и canonical owner из
  `tickets`.
- Нужно различать отсутствие бизнес-назначения при создании от отказа доступа
  к уже созданному обращению.

## Что сделать

- Проследить путь нового обращения и условия назначения `business_id`.
- Проверить API операторских действий, scope/access guard и актуальные логи.
- Сформулировать подтверждённую причину, последствия и узкий план исправления.

## Критерии готовности

- Есть воспроизводимая, подтверждённая кодом или логами причина для каждого
  симптома либо честно указан недостающий сигнал.
- Production данные, конфигурация и контейнеры не изменены диагностикой.

## Результат диагностики

- В проверенном новом обращении `tickets.business_id` задан, а в связанных сообщениях нет текстового поля `messages.business`. Общий список обращений строит подпись бизнеса только из `messages.business`, поэтому показывает «Без бизнеса», хотя бизнес назначен корректно.
- Запрос смены категорий попадает в legacy endpoint с raw `ticketId`. Он загружает диалог, но затем legacy guard сознательно отвергает BUSINESS owner. Результат склеивается с настоящим отсутствием записи и возвращается как HTTP 404 «Диалог не найден».
- BUSINESS lifecycle уже реализован отдельно через canonical public ID и scoped owner в форме бизнес-обращения. Общая карточка диалогов не передаёт в клиент scope и public ID, поэтому не может выбрать этот путь.
- Исправление требует scope-aware представления в общем списке и маршрутизации действий в BUSINESS lifecycle; ослаблять legacy guard нельзя.
