# Задача 01-309

## Запрос пользователя

> ответил другой оператор, не я, но я вижу в диалоге пользователя с прочерком и моей аватаркой, а у ответившего оператора отображается его аватарка и его логин.

## Цель

Показывать в истории диалога фактического автора операторского сообщения: его отображаемое имя, логин и аватар, независимо от того, кто открыл карточку.

## Причина

`chat_history` сохраняет роль отправителя `operator`, но не его учётную запись. Рендерер истории из-за этого подставляет профиль текущего просмотрщика каждому операторскому сообщению.

## Границы

- Хранить identity автора только для новых исходящих операторских текстовых и медиа-сообщений.
- Не выполнять backfill и не изменять рабочие диалоги.
- Не расширять доступ оператора между BUSINESS: в исследованном обращении ответивший пользователь не имеет membership или `ALL_BUSINESSES`-гранта, поэтому scoped take/categories намеренно не могут быть выполнены.

## Критерии готовности

- История API возвращает автора и URL его аватара для новых сообщений оператора.
- Обычная и workspace-история показывают автора сообщения, а не текущего просмотрщика.
- Старые записи без identity остаются читаемыми с безопасным прежним fallback.
- Есть миграция и targeted Java/Node regression-проверки.

## Результат

- Добавлена миграция `V101__chat_history_sender_identity.sql`: новое nullable-поле `sender_identity` не меняет старые строки.
- Текстовые ответы, медиа-ответы и runtime relay сохраняют identity оператора вместе с ролью отправителя.
- API истории обогащает сообщение логином, отображаемым именем и URL аватара автора; обычная и workspace-история используют эти поля вместо профиля просмотрщика.
- Для схемы без новой колонки исходящие сообщения сохраняют прежний формат до выполнения миграции.
- Проверены `DialogConversationReadServiceTest`, `DialogReplyServiceTest`, `DialogReplyTargetServiceTest` (40 Java tests, GREEN), Node regression `dialog-message-author-r309.test.js`, `node --check` и `git diff --check`.

## Диагностика scoped-операций

В фактическом обращении автор ответа — активная учётная запись, но у неё отсутствуют membership целевого BUSINESS и активный `ALL_BUSINESSES` grant. Поэтому canonical scoped assignment и category mutation не могут выполнять `take`/`categories`; их 404 — безопасный результат отсутствия доступа, а не потеря категорий. Для ожидаемого поведения этому оператору нужно выдать доступ к соответствующему BUSINESS либо `ALL_BUSINESSES` grant. Изменение этой политики в код не выполнялось.
