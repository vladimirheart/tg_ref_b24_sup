# Задача [01-232] Устранить конкурирующие Telegram long-polling экземпляры с одним токеном

## Короткое описание

Оставить ровно один активный long-polling процесс на каждый Telegram bot token и исключить `409 Conflict`.

## Цель

Сделать приём сообщений детерминированным: Telegram не должен поочерёдно отключать экземпляры бота из-за одного токена.

## Контекст

- В `logs/support-bot-telegram-1-process.log` зафиксированы повторяющиеся `409 Conflict: terminated by other getUpdates request`.
- Логи показывают активные процессы как минимум для каналов `telegram-1` и `telegram-3`; требуется сопоставить их bot token и способ запуска.
- Текущие процессы запущены через Maven runtime (`target/classes`), не Docker profile `bot-telegram`.

## Что сделать

- Сопоставить каждый Java-процесс с channel id, username и безопасным fingerprint токена из его startup log.
- Остановить только дублирующий экземпляр каждого токена штатным lifecycle-путём панели.
- Проверить отсутствие новых `409` в process logs после стабилизации.
- Перезапустить нужный Telegram-бот после применения `01-231` и отправить тестовый текст и стикер.
- Добавить технический guard/диагностику, если launcher позволяет второй process для уже активного token.

## Критерии готовности

- На каждый token работает один ingress owner.
- В логах нет повторяющихся `409 Conflict`.
- Текст и стикер принимаются стабильно; клиентские fallback-ответы читаемы.

## Выполнение

- Исторический `409` подтверждён для `tst_int_SV_bot`; channel `telegram-3` использует другой token fingerprint и не является его дублем.
- Причина в защите найдена и устранена: Redis ingress lease строился по `GROUP_CHAT_ID`, из-за чего один token с разными чатами мог одновременно получить два lease.
- Telegram lifecycle теперь использует SHA-256 fingerprint токена. Секрет не попадает в Redis key и не выводится в лог.
- Проверено: `mvnw.cmd -pl bot-telegram -am -Dtest=BotIngressCoordinationServiceTest,BotPropertiesTest,SupportBotTest,SupportBotChoiceInputContractTest -Dsurefire.failIfNoSpecifiedTests=false test` — 9 tests, 0 failures.
- Runtime-проверка отложена в `01-235`: на момент работы нет Java bot process и остановлены PostgreSQL/RabbitMQ, поэтому безопасный restart и проверку отсутствия новых `409` выполнить невозможно.

## Обязательные дополнительные условия

- Не останавливать процессы без подтверждённого соответствия token и канала.
- По завершении показать алерт через `./ai-context/baseline/scripts/show-completion-alert.sh`.
- В финальном ответе подготовить `Резюме для коммита`.
- После file changes создать отдельный changelog в `ai-context/changelog` с пользовательским промптом.
