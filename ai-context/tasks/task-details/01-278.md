# Задача [01-278]

## Статус

🟡 В работе: S0-контракт, S1 source foundation и S2A ticket locator/read-only
assignment preview/disabled feature flags foundations зафиксированы. Это только
исходники additive Flyway-моделей и services,
проверенные во временной PostgreSQL Testcontainers-схеме; S2B–S6 не начаты.
Рабочая/production БД, backfill и rollout не изменялись и не выполнялись.

## Короткое описание

Ввести в Iguana универсальные независимые бизнесы: собственные списки обращений и настраиваемых вопросов, общий обзор доступных бизнесов, гибкие права сотрудников и безопасную маршрутизацию общих каналов, без обязательной связи с iiko либо другим внешним ПО.

## Цель и граница задачи

Превратить текущие текстовые обозначения «бизнеса» в каноническую предметную модель, чтобы:

- «Суши» и «Блины» существовали по умолчанию как **два отдельных бизнеса**, каждый со своим списком обращений и вопросами; существующая работа с ними и история сохранялись;
- можно было создавать любое число новых бизнесов (например, автосервис) без iiko, 1С, CRM, бота либо иной интеграции;
- вопросники, шаблоны, обращения, диалоги и относящиеся к ним события разных бизнесов не смешивались ни в интерфейсе, ни через API, очередь, поиск, оповещения или фоновые задания;
- сотрудник имел единую учетную запись и доступ к одному, нескольким или всем бизнесам, с функциональными ролями/правами в соответствующем контексте;
- режим «Все доступные бизнесы» давал сводный просмотр, не расширяя права и не изменяя принадлежность исходных данных;
- бизнес, локация, юридическое лицо, интеграция и канал оставались **разными сущностями**: iiko — лишь один из необязательных источников справочников/событий.

Термины: **«вопросы»** — настраиваемые шаги вопросника бота/формы; **«обращения»** — `tickets` и их связанные диалоги/сообщения. Изоляция требуется для обоих смыслов, но модели их хранения различны.

## Принятые пользовательские решения

1. Выбран вариант Б: **каждому бизнесу — независимый список**, плюс общий обзор.
2. «Суши» и «Блины» — предустановленные бизнесы. Новые направления не попадают в их вопросы/обращения автоматически.
3. Сотрудник может работать со всеми бизнесами, с несколькими выбранными либо только с одним; отдельные учетные записи для разных бизнесов не нужны.
4. Наличие интеграции iiko либо вообще какого-либо внешнего ПО не является условием создания бизнеса.
5. Разграничение обязано работать на сервере и в хранилище; один UI-фильтр недостаточен.

## Целевая модель (предварительное техническое решение, проверить до SQL)

### 1. Бизнесы, сотрудники и доступы

- `businesses`: внутренний стабильный ID, уникальный неизменяемый code/slug, отображаемое имя, статус (active/archived), служебные timestamps, опциональные настройки. Предустановленные Суши/Блины — обычные записи со стабильными ID/code, не два специальных `if` в приложении.
- `business_memberships` или эквивалентная таблица на **канонического авторизованного пользователя `users.id`**: доступ к конкретным бизнесам, роль/permissions в данном бизнесе, состояние membership. Точную связь с существующими `roles`, direct `user_authorities` и `panel_users` проверить перед реализацией.
- Отдельный явно назначаемый `ALL_BUSINESSES` grant для доступа ко **всем существующим и будущим** бизнесам; по умолчанию никто его не получает. Такой grant **не равен** глобальному системному администратору.
- Функциональные полномочия (читать/отвечать/администрировать/управлять настройками) и data scope (какие бизнесы доступны) проверяются **совместно**. Роли могут отличаться для разных бизнесов; не дублировать пользователей.
- Функция `resolveAccessibleBusinessIds(user)` и серверная business scope guard — единая логика для UI/API/внутренних сервисов. Режим ALL представляет union разрешенных IDs, а не обход авторизации.

### 2. Обращения и жизненный цикл

- Каноническая принадлежность каждого нового `ticket` — ровно один `business_id`, определенный до фиксации root ticket/message; добавить FK и индексы только в согласованной additive migration.
- `messages.business` остается совместимым legacy display/metadata-полем на переходный период и не служит authority для проверок доступа.
- `chat_history`, `ticket_attributes`, `ticket_categories`, `ticket_participants`, `ticket_responsibles`, `ticket_spans`, `ticket_active`, attachments, AI/dialog state и уведомления получают принадлежность **через канонический ticket** либо явный persist scope там, где нет безопасной ссылки.
- На чтении **и записи** проверять `business_id`: прямые URL `/dialogs/{ticketId}`, ID API, действия reply/edit/delete/resolve/reopen, поиск, pagination/count, экспорт, SSE/realtime/outbox, фоновые задачи и webhook paths.
- Не переносить существующий `ticket_id` в новую нумерацию и не переписывать историю. Привязку к composite key `(user_id,ticket_id)` / globally unique public ID уточнить отдельно; исключить ambiguity на чтении дочерних сущностей.
- Изменение бизнеса у существующего обращения — отдельная привилегированная, протоколируемая операция с проверкой связанных записей; не считать смену бизнес-фильтра в UI переносом данных.

### 3. Каналы, боты, шаблоны вопросов

- Поддержать как **отдельный канал одного бизнеса**, так и **один канал нескольких бизнесов** (это реальный сценарий R2A: 2 смешанных канала из 3).
- Обеспечить `business_channel_bindings`/правила маршрутизации либо эквивалент: идентифицировать допустимые бизнесы канала и правила выбора (явный вопрос, структурированный ответ, сопоставленная локация, проверенное внешнее событие); конфликты не разрешать молча.
- Для shared-канала сначала определить или явно запросить бизнес, затем использовать **его** цепочку вопросов, а не общий глобальный список. Замороженный в `ticket` scope сохраняется при последующих сообщениях/ответах/feedback/retry.
- Изолировать definitions/versions вопросников и шаблонов по `business_id` (и, где нужно, по каналу). При создании бизнеса можно **скопировать** стартовый шаблон, но последующее изменение не должно менять шаблоны других бизнесов.
- Сохранить совместимость с текущими `channels.questions_cfg`, `question_template_id`, `rating_template_id`, `auto_action_template_id`, `settings_parameters`, `ticket_attributes` и Telegram/VK/MAX. Точная форма новых таблиц определяется после отдельного анализа владельца конфигурации/ID и precedence.
- Рассмотреть идемпотентность входящих событий, пересылок/редактирований, delayed retries и outbox: `business_id` определяется авторитетно и не теряется при асинхронном переходе; неизвестный scope → управляемое отказное состояние/ручное назначение, не произвольный default.
- Новый бизнес может работать без внешней интеграции: ручное создание локаций/обращений, а подключение iiko, CRM или другого источника — отдельная optional связь.

### 4. Локации, организации и интеграции

- Канонические `business_locations` / `locations` должны ссылаться на `business_id` и хранить собственный ID, тип, название, статус; legacy дерево/параметры iiko остаются совместимыми до migration plan.
- Отдельно моделировать юридические лица, объекты/паспорта и сторонние источники: не отождествлять текстовую локацию, GUID iiko, юридическое лицо и business ID.
- Для источников iiko использовать mapping внешнего идентификатора к существующим внутренним ID, не пересоздавая уже связанные сущности. Изменение синхронизации не должно перезаписать пользовательский business scope.
- Объекты/заметки/оборудование, workforce/мониторинг/инциденты разделять по явно утвержденной модели: business-owned, shared-by-permission либо global/system. Не выполнять механический backfill всех таблиц.

### 5. Задачи, проекты, статистика, уведомления

- У каждой новой бизнес-задачи есть авторитетный scope; если задача связана с обращением, принадлежность согласована с ним. Не менять существующие `tasks.id`, `projects.id`, board/task placements, membership и события.
- Для задач без связанного обращения и для инфраструктурных инцидентов вводить явную политику `business | global_system | unresolved`, а не выбирать произвольный бизнес. Project/board и analytics-фильтры не должны показывать запрещенные бизнесы.
- Уведомления, operator watchers, UI outbox и SSE направлять только участникам/исполнителям с соответствующим доступом; email/chat delivery channel не расширяет data scope. Уведомления системного уровня должны иметь отдельный явный тип и полномочия.
- Общий обзор — агрегирование строго `accessibleBusinessIds`, с business label для каждого элемента, без двойного подсчета shared-канала и без изменения первичных данных.
- AI/knowledge/analytics read paths тоже должны соблюдать business scope при извлечении контекста, отчете, предложении и автодействии.

4. Проверить три несовпадения `chat_history.channel_id`: отличать легальную историю перенаправления от ошибочной ссылки; источник принадлежности — canonical ticket.
5. Отдельно классифицировать две задачи без ticket link, 105 инцидентов и общесистемные оповещения без ложного бизнес-атрибута.
6. Зафиксировать evidence до/после: точные counts, долю unresolved, FK checks, повторяемость backfill, отсутствие переприсвоения первичных ID и hash/снимки контрольных агрегатов. Для unresolved — защищенная очередь ручного решения, без silent assignment.
7. Обсудить, нужно ли блокировать включение строгой фильтрации, пока остались unresolved записи; минимум — не показывать их пользователям без специального права на ручную классификацию.

**Важно:** данный task-файл не разрешает и не запускает backfill. Любая migration/production mutation — отдельная явно согласованная стадия с preflight и rollback.

## UI/UX контракт

- В панели компактный переключатель `Все доступные | Суши | Блины | ...`; отображать только разрешенные сотруднику бизнесы. При одном разрешенном бизнесе лишний выбор можно скрыть.
- В режиме «Все доступные» список показывает бизнес у каждой строки/карточки; при выборе бизнеса — только его обращения/задачи/метрики.
- На странице настроек отдельный каталог бизнесов: создать/переименовать/архивировать бизнес, привязать сотрудников, локации, каналы, шаблоны и необязательные интеграции, не затрагивая чужой business scope.
- Сотруднику доступны явные multi-select бизнесов или динамическое разрешение «Все бизнесы»; роли в бизнесах редактируются независимо от membership других бизнесов.
- Создание нового бизнеса не переписывает существующие вопросы Суши или Блинов. Пустой бизнес корректно отображает отсутствие данных; ручное создание обращения остается возможным.
- Динамический switch не должен раскрывать открытый чужой диалог из прежнего контекста; при смене бизнес scope проверить детали, вложения, autocomplete, счетчики, сохраненные фильтры и realtime subscription.
- Следовать существующим theme tokens, компактным UI-паттернам Iguana, keyboard navigation и понятным сообщениями об отказе в доступе.

## Критерии готовности (end-to-end)

1. Есть два начальных независимых бизнеса Суши и Блины; новый третий бизнес создается без интеграций и не появляется в вопросниках/списках первых двух.
2. Одна учетная запись с доступом к A,B видит A,B и их объединение, но не C; пользователь только A не видит B через list, direct ID API, поиск, файлы, SSE, UI, exports и counts.
3. `ALL_BUSINESSES` дает доступ к новому бизнесу без ручного добавления membership, но не делает человека системным администратором; операции в бизнесах по-прежнему ограничены ролями.
4. Shared channel с бизнесами A и B задает бизнес **до** вопросника/создания тикета, выбирает нужный вопросник, не смешивает ответы/обратную связь и корректно обрабатывает retry/event replay.
5. Разные бизнесы могут иметь одинаковые наименования локаций, вопросов, шаблонов и категорий без смешивания ID; редактура шаблона B не меняет A.
6. Записи без бизнес-принадлежности и конфликты не попадают в произвольный business list; действуют согласованные политики для `UNRESOLVED` и `GLOBAL_SYSTEM`.
7. Существующие 47 тикетов, 47 root messages, 619 history и 108 attachment metadata не теряют связи, идентификаторы и историю; исторические 3 channel mismatch обработаны по согласованной модели.
8. Задачи, проекты, board placements, уведомления, realtime, AI, monitoring/integrations корректно разделяют business и global/system state.
9. Все изменения имеют targeted unit/integration/security tests (включая реальные PostgreSQL constraints, transport replay, cross-business negative paths), build GREEN и доказанную backward compatibility.
10. Развертывание, миграция, backfill и rollback выполняются только по отдельному разрешению с проверяемыми checkpoint и независимой пост-приёмкой.

## S2A: сериализация ingress по legacy ticket ID (R3)

- До проверки composite idempotency и записи root data ingestion берёт PostgreSQL
  transaction advisory lock из exact legacy `ticket_id`; concurrent событие с
  тем же ID ждёт commit/rollback первого обработчика и затем проходит обычную
  canonical/collision проверку.
- Lock не нормализует ID, не создаёт business assignment и освобождается
  PostgreSQL автоматически вместе с транзакцией. Схема, legacy rows и
  production/runtime не изменялись.
- Этот же guard применён к ingress клиентских сообщений до lookup ticket: child
  history с тем же legacy ID не может обойти незавершённое создание root-ticket.
- Inbound client message использует canonical `(user_id, ticket_id)` из event
  для lookup ticket и не вызывает bare `findByIdTicketId`.
- Оставшиеся legacy service paths без полного tuple используют только
  fail-closed resolver: bare `ticket_id` допустим лишь при ровно одном
  кандидате; duplicate mapping возвращает отсутствие ticket и не выбирает
  произвольную запись.

  bot-runtime перед чтением или записью проверяют тот же инвариант через

### R12: origin задач и произвольные связи (проектный контракт 2026-10-11)

**Статус: PROPOSED_NOT_APPROVED.** Пользователь условно согласился с моделью и уточнил: правила наследования бизнес-принадлежности относятся только к задачам, создаваемым из обращений. Созданные вручную задачи независимы и могут иметь связи с любыми поддерживаемыми сущностями. R11 сохранил отдельное защищённое предложение, но формальное согласование остаётся PENDING.

**Факты по source на R12 baseline:**

- `TaskApiController` создаёт ручные задачи без обязательного ticket relation.
- `DialogAutoCloseFollowUpTaskService` создаёт автоматические задачи через `PanelTaskService` с `source=dialog_auto_close` и ссылкой на обращение.
- `Task.source` сейчас свободная строка, а не canonical origin. `task_links` хранит связи с обращениями через `(task_id, user_id, ticket_id)`; project membership хранится отдельно. Универсальный entity-link registry ещё не реализован.

**Предложение для отдельного product signoff и будущей реализации:**

1. Ввести явный immutable/controlled provenance задачи: создана вручную, порождена обращением или исторически не установлена. Ни наличие ссылки, ни текст `source` сами по себе не определяют provenance.
2. Задача, **созданная из обращения**, наследует бизнес только из подтверждённого canonical `tickets.business_id` исходного обращения, разрешённого по public ID или полному `(user_id, ticket_id)`. Если owner не определён, неоднозначен или недоступен, использовать fail-closed unresolved policy и не выбирать бизнес эвристически.
3. **Ручная задача** самостоятельна: может иметь ноль, одну или много ссылок на поддерживаемые сущности разных бизнесов. Связь с обращением не превращает её автоматически в ticket-derived задачу и не расширяет права чтения/изменения.
4. Собственная видимость задачи и видимость **каждой** связанной сущности проверяются раздельно; нельзя раскрывать скрытые названия, поля, счётчики, файлы, комментарии, события, уведомления или поисковые результаты. Универсальная модель links ещё требует проектирования и проверок; существующие `task_links`/projects не переписывать в R12.
5. Две исторические задачи без ticket link **нельзя** классифицировать автоматически как `UNRESOLVED`/`GLOBAL_SYSTEM`: это могут быть корректные ручные задачи. Их классификация остаётся PENDING до защищённой проверки.
