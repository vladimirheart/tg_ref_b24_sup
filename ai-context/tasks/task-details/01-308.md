# Задача 01-308

## Запрос пользователя

> найден не слабый баг: после прохождения клиентом опросника, на описание проблемы, если оператор не ответил, то все сообщения клиентом перетираются и остаётся только последнее сообщение. например последний сегодняшний диалог

## Цель

Показывать в карточке обращения каждое сообщение клиента, отправленное после завершения опросника, даже пока оператор не ответил.

## Контекст и причина

В последнем обращении от 24.11.2026 PostgreSQL содержит все 12 сообщений клиента с разными provider message ID; записи не перезаписываются. Ошибка находится в `dialogs-details-history-runtime.js`: UI сворачивал любой начальный непрерывный блок клиентских сообщений до одного предполагаемого описания проблемы. Поэтому в паузе до первого ответа оператора исчезали обычные follow-up сообщения.

Начальные ответы опросника в `chat_history` не имеют `ticket_public_id`, а сообщения уже открытого обращения получают immutable public ID. Это позволяет передать в read model доказанный признак ответа опросника и сворачивать только такой начальный блок, не угадывая его по тексту или отсутствию ответа оператора.

## Что сделать

- Передать в DTO истории признак начального ответа опросника, только если он доказан canonical owner tuple и public ID обращения.
- Ограничить сворачивание истории UI только этим начальным блоком.
- Добавить backend и Node-регрессии: несколько follow-up сообщений клиента без реплики оператора должны оставаться видимыми.
- Обновить cache marker изменённого runtime-скрипта.

## Критерии готовности

- Сообщения после анкеты отображаются все, если оператор ещё не отвечал.
- Ответы опросника могут оставаться компактными, но не классифицируются по эвристике текста.
- Исторические/неподтверждённые строки не скрываются.
- Targeted Java и Node проверки проходят.

## Границы

Миграции, backfill, изменение рабочих диалогов и deploy не выполняются. Исправляется только read model и клиентский рендер истории.

## Результат и проверки

- В `ChatMessageDto` добавлен `questionnaireAnswer`. Read model выставляет его
  только для client-строки без public ID, когда полный owner tuple
  `ticket_id/user_id/channel_id` доказывает, что у обращения уже есть public ID.
  Строка с чужим owner, операторская строка и строка с public ID остаются
  обычной историей.
- UI сворачивает только непрерывный начальный блок таких доказанных ответов
  анкеты. Он больше не делает вывод по тексту сообщения или по отсутствию
  ответа оператора, поэтому follow-up реплики клиента не пропадают.

  клиентскую логику после выпуска.

  классификации дала `questionnaire` только для первых шести; последующие
