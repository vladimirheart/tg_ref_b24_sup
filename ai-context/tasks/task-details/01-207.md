# Задача [01-207]

## Короткое описание

Расширить provider delivery ledger на `edit/delete` reply-path и runtime-инициированные outbound senders вне `operator quick-actions`.

## Цель

Сделать `provider_delivery_ledger` ближе к реальному operator/runtime delivery contour:

- покрыть не только первичную отправку reply/media, но и последующие outbound mutations;
- не терять provider-side изменения сообщений, если они выполнены через `edit/delete`;
- фиксировать outbound send success, которые произошли вне panel quick-actions и дошли до панели только через internal bot runtime write API;
- сохранить единый monitoring / analytics / alerting source of truth для outbound provider activity.

## Контекст

- В `01-203` ledger уже покрывает direct `send` для text/media reply-path через `DialogReplyService`.
- В `01-206` поверх этого ledger появился burn-rate alerting, так что новые outbound paths важно не выводить в отдельный контур и не дублировать в другой таблице.
- По фактическому коду сейчас есть две реальные дыры:
  - `DialogReplyService.editOperatorMessage(...)` и `deleteOperatorMessage(...)` выполняют provider side effect, но не пишут попытку в ledger;
  - `BotRuntimeTicketWriteService.recordOperatorRelay(...)` и `markOperatorMessageEdited(...)` отражают runtime-инициированные outbound события в panel-side state, но не синхронизируют их в ledger.
- `ai_agent` уже использует `dialogReplyService.sendReply(..., "ai_agent")`, поэтому его direct auto-reply path в текущем состоянии ledger уже покрыт.
- Отдельной internal runtime API для provider-side delete сейчас нет, так что в `01-207` достаточно честно закрыть существующие runtime write paths без изобретения несуществующего контракта.

## Что сделать

- Расширить transport/ledger contract для provider-side `edit/delete` операций.
- Для panel-side quick actions записывать в ledger:
  - успешные и неуспешные `edit`;
  - успешные и неуспешные `delete`.
- Для runtime-observed internal API записывать в ledger как минимум:
  - `operator-relay` success path;
  - `operator-message-edited` success path.
- Использовать текущие поля ledger (`sender_kind`, `message_kind`, classification/severity/retry) без введения новой business-таблицы, если этого достаточно для различения operation kind.
- Обновить overview/history/API/UI так, чтобы новые `message_kind` / `sender_kind` корректно отображались в аналитике.
- Добавить целевые тесты на:
  - `DialogReplyService` edit/delete ledger recording;
  - `BotRuntimeTicketWriteService` runtime-observed ledger recording;
  - при необходимости controller/API contract, если меняется surface.

## Ограничения и допущения

- Источником истины остаётся текущий `provider_delivery_ledger`; отдельный runtime-owned ledger не нужен.
- Для internal bot runtime write API допустима модель `observed success`: панель фиксирует уже подтверждённый runtime-side outbound outcome, который пришёл постфактум через trusted internal API.
- В рамках `01-207` не требуется придумывать новые internal write endpoints только ради полноты delete-path, если такого runtime contract в проекте сейчас нет.
- Если operation platform фактически не поддерживает `edit/delete`, это должно приводить к честной classification в ledger, а не к silent skip.

## Критерии готовности

- `provider_delivery_ledger` фиксирует panel-side `edit/delete` reply-path.
- `provider_delivery_ledger` фиксирует runtime-observed outbound success path вне operator quick-actions для уже существующих internal API.
- Analytics/history корректно показывают новые operation kinds и sender kinds.
- Изменения покрыты целевыми тестами.

## Текущее состояние

- `DialogReplyTransportService` переведён на структурированный `DialogReplyTransportResult` и теперь одинаково классифицирует `edit/delete` transport outcomes для ledger.
- `DialogReplyService` пишет в `provider_delivery_ledger`:
  - успешные и неуспешные provider-side `edit`;
  - успешные и неуспешные provider-side `delete`;
  - validation failures для неподдержанного/неполного channel transport контракта.
- `ProviderDeliveryLedgerService` расширен helper-методом `recordObservedSuccess(...)` для trusted runtime-observed outbound success paths.
- `BotRuntimeTicketWriteService` теперь синхронизирует в ledger:
  - `recordOperatorRelay(...)` как `sender_kind=operator_runtime`, `message_kind=text`;
  - `markOperatorMessageEdited(...)` как `sender_kind=operator_runtime`, `message_kind=text_edit`.
- Целевые тесты добавлены/обновлены:
  - `DialogReplyServiceTest`;
  - `BotRuntimeTicketWriteServiceTest`;
  - `DialogQuickActionsIntegrationTest`.
- Во время верификации дополнительно закрыты совместимости test/runtime contour:
  - явный constructor DI для service-beans с test-only overload constructors;
  - lenient timestamp converter для `Notification.createdAt`;
  - SQLite-safe generated-key fallback в `DialogReplyTargetService` media path;
  - актуализированы media attachment expectations в integration-тесте под `by-storage-key` URL.

  - `DialogQuickActionsIntegrationTest` ранее был прогнан целиком; после точечного фикса оставшихся media-scenarios последний остаток был снят адресным перепрогоном этих двух методов.
