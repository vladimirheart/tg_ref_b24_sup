# R209: Operational notification load shedding

## Статус

Действует с 25.11.2026.

## Правило

Persisted bell-уведомления предназначены только для критичных операционных состояний:

- incident с severity `critical` или выше;
- event, содержащий escalation;
- SLA-эскалация просроченной первой реакции;
- AI-эскалация диалога.

Routine-события диалога — новое обращение и входящее сообщение клиента — не создают notification rows для всех операторов. Они остаются доступными через список диалогов, историю и UI realtime events.

## Представление оповещений — 01-317

- Оценки клиента не создают bell-оповещений. Старые оповещения об оценках
  исключаются одним SQL-предикатом до пагинации и из unread count/read mutations;
  записи оценок и отчёты не удаляются, realtime обновление сохраняется.
- В текстах оповещений о диалогах используется canonical номер YYYYMMDD-NNN.
  UUID/legacy ticket_id не является display fallback. При ожидании регистрации
  сообщать об отсутствии номера. Точный ID в URL, SQL и scope не заменяется номером.
- Все legacy summaries и пересылки техническому каналу Telegram/VK/MAX используют
  номер. Подтверждение клиенту и summary используют один результат ожидания номера.
  Запрет raw support-chat summary для BUSINESS и guards доставки сохраняются.
- Bell показывает иконку и цветную подпись раздела (Диалоги/Инциденты/Задачи/
  Проекты/Мониторинг/База знаний/Настройки/Система). Source — только presentation,
  не доказательство доступа или расширение получателей. Неизвестный источник — Система.
- Внешнее техническое сообщение отделяет источник/платформу/доступное имя канала
  от тела. HTML клиента и произвольные source keys не попадают в разметку UI.

## Производительность

Fallback polling sidebar обязан иметь один in-flight запрос и увеличивать интервал после ошибки. Нельзя использовать независимый `setInterval` для endpoint, который может работать дольше интервала.

## Граница PostgreSQL

`APP_POSTGRES_MAX_CONNECTIONS=550` — серверный потолок контура. Он не отменяет ограничений отдельных Hikari-пулов: увеличение pool size требует отдельной оценки суммарной concurrency и памяти хоста.
