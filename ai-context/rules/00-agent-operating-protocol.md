# Правило: обязательный operating protocol AI-агента

## Статус

Действует. Обязательно к чтению перед изменением репозитория.

## Главный принцип

Агент продолжает работу от фактического состояния репозитория и явно подтвержденного состояния среды, а не от предположений, устаревшего chat-summary или ранее сгенерированного operator.

Безопасность изменения важнее скорости и формального уменьшения количества шагов.

## 1. Сначала свежий контекст

Перед новым structural/functional step агент должен:

- поднять применимые `ai-context/tasks`, `ai-context/rules`, `ai-context/changelog`, `ai-context/mcp` и baseline rules/guides;
- получить свежий `HEAD`/`origin/main` или свежий GitHub `main`;
- для файлов, которые будут изменяться, читать свежую версию из этого commit, а не полагаться на старый фрагмент из чата;
- при необходимости зафиксировать ожидаемые blob SHA или иные точные content guards;
- проверить предыдущий commit: SHA, parent, message и фактически измененные файлы, если следующий шаг зависит от его успешного применения.

Если baseline operator устарел, нельзя советовать пользователю `reset` только ради того, чтобы старый operator снова подошел. Нужно прочитать свежий `main` и подготовить новый operator/patch против нового baseline.

## 2. Значение пользовательского `готово`

`готово` трактуется только в контексте непосредственно предыдущей инструкции.

Примеры:

- если агент сказал «после `git push` напиши `готово`», это означает, что пользователь сообщает о выполненном push;
- это не является автоматическим подтверждением всей задачи, production acceptance или разрешением менять task-status на `🟢`;
- task-status `🟢` выставляется только после явного пользовательского принятия результата в смысле task workflow;
- если AI закончил работу, но пользователь еще не принял ее, используется `🟣` согласно baseline task protocol.

Нельзя подменять факт выполнения технического шага фактом пользовательской приемки.

## 3. Разделять факты состояния

При любой автоматизированной правке отдельно фиксируются как минимум:

- `baseline`;
- `head`;
- `origin_main`;
- `sandbox_green`;
- `source_applied`;
- `staged`;
- `committed`;
- `pushed`;
- `deployment`;
- список реально измененных project files.

`source_applied=true` допустимо сообщать только после фактической записи project files в рабочий checkout.

Успешная sandbox-валидация и применение в рабочий checkout — разные факты.

## 4. RED означает остановку commit-flow

Если operator завершился `RED`:

- при `sandbox_green=false` и `source_applied=false` считать рабочий checkout неизмененным и не предлагать commit;
- если `source_applied=true`, не предлагать commit до разбора `git status`, diff и причины ошибки;
- не маскировать ошибку ослаблением существующего integration/layout/contract test без отдельного подтвержденного scope;
- сначала диагностировать точную причину RED, затем выпускать новую версию operator/patch.

## 5. Один scope — один structural commit

Не смешивать в один commit независимые structural refactor, functional behavior change, deploy, migration и metadata closeout, если пользователь явно не выбрал другой формат.

При structural refactor:

- сохранять публичное поведение;
- добавлять/обновлять targeted contract tests;
- не изменять legacy wording или quirks только потому, что они выглядят странно;
- не дробить связный orchestration/state/I/O код только ради уменьшения размера файла.

Размер файла — review signal, а не самостоятельная причина декомпозиции.

## 6. Commit/push остаются пользовательским действием

Guarded operator, который вносит source changes, по умолчанию не должен:

- `git add`;
- `git commit`;
- `git push`;
- выполнять deploy;
- выполнять DB migration/backfill или внешнюю mutation.

После GREEN агент дает пользователю точный список файлов и готовый PowerShell-блок для staging/commit/push.

Перед commit пользователь должен иметь возможность увидеть:

- `git status --short`;
- `git diff --cached --check`;
- `git diff --cached --name-only`.

Список staged files должен совпадать с ожидаемым scope точно, а не «примерно».

## 7. Не считать untracked безопасными по умолчанию

Operator-artifacts (`apply-*.js`, zip и т.п.) могут лежать untracked в корне репозитория.

Status guard может игнорировать только точные известные имена собственных operator-artifacts. Нельзя игнорировать все untracked files или wildcard-категорию целиком: это может скрыть пользовательскую работу.

## 8. Changelog и task metadata

- changelog является append-only журналом фактических изменений;
- task details должны описывать реальный scope и фактическую валидацию;
- AI не должен объявлять deployment, migration, backfill, push или acceptance выполненными, если они не были реально выполнены и подтверждены;
- metadata closeout выполняется после технического завершения, а не вместо него.

## Практический смысл

Любой новый AI-агент должен иметь возможность продолжить работу после смены модели/чата без догадок, не потерять production checkpoint и не выполнить опасный шаг только потому, что старый operator или старый summary выглядели актуальными.
