# Понятные описания инцидентов

R13 задачи 01-281, 24.10.2026. Представление должно объяснять наблюдаемую
проблему, возможное влияние и что проверить. Не выдавать предположение за
подтверждённую первопричину: недоступность метрик не доказывает остановку
сервиса, отсутствие отметки работы — остановку процесса, разница cursor IDs —
точное количество необработанных записей.

Каталог incident-descriptions.js — чистое UI-преобразование сохранённого
сигнала. Не переписывать исторические title/summary/description, editable
values или payload; исходный текст доступен в технических подробностях.
Ручные описания сохраняются. Для неизвестного внешнего сигнала показывать
честный fallback, а не угадывать диагноз. Закрытый инцидент описывает прошлое,
не текущее состояние. Все строки при HTML-rendering экранируются.

Согласовывать пояснения известных Alertmanager rules с условиями в
observability/prometheus/rules/iguana-alerts.yml, не расширять backend access
и не запускать проверки ради построения пояснения. Изменение представления
не должно менять маршрутизацию, формулы/пороги, мониторинг или историю.

R14: объяснять, какие операции стоят за счётчиком и что означает повторение
проверок. N проверок подряд не равны N новым ошибкам. Старые failed records
не выдавать за новые сбои. Текущая подробная выборка existing read-only
analytics API показывается отдельно от сохранённого snapshot, с датой загрузки,
датами записей, учётом limit и явным stale fallback при ошибке обновления.
Не смешивать её с закрытым инцидентом или отдельным другим worker signal.
Не добавлять analytics fetch без прежних прав; не сбрасывать drafts при
асинхронном обновлении подробностей. Навигация к записи не запускает replay.

R15: называть конкретный вид учётных данных и их настройку (например пароль
прокси канала), а не любой секрет «ключом интеграции». Пустые необязательные
поля и локальные proxy-поля невыбранного маршрута не являются critical:
сохранять прежние записи как not_required, без удаления истории. Это не
подтверждение отказа подключения. Не выводить значения секретов.
Ручной приоритет инцидента сохраняется транзакционно в журнале и имеет
преимущество при автоматическом обновлении; оценка мониторинга отделена от
приоритета оператора. Служебное событие приоритета нельзя подделать через
публичное добавление комментария. Для изменения схемы БД нужен отдельный scope.

R16: конкретные операции и названия задач показывать перед справочным текстом.
Для отдельного worker signal отбирать только его worker_key; общий список не
подменяет конкретную задачу. Возраст progress cursor — не heartbeat и не время
простоя: при cursor_lag=0 явно говорить об отсутствии более новых записей в
снимке, при неизвестном lag не объявлять задачу idle. Ненулевой ID gap не равен
числу пропущенных сообщений. Current GET не переписывает сохранённый snapshot,
историю или drafts; закрытые инциденты и отсутствие analytics grants остаются
за прежней границей. Эта UI-правка не меняет формулы stale/lag и мониторинг.

R17, 25.10.2026: требование R14/R16 показывать конкретные failed-сообщения
в карточке отменено владельцем. UUID обращений/событий, SQL-текст и список
ошибок отдельных записей остаются только в диагностике транспорта и логах.
Сами failed-счётчики не создают инцидент и не повышают его приоритет, включая
накопленную историю проверок; политика зафиксирована в
05-monitoring-policy-and-employee-pickers.md. В карточке сохраняются только
системные счётчики очереди и конкретные фоновые задачи. Существующие критерии
stale/lag в R17 не исправлялись; это не доказательство остановки процесса.

R18: по новому запросу владельца исправлены сами критерии progress monitoring:
idle/unknown/retired позиции не являются инцидентом. Возраст позиции отделять
от длительности подтверждённого наблюдения необработанных новых данных.
Новые правила и три отдельные настройки — в05-monitoring-policy-and-employee-pickers.md.
Исторический исходный текст сохраняется; снятие ложного сигнала не объявлять
успешной доставкой сообщений или доказательством восстановления обработчика.
