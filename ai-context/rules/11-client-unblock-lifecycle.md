# Жизненный цикл заявок разблокировки клиента

Действует с 25.11.2026, задача 01-313.

- Канонические поля client_blacklist.is_blacklisted и unblock_requested имеют
  PostgreSQL type BOOLEAN. JDBC-параметры и тестовые fixtures используют boolean,
  SQL-литералы TRUE/FALSE; integer 0/1 не допускаются.
- Pending unblock request не является подтверждением действующей блокировки.
  Решение повторно проверяет blacklist после блокировки записи.
- Порядок блокировок: blacklist клиента, затем заявка. После захвата заявки
  повторно проверяются pending status и user_id. Повторное решение не создаёт
  второй аудит/уведомление.
- Если блокировка уже отсутствует, заявка становится expired с пояснением.
  Blacklist не создаётся заново, фиктивное событие unblocked и сообщение клиенту
  не отправляются. История и первоначальная причина заявки сохраняются.
- Approve снимает существующую блокировку, reject её сохраняет; оба действия
  снимают флаг запроса. Изменения БД выполняются одной транзакцией, UI refresh
  публикуется после commit.
- Персональные отметки просмотра не меняют pending status и не подменяют решение.
  Права действий определяются AccessRecoveryService.canUnblockClient.
