# Начальная история клиента и запись исходящих ответов

Статус: действует с 01-316.

- Все сохранённые реплики клиента до, во время и после анкеты показываются
  оператору в исходном порядке. Короткий текст, совпадение с городом/бизнесом
  и questionnaireAnswer сами по себе не являются основанием скрыть сообщение.
  Отдельные технические события оценки/feedback фильтруются прежним способом.
- В chat_history ticket_owner_user_id хранит BIGINT владельца обращения,
  sender_identity — identity автора ответа. В INSERT ... SELECT с этими полями
  перечислять проекцию явно в порядке целевых столбцов; outgoing.* не подходит
  при добавлении автора перед присоединённым владельцем. Правило одинаково
  для текста и медиа. Проверять SQL реальным PostgreSQL, включая generated keys.
- Успех транспорта ещё не означает успех всей операции панели. Регрессия
  должна проходить запись истории, metadata, activity и назначение ответственного
  после симулированной доставки, не отправляя сообщения реальному клиенту.
- Исправление записи не является основанием повторно отправлять уже доставленные
  ответы или придумывать их отсутствующий в истории текст. Восстановление данных
  требует отдельного подтверждённого источника и scope.

## Внутренняя переписка — 01-322

- Сообщения сотрудников хранятся в dialog_internal_messages, отдельно от
  chat_history, клиентских транспортов, AI-источников и очередей доставки.
  Выдача сообщений и запись требуют PAGE_DIALOGS и текущего доступа к exact
  numeric/raw/public owner. Для записи дополнительно нужен OPERATE; приглашение
  в участники не требуется. Нет admin/global-directory bypass.
- Автор сохраняется по bound numeric account и точному stored username.
  Append-only запись, UUID request ID и точная проверка payload обеспечивают
  идемпотентность. Текст выводится как textContent. Выборка ограничена 50 записями
  с курсором; отдельная форма явно помечена «клиент не видит».
- Внутренний комментарий не назначает ответственного и не меняет клиентский
  unread/last message/анкеты/историю. При переносе бизнеса доступ проверяется
  заново по текущему root; старая membership не открывает внутреннюю переписку.

## Представление и непрочитанные — 01-323

- Автор показывается по users.full_name, присоединённому только по сохранённому
  author_user_id. Пустое ФИО использует snapshot login. Отображаемое имя не
  участвует в авторизации; Unicode/HTML выводятся как textContent.
- Персональные markers хранят монотонный last_read_id для exact numeric/raw/public
  owner. Mark-read требует текущий READ и существующий показанный ID того же
  диалога; нельзя отметить будущий/чужой ID. Свои сообщения не входят в unread.
  Внутреннее прочтение не меняет клиентские счётчики или историю.
- Bounded batch счётчиков принимает не более 100 public IDs, выполняет текущий
  scope/READ predicate и возвращает только разрешённые IDs/числовые строки.
  Счётчик виден и при свёрнутом блоке, и в строке списка.
- Read acknowledgement отправляется только для открытой, видимой переписки
  у её нижней границы. Новое сообщение следует за viewport у нижней границы;
  при чтении старых сохраняется позиция и показывается переход к новым.
- Внутреннее и клиентское поля разделены, но используют один send-mode control
  и общую настройку Enter/Ctrl+Enter. Клиентский draft/transport не участвует.
  Wheel/touch остаются в открытом диалоге и не прокручивают страницу под ним.

## Внутренние файлы — 01-324

- Бинарники принадлежат отдельному object-storage domain internal_dialogs,
  а metadata — dialog_internal_attachments. Они не регистрируются как клиентские
  chat_history attachments и не получают публичные/transport URLs.
- Multipart batch отправляется по current OPERATE/full owner. IO хранилища
  выполняется вне JDBC locks; в одной SQL transaction повторно проверяются
  account/grants/owner и записываются сообщение и все metadata.
- Idempotency включает body и упорядоченные name/MIME/size/SHA-256 файлов.
  Replay удаляет новые копии; известный rollback удаляет upload. При неизвестном
  результате commit объекты сохраняются приватными для reconciliation, чтобы
  не удалить уже зафиксированные файлы. API без metadata их не выдаёт.
- GET требует PAGE_DIALOGS/current READ того же numeric/raw/public owner, даже
  для preview/range. Имя не участвует в storage key. MIME определяется по
  содержимому; SVG/HTML и неизвестные типы — только download с nosniff/no-store.
- До 10 непустых файлов, суммарно до 50 МБ. Файловое сообщение может быть без
  текста. Клиентское поле/файлы отдельны; изменения unread/ответственного/outbox
  доставки не добавляются. Polling сохраняет существующие media DOM nodes.
