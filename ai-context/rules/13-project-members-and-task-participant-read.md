# Проекты и чтение задач участниками — 01-327

Действует поверх R302–R305/R327 для READ задач, с уточнением пользователя в R328:
участие в проекте открывает READ всех связанных задач. Владение не выводится из
creator/lead или отображаемых имён.

## Чтение задачи

- Ответственный, соисполнители и наблюдатели получают только READ своей задачи
  через task_people.user_id. OWNER/EDITOR/VIEWER в shared_task_members остаются
  отдельными явными назначениями. Производное участие не выдаёт WRITE/OWNER.
- Сохраняются current account, exact ID/raw username, PAGE_TASKS и ограничения
  enabled/blocked. R328: отсутствие shared_work_grants означает разрешение чтения
  для участника; явный can_read=false запрещает его. Создание по-прежнему требует
  отдельного разрешения. Системный администратор имеет прежний полный доступ.
- R328: NULL shared_owner_user_id не отменяет numeric task_people READ и явные
  EDITOR/VIEWER назначения. Один лишь creator/lead либо NULL owner ничего не даёт.
  OWNER membership действует только при совпадении с root.shared_owner_user_id;
  владельца назначают явно. Участник проекта читает все связанные с ним задачи;
  прочие задачи без самостоятельного участия остаются закрыты.
- List/count/page, «Мои задачи», прямой READ, вложения, notification recipients и
  поздняя доставка используют это же правило. «Мои» дополнительно фильтрует
  assignee/co/watcher по numeric user_id, включая переименованный аккаунт;
  одно лишь участие в проекте не включает задачу в «Мои».
- Состав меняется доверенным WRITE задачи. В той же транзакции новые назначения
  привязываются к единственному exact account; неизменённая историческая привязка
  сохраняется, в том числе NULL после удаления. Повторное использование логина
  другим аккаунтом не восстанавливает старое участие. Физическое удаление аккаунта
  ставит FK в NULL; identity/role остаются историческими данными.
- Удаление из состава отзывает производный READ. Явный grant остаётся независимым.
  READ удерживает share lock участника до commit; roster replacement ждёт окончания
  чтения/доставки. Глобальные права и допуски автоматически не выдаются.
- V109 один раз связывает существующие assignee/co/watcher с exact, однозначными
  users.id. Не делает trim/case folding, не связывает creator, не меняет ownership.
  Если assignee отсутствует в roster, V109 сохраняет его из канонического поля
  tasks.assignee, включая историческую подпись с NULL binding. Новые system
  follow-up writers записывают assignee в roster сразу: «Мои» не теряет такие задачи.

## Панель проекта

- «Сведения» и «Участники» находятся внутри прокручиваемой modal body. На карточке
  проекта есть явная кнопка участников; после создания открывается их вкладка.
- Добавление доступно OWNER/current system admin и видно перед длинным roster.
  Кандидаты берутся из server-scoped people API: активный однозначный аккаунт,
  PAGE_TASKS и отсутствие явного запрета чтения; поиск по логину или full_name.
  Дополнительная запись допуска не нужна. Результат mutation повторно читается
  без автоматического retry. Настройки общих прав показывают этот default явно.
- Дополнительные поля, архивирование, передача владельца и аудит свёрнуты. Действия
  состава сохраняются сразу, редактирование сведений — кнопкой «Сохранить».
- Производный taskParticipant в roster не предлагает бесполезный DELETE явного
  membership: такой READ меняется составом задачи. Явный membership можно отозвать.
- Запрет доступа закрывает карточку также во время открытия Bootstrap modal.

## R328 — конкурентный запрет чтения

Установка общего запрета блокирует users target FOR UPDATE. Это сериализует первый
INSERT can_read=false с уже выполняющимся READ, даже когда строки допуска ещё нет.
Обычные READ держат FOR SHARE account/member/participant до конца транзакции.
Account pre-lock выполняется отдельным statement до permission statement: после
ожидания первого INSERT запрета следующий READ COMMITTED snapshot уже видит его.
Отсутствующий/stale account не превращает empty-list чтение в исключение;
основной current-account predicate по-прежнему исключает его из reader.
Производный READ через проект держит FOR SHARE project/member/task-project link;
отзыв участия или удаление связи ждёт окончания чтения/доставки. После отзыва READ
через этот проект исчезает; независимое участие в задаче/другом проекте сохраняется.
Право редактировать проект не даёт права редактировать его задачи.
Назначения, владельцы и grants в рабочей БД автоматически не изменяются; новой
миграции для этой политики нет. V109 numeric roster остаётся источником участия.
